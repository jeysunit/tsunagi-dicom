# Design

## Context

- 決定（2026-10-25）：画面の値の修正を2種類に分ける。患者の属性（患者 ID・氏名・生年月日・性別）と受付番号の訂正は、IHE の PIR と同じく Study・Series・SOP Instance UID を保つ。HL7 の更新が持つ `Keep`・`Force`・元の置き換えの形を使い回す。画像の中身が変わる訂正（検査日など）は、今のまま新しい UID を作る。
- 原典は IHE RAD TF-2 Rev. 23.0（2025-08-08）の 4.14.4.1.3・4.16.4.2.3・4.17.4.2.3・4.13.4.3・4.12、IHE RAD TF-1 Rev. 23.0 の Case 6（4.3.1・4.4.6）。要点は `docs/spec.md` の 3.5 に書いた。
- HL7 による患者情報の更新（`openspec/changes/archive/2026-10-24-add-hl7-patient-update-receiver/design.md` と `openspec/changes/add-pir-case6-procedure-update/design.md`。以下「HL7 の設計」）は、UID を保つ書き換え・付け替えの印・元の画像の名指しの削除・書き換えの後の確かめ・結果不明の照らし合わせを持つ。
- 書き込みの操作の共通の決まり（役割・CSRF・ロック中の 423・要求の ID・呼ぶ前と後の監査の記録・結果不明・照らし合わせ・再認証）は `docs/spec.md` の 3.5 にあり、送信・削除が使っている。

## Goals / Non-Goals

**Goals:**

- 画面から、患者の属性と受付番号を UID を保って直す。
- 画面から、それ以外の値を新しい UID の検査として直す。
- 直す前の値を監査の記録に残し、誰が・いつ・何を・なぜ直したかを追えるようにする。

**Non-Goals:**

- 送った先の機器に、直した値を知らせること（HL7 の転送・自動の再送信）。送った先を直すのは施設の運用。
- 他の施設のデータを自施設の患者 ID に書き換えて取り込む形（`docs/spec.md` の 3.5 の取り込み。段 6 の別の PR で、この change の部品を使って決める）。
- 結合と分割（段 7）。

## Decisions

### 1. 2種類の分け方

- 属性の訂正：PatientID (0010,0020)・PatientName (0010,0010)・PatientBirthDate (0010,0030)・PatientSex (0010,0040)・AccessionNumber (0008,0050)。直す範囲で3つに分ける。
  - 患者の属性の訂正（氏名・生年月日・性別）：同じ患者 ID の Orthanc の全部の検査に当てる。DICOM の Patient Module（PS3.3 C.7.1.1）の属性は患者のすべての検査に共通で、1つの検査だけを直すと検査どうしで値が食い違い、HL7 の A40 の確かめ（替え先の患者の検査どうしで属性が揃っているか）にも断られる。HL7 の A08 と同じ範囲になる。検査ごとに1つの書き換えとして流し、途中で失敗すれば部分反映として残す。
  - 患者 ID の付け替え：選んだ1つの検査だけを、別の患者 ID へ移す（取り違えの直し）。替え先の患者が Orthanc にあれば、氏名・生年月日・性別はその患者の値にそろえる（入力の値と違えば断る。下の 2）。替え先の患者が無ければ、入力の値（入力が無ければ元の値）にする。患者の全部の検査を移す統合は HL7 の A40 の役目で、画面には持たない。
  - 受付番号の訂正：選んだ1つの検査だけに当てる。
- 中身の訂正：それ以外の直せる値。いまは StudyDate (0008,0020)・StudyDescription (0008,1030)。後で直せる値を足すときも、上の5つでなければ中身の訂正に入れる（UID を保つ側を広げるときは、その属性が PIR の患者の情報か手続きの情報に当たるかを原典で確かめ、`docs/spec.md` を先に直す）。
- 検査名（StudyDescription）は、手続きの情報（RAD-13）に近いが、2026-10-25 の決定は UID を保つ側に検査名を挙げていないので、中身の訂正に置く（これまでどおり新しい UID になる）。UID を保つ側へ移すかは、決めた方針を広げる判断になるので、この change では決めない。
- 1つの要求に2種類の値を混ぜた要求は、BFF が 400 で断る（監査の記録に `denied` として残す）。混ぜて受けると、UID を保つか作り直すかを1つに決められない。作り直す側に寄せると属性の訂正の UID が変わり、保つ側に寄せると中身の訂正が UID を保ってしまう。両方を直すときは、画面が属性の訂正を先に送り、終わってから中身の訂正を送る。
- 別の案は、混ぜた要求を受けて新しい UID で作る形。属性の訂正が UID を保つという決定を、利用者の入力の組み合わせしだいで破るので採らない。

### 2. 属性の訂正の書き方

- HL7 の設計の書き換えの部品（`src/lib/hl7/apply.ts` の書き換え・確かめ・照らし合わせと、`Backend` の `modifyStudyKeepingUids`・`studyInstanceFiles`・`deleteStudyInstances`・`lockStudy`・`unlockStudy`・`studyInstanceOrigins`）を、HL7 に依らない場所（例：`src/lib/keep-uid-write.ts`）に切り出し、HL7 と画面の両方から呼ぶ。HL7 の振る舞いは変えない（HL7 の試験が全部そのまま通ること）。
- 患者 ID を変える訂正は、A40 と同じく、付け替えの印を付けてから書き換え、書き換えた画像が新しい患者 ID の検査に揃い、写しの `ModifiedFrom` が元の画像の ID と合うことを確かめてから、元の画像を名指しで消す（HL7 の設計の 15.4）。
- 患者 ID を変えない訂正は、`OverwriteInstances: true` で元の画像を置き換える（HL7 の設計の A08・ORM と同じ）。
- 替え先の患者 ID の患者が Orthanc にすでにあるときは、移す検査の氏名・生年月日・性別をその患者の値にそろえる。確かめの画面には替え先の患者の値を出し、利用者が入力した値と違えば書き換えずに断る（打ち間違えた患者 ID へ移すのを防ぐ）。替え先の患者の検査どうしで値が食い違っているときも断る（A40 の替え先の確かめと同じ。取り違えを広げない）。
- 書き換えの後に全部の画像の UID と値を確かめ、合わなければ部分反映、答えが来なければ結果不明にする。結果不明の訂正が残る検査には、同じ検査への値の修正を断り、照らし合わせを求める（`docs/spec.md` の 3.5）。
- 画面の訂正と HL7 の書き換えは、同じ検査を同時に書き換えないように、同じ列（`enqueue`）で1つずつ流す。どちらかの結果不明・部分反映が残るあいだは、両方の書き換えを止める（HL7 の設計の 10 と同じ考え）。
- 列は重なりを防ぐだけで、確かめの画面を開いた後に検査が変わったこと（HL7 の A40 が同じ UID の検査を別の患者へ移したなど）は防がない。削除と同じく、確かめの画面で見せた検査（Orthanc の中の ID・UID・患者 ID・直す項目の前の値）を、サーバーの秘密で暗号化した短い期限の token に結ぶ。BFF は列の中で書き換える直前に、token の中身の全部がいまの検査と一致するかを確かめ、違えば書き換えずに 409 を返す（利用者は確かめの画面を開き直す）。
- 結果不明・部分反映を照らす・解く道も共有する。いまの `history()` は監査の記録の `hl7` の行だけを読み、管理者が手で解く `/api/hl7/resolve` もその行だけを相手にする。切り出しでは、`hl7` と `modify` の両方の行を読み、照らし合わせの結果はそれぞれの操作の行に書く。管理者が値の修正の結果不明・部分反映を手で解く道を足す（`/api/hl7/resolve` を広げるか、値の修正の道を別に置くかは実装の PR で決める。管理者だけ・理由・監査の記録は `/api/hl7/resolve` と同じ）。
- HL7 の見回り（HL7 の設計の 15.3 の 4）は、前に患者 ID を書き換えようとした画像が移す前の患者 ID に戻っていれば統合し直さない。画面の属性の訂正の `request` の行も、この「前に書き換えようとした画像」に数える（人が画面で書き戻した統合を、見回りが統合し直さないため）。
- 画面で患者 ID を付け替えた後に、装置が元の患者 ID・同じ StudyInstanceUID で画像を送ると、同じ UID の検査が2件並び、UID からの引き当てが 409 になる（HL7 の Case 6 と同じ場面）。次の2つで扱う。
  - 画面の付け替えも、A40 と同じ形の覚え（元の患者 ID・替え先の患者 ID・StudyInstanceUID・前の氏名など）を `result` の行に残し、見回り（HL7 の設計の 15）が受理から 24 時間拾えるようにする。見回りは HL7 の受け口が呼ぶので、受け口を動かしている環境（いまは開発の一式）でだけ効く。
  - 見回りが拾わない環境と、24 時間を過ぎた後のために、同じ UID の検査が複数あるときに、検査を Orthanc の中の ID で選んで患者 ID を付け替える道を用意する（確かめの画面に、同じ UID の検査を全部並べる）。
  - 自動で拾う方は、見回りの条件（HL7 の設計の 15.3）を画面の付け替えにもそのまま当てる。条件を緩めない。

### 3. 元の値の残し方

Orthanc は、同じ患者 ID の下に同じ UID の画像を1件しか持てない。属性の訂正では、元の画像を置き換えるか名指しで消すので、元の版は検査の中に残らない。

- 案 A（推奨）：監査の記録（`modify`）の `request` に、直した項目ごとの前と後の値（氏名は `=` で区切った組の全部）・StudyInstanceUID・元の Orthanc の検査の ID・書き換える画像の ID とファイルの印を残す。戻すときは、前の値への属性の訂正をもう一度行う（新しい要求として、理由と再認証を通す）。画像の写しを持たないので、BFF の側に患者の画像を置かずに済む（原則 10）。HL7 の更新と同じ残し方になる。
- 案 B：案 A に加え、書き換える前の検査をエクスポートと同じ形の ZIP として、施設が決めた置き場に残す。戻せるのは DICOM のファイル（直した属性のほかの値も含む）までで、Orthanc のメタデータ（受信の日時・送信元の AE タイトル・`Origin` など）は ZIP に入らず、入れ直しても元に戻らない（Orthanc が持つシステムのメタデータは REST から書けない）。受信の情報を残すなら、案 A の監査の記録に前の値として入れる（下の Risks）。案 B では、患者の画像の写しがアプリの外に増え、置き場の権限・保管の期間・削除の手順を施設が決める必要がある（第7.0版 7）。置き場への書き込みも、監査の記録と役割の確かめの対象になる。
- どちらにするかは実装の PR で決める。案 A だけで始め、案 B は設定で足せる形にする道もある。
- どちらでも、属性の訂正は削除の操作に当たらないとして、一般にも許す（`docs/spec.md` の 3.6）。画素は変えず、変わるのは直した属性だけで、前の値は監査の記録から戻せるため。

### 4. 属性の訂正に要る Orthanc の設定

- `OverwriteInstances: true`（患者 ID を変えない訂正の置き換え）、`LuaScripts`（`deploy/orthanc/tsunagi-lock.lua`）と `UserMetadata`（`TsunagiLock`）（患者 ID を変える訂正の付け替えの印）。いまは開発の一式と結合の試験の Orthanc にだけ入れている。
- 配る compose と施設の Orthanc の扱いは、次の2案から実装の PR で決める。
  - 案 1：配る compose の Orthanc に3つを入れる。どの施設でも属性の訂正を使えるが、`OverwriteInstances: true` は、装置が同じ SOP Instance UID の画像を送り直したときの扱い（無視する→上書きする）をすべての受信で変える。
  - 案 2：配る compose は変えず、施設が `tasks.md` の手順で入れたときだけ属性の訂正を使えるようにする。入れていない Orthanc では、属性の訂正を断る。
- 設定の無い Orthanc で書き換える前に断る方法（印を付けられなければ断る、のほかに `OverwriteInstances` を前もって確かめる道があるか）は、Orthanc の版で実測して決める。前もって確かめられなければ、書き換えの後の確かめで止める（値が変わらずに失敗として残る）。
- 中身の訂正は、これらの設定に依らない。

### 5. 中身の訂正の書き方

- Orthanc の `/studies/{id}/modify` に `Replace` を渡し、`Keep` を渡さない（新しい Study・Series・SOP Instance UID ができる）。元を残すか（`KeepSource`）は、Orthanc の版で実測して決める（`docs/spec.md` の 3.5）。一般の要求では元を必ず残し、BFF は一般の要求で元を消す指定を断る。
- 作られた検査を Orthanc で探して照らす方法（結果不明のとき）は、Orthanc の版で実測して決める（`docs/spec.md` の 3.5 の照らし合わせ）。

### 6. 画面の API と監査の記録

- `POST /api/studies/{uid}/modify`。本文は、要求の ID・訂正の種類（`attribute`・`content`）・直す項目と値・理由・確かめの画面の token（2）。種類と項目が合わなければ 400。確かめの画面（GET）は、直す検査（患者の属性の訂正では同じ患者 ID の全部の検査）と前の値、患者 ID の付け替えでは替え先の患者の値を返す。
- 役割は一般と管理者（`src/lib/auth/roles.ts` に `study.modify` を足す）。再認証はパスワードだけで、`REAUTH_MINUTES` の間は聞き直さない（削除と同じ）。CSRF・画面のロック中の 423・`DEV_ALLOW_WRITE` は共通の決まりのとおり。
- 監査の記録は `modify`。`request`（呼ぶ前）・`dispatch`（仕事の ID）・`result`（成功・失敗・部分反映・結果不明）。`detail` に種類・項目ごとの前と後の値・元と後の StudyInstanceUID（属性の訂正では同じ値）・理由・要求の ID を入れる。外から来た値（理由・直す値）は、制御文字を見える形にしてから記録に入れる。
- 値は DICOM の型と長さで確かめる（PS3.5 6.2：LO は 64 文字、PN は組ごとに 64 文字、DA は `YYYYMMDD`、CS の性別は `M`・`F`・`O`、SH の受付番号は 16 文字）。
- 本文の項目は「無い＝変えない」と「空の文字列＝値を空にする」を分ける。氏名・生年月日・性別・受付番号・検査日は Type 2（PS3.3 C.7.1.1・C.7.2.1。値が分からなければ長さ 0 の値を置く）なので、タグを残したまま空にできる（空だった値を直した後に、前の値へ戻せるようにするため）。患者 ID は空にしない（検査を患者に結べなくなる）。患者 ID は、HL7 の更新と同じく設定した発番元のものだけを受けるかを実装で決める。

## Risks / Trade-offs

- **送った先の機器には、直す前の値が残る。** 属性の訂正の後も、送った先の機器にある画像は、同じ UID で前の値を持つ。PIR はこの形（同じ UID で値の違う画像）を前提にしているが、tsunagi-dicom は送った先に知らせない。送った先を直すには、施設が再送信するか、送った先の機器で直す。再送信で上書きされるかは送った先の設定による。
- **Orthanc のメタデータが変わりうる。** 置き換えた画像の受信の日時・送信元の AE タイトル・入った道（`Origin`）が、書き換えの時の値になりうる。そうなると、受信一覧と、インポートの印（`docs/spec.md` の 3.5 の案 A は `Origin` を使う）の表示が変わりうる。実装の PR で Orthanc の版で実測し、変わるなら前の値を監査の記録に残すか、インポートの印の判別を変える。
- **取り違えを広げる恐れ。** 誤った患者 ID への訂正は、UID を保ったまま別の患者の検査にまとめる。理由と再認証を必須にし、確かめの画面に前と後の値を並べ、替え先の患者の属性が違えば断る（2）。戻すのは前の値への訂正。
- **HL7 との競合。** 同じ検査を HL7 と画面が続けて書き換えると、後の書き換えが前を上書きする。同じ列で1つずつ流し（2）、どちらの書き換えも監査の記録に残るので、後から順を追える。RIS から後で A08 が届けば、画面の訂正は RIS の値で上書きされる（RIS を正とする運用では、画面の訂正は RIS の直しと合わせて行う）。
- **設定の無い Orthanc。** 案 2（4）では、属性の訂正を使えない施設が出る。断るときの文言で、Orthanc の設定が要ることを示す。

## Migration Plan

- 実装は段 6 の中の1つのまとまりとして出す（AGENTS.md の PR の単位）。HL7 の部品の切り出しを先の PR にし、HL7 の試験が全部通ることを確かめてから、値の修正の PR を出す。
- データベースは変えない（監査の記録の `detail` に入れる）。
- 戻すときは前の版に戻す。属性の訂正で直した値は Orthanc に残る（監査の記録の前の値で、手で戻せる）。
