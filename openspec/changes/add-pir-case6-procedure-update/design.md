# Design

## Context

前の設計（`openspec/changes/archive/2026-10-24-add-hl7-patient-update-receiver/design.md`。以下「前の設計」）の 1〜14 は変えない。この change は、前の設計の 9（3 つのメッセージの反映）を広げ、15・16 を足す。番号は前の設計の続きにし、コードのコメントの `design.md §15`・`§16` はこの文書を指す。

- 承認者の決定（2026-10-25 06:25）：照合の後に仮の ID で届いた画像も正式の患者に書き換える。ORM の CA・DC・XO を受けて、検査を消さずに印を付ける（受付番号を外すか、使わない検査の印かは作るときに決める）。対応の記録をいつまで覚えるかも作るときに決める。患者の取り違えの影響が大きいので、試験を厚くする。
- 送り手は ris-emulator の照合（`docs/spec/07_reconciliation.md` の 3.4・4.3）と、DTG の緊急の患者の追加撮影（`exam --emergency --append --study-uid`）。
- tsunagi-dicom は検査の状態の印を持たない（`docs/spec.md` の原則 10）。BFF のデータベースに持つのは、利用者・画面の設定・ビューアの覚え・監査の記録だけ。

## Goals / Non-Goals

**Goals:**

- 照合（A40）の後に、仮の患者 ID のまま同じ Study で届いた画像を、統合した先の患者の検査にまとめる。
- RAD-13 の ORM（CA・DC・XO）を受け、Orthanc の検査を揃える。
- 別の患者の画像を書き換えない。決められないときは書き換えずに残す。

**Non-Goals:**

- 照合の後に届いた、StudyInstanceUID の違う新しい検査（Case 6 のうち、新しい手続き）の書き換え。仮の患者 ID は使い回されうるので、StudyInstanceUID で結べない検査は書き換えない。
- 画面に、取消・中止の印を出すこと。
- HL7 v2.5.1、A02・A03・A06・A07。

## Decisions

### 15. 照合の後に届く画像

#### 15.1 覚える中身と置き場

- A40 と ORM を受理（AA）したときだけ、`ack` の行の `detail.remember` に覚えを入れる。AE・AR のメッセージは覚えない。
  - A40：旧い患者 ID（`from`）、統合した先の患者 ID（`to`）、その A40 で書き換えた検査の StudyInstanceUID（`studies`）、書き換える前の氏名・生年月日・性別（`fromNames`・`fromBirthDates`・`fromSexes`）、統合した先の患者の値（`attributes`）、受理の時刻（`at`。BFF の時計）。
  - ORM：患者 ID、StudyInstanceUID、受付番号、ORC-1、受理の時刻。
- 置き場は監査の記録にする。BFF のデータベースに表を足さない（原則 10）。`ack` の行は送り直しの判定（前の設計の 10）にも使っているので、覚えも同じつなぎの中で改ざんを見つけられる。
- 監査の記録の HL7 の行は、使う前に確かめる（`src/lib/hl7/apply.ts` の `history`）。まずつなぎの全部を `verifyAuditChain` で確かめる（行の `action` を書き換えて、結果不明の `request` や続きの A40 を HL7 の行から隠されても見つける）。使うのは、確かめた行のうち HL7 の行そのもの（`verifyAuditChain` の `onRow`）で、確かめた後に読み直さない（読み直す前に書き換えられた行を使わない）。覚え（`remember`）を持つ行は鍵つきだけを受け、最初の鍵つきの行より後の鍵の無い行はつなぎの決まりで受けない（鍵の無い SHA-256 の行は、鍵を持たない者でも作れる。偽の照らし合わせの行で結果不明の書き換えを解かせない。`verifyAuditChain` と同じ決まり）。合わない行が 1 つでもあれば、見回りは何も書き換えず（`blocked`）、メッセージは AE を返す。データベースを書き換えられる者が、別の患者を指す覚えを書き足す・先の時刻の覚えを書き足して見回りを時計の巻き戻りとして待たせ続ける、のどちらもできない（鍵の不一致として止まり、人が `/api/audit/verify` で確かめる）。先頭の控え（`AUDIT_ANCHOR_FILE`）を設定していれば、`/api/audit/verify` と同じく照らし（末尾を消して結果不明の書き換えや続きの A40 を隠されても見つける）、控えを読めなければ止める。最後の控えより後の行（控えは 10 分ごと）の末尾の削除は、控えでは見つからない。
- 別の案は、BFF のデータベースに対応の表を足す形。表の中身が監査の記録と食い違ったときにどちらを信じるかを決める必要があり、原則 10 にも当たるので採らない。

#### 15.2 期限：受理から 24 時間

- 覚えは受理から 24 時間だけ使う。緊急の撮影の照合の後の追加撮影は、同じ受診の中で起きる。24 時間あれば、照合の翌日の朝までの追加撮影を拾える。
- 長くすると、モダリティが仮の患者 ID を使い回したときに、別の患者の画像を拾う恐れが増える（StudyInstanceUID でも絞るので、増えるのは UID の重なりが起きたときだけ）。
- BFF の時計が少し巻き戻ったとき（5 分まで）は使う。どれか 1 つでも、覚えの時刻が時計より 5 分より先にあれば、どの覚えを使ってよいか決められないので、時計が追いつくまで見回りは何も書き換えない。
- 期限は、統合の最初の段の最初の A40 の受理から数える。統合の段（送り直しのまとめ）と前後（続きの段、ORM の採否）は、期限で切る前の全部の覚えで、受理した順（監査の記録の並び）で決める。時刻で前後を決めると、同じミリ秒の受理を取り違える。期限で古い A40 だけを落としてから段を決めると、送り直しが新しい段に見え、統合の先と ORM の採否が変わる。

#### 15.3 書き換える検査の条件

見回りは、覚えのある旧い患者 ID ごとに、次をすべて満たす検査だけを書き換える。1 つでも外れれば書き換えず、ログに 1 行残す（見回りのたびに同じものが出るので、監査の記録には残さない）。

1. 統合の先が 1 つに決まる。旧い患者 ID から `to` をたどり（仮→正→別の正）、最後の患者 ID を先にする。同じ旧い患者 ID から同じ先への A40（別の MSH-10 の送り直し）は 1 つの段にまとめ、覚えの検査・氏名などを合わせ、段の時刻は最初の A40 の時刻にする。続きの段は、前の段の時刻より後に受理したものだけをたどる。同じ患者 ID から 2 つ以上の先がある、輪になっているときは決められない。
2. StudyInstanceUID が覚えにある。覚えは、最初の段の A40 で書き換えた検査と、最初の段の先の患者の ORM の StudyInstanceUID。ORM は、その段の時刻の後で、次の段（その患者がさらに別の患者に統合された）の時刻より前に受理したものだけを使う。統合された後の患者 ID の ORM と、後の段の先の患者の検査・ORM は、その患者のほかの検査でありうるので相手にしない。
   - A40 で書き換えた検査の StudyInstanceUID は、統合した先にその UID の検査が残っているとき（6 の検査が 1 件以上あり、全部が統合した先の患者のもの）だけ使う。人が誤った統合を Orthanc で元の患者へ書き戻す（UID はそのまま）と、統合した先にその UID の検査が無くなる。そのとき書き換えると、書き戻しを次の見回りが統合し直す。ORM だけから来た StudyInstanceUID は、A40 の時点で画像が無かった検査でありうるので、統合した先に検査が無くても使う。
3. 届き終えている（Orthanc の `/studies/{id}` の `IsStable` が true）。届いている途中の検査を書き換えると、書き換えの最中に画像が届いて部分反映で止まりやすいため。
4. 読んだ画像の患者 ID が、全部その旧い患者 ID と同じ（Orthanc の患者 ID での検索は検査の要約で引くので、画像ごとにも確かめる）。前に患者 ID を書き換えようとした画像（監査の記録の `request` の `before`。成功だけでなく、結果不明・部分反映・人が解いた書き換えも含め、何も変わらずに失敗した書き換えだけを除く）が、移す前の患者 ID に戻っていない（人が一部の画像だけを書き戻したときも、部分反映の後に書き戻して解いたときも、統合し直さない）。
5. 画像の氏名が、最初の段の A40 の前の氏名のどれかと同じ（覚えが空なら見ない）。生年月日・性別は、画像と覚えの両方が空でなく、覚えのどれとも違えば書き換えない。
6. 同じ StudyInstanceUID の検査がほかにあれば、それは全部、統合した先の患者のもの（仮の患者 2 人と統合した先の 3 件に同じ UID があれば、どれも書き換えない）。
7. 統合した先の検査に、同じ画像（Study・Series・SOP の UID が同じ）が無い。モダリティの送り直しの画像は、書き換えると上書きになって確かめが合わず、後の書き換えを止めてしまうため。
8. 統合した先の患者の検査が Orthanc にあれば、その検査どうしで氏名・生年月日・性別が揃っている。
9. 画像に受付番号が入っていれば、それが下で決める受付番号と同じ。

#### 15.4 書き方

- 患者の値は、統合した先の患者の Orthanc のいまの値（A40 の後の A08 を巻き戻さない）。Orthanc に無ければ、最後の A40 の値。
- 受付番号は、その StudyInstanceUID の最後の ORM の値（CA・DC なら空）。ORM が無ければ、同じ StudyInstanceUID のすでにある画像の値（揃っているとき）、それも無ければ届いた画像の値のまま。
- 書き方は A40 と同じ（前の設計の 4）。UID を保ち、Orthanc の検査の ID は患者 ID と StudyInstanceUID から決まるので、書き換えた画像は統合した先の検査にまとまる。
- 元の検査は、Orthanc に消させない（`KeepSource: false` を渡さない）。この change で、A40 の書き方（前の設計の 4）も同じに改める。`KeepSource: false` では、書き換えの最中に元の検査へ届いた画像を Orthanc が残すかどうかが Orthanc の作りに依り、消えれば後の確かめでは見つからない。代わりに次の順で書く。
  0. 元の検査に付け替えの印を付ける（下の「付け替えの印」）。印も Orthanc への書き込みなので、付ける前に監査の記録に `lock` の行（`writeId`・元の検査の ID・期限の秒）を残し、残せなければ付けない（付け直しと外すことはこの行に含める）。印を付けた後 1 秒待ってから 1 に進む。印を付けられなければ、`request` を残さずに書き換えをやめる（メッセージは AE、見回りは止まる）。
  1. 元の検査の画像ごとのファイルの印（`/studies/{id}/instances` の `FileUuid`）と画像の ID を読み、`request` の `sourceFiles`（`files`・`ids`）に残す。続けて元の検査の画像を読み直し、照合（前の設計の 9・15.3）に使った画像と UID の組と値が同じでなければ（照合の後・印の前に、同じ UID の画像が別の値で置き換わった）、`request` を残さずに書き換えをやめる。`KeepSource` を付けずに（既定の true）書き換えの仕事を作り、仕事の終わりを待つ。
  2. 統合した先の検査（元の検査の外の、同じ StudyInstanceUID の検査）の画像が、`alongside` と書き換えた後の画像の和と過不足なく同じか確かめる。合わなければ元を消さず、下の確かめが部分反映として止める。続けて、書き換えた画像（`before` と UID の組が同じもの）の Orthanc のメタデータ `ModifiedFrom`（Orthanc が写しに残す元の画像の ID）が、1 で残した元の画像の ID と同じかを確かめる。写しの後に同じ UID の画像が REST・STOW-RS で統合した先の患者 ID で届くと、`OverwriteInstances` で写しが置き換わり、`ModifiedFrom` が無くなる（2026-10-25 に Orthanc 1.13.0 で確かめた）。1 つでも違えば元を消さず、`result` に `foreignCopies` を付けて部分反映として止める。`ids` の無い前の版の `request` でも元を消さない。
  3. 元の検査の画像を読み、書き換えた画像のうち、ファイルの印が 1 で残したものと同じ画像だけを、Orthanc の画像の ID で 1 枚ずつ消す（`DELETE /instances/{id}`。`Backend.deleteStudyInstances`）。仕事が写した後に同じ UID の画像が届き直して置き換わった（`OverwriteInstances`）ものは、印が変わるので消さず、下の確かめが部分反映として止める。印を読んだ後に置き換わった画像を見つけるため、1 で印を読む前に Orthanc の変更の記録（`/changes`）の位置を `sourceFiles` に残し、画像を 1 枚消す直前に、その画像の ID の届いた記録（`NewInstance`）がその位置より後にあれば消さない（Orthanc は画像を消すとその変更の記録も消すので、消した後には確かめられない）。消さなかった画像は元の検査に残り、下の確かめが部分反映として止める。変更の記録を読んでから `DELETE` までの間（1 回の要求の往復）に届き直した画像は、Orthanc の削除に条件を付ける道が無いので消えうる。C-STORE はこの間も付け替えの印で断られるので、この隙に入りうるのは REST・STOW-RS で届き直した画像だけになる（`KeepSource: false` のときは、仕事の全部の間が、C-STORE も含めてこの隙だった）。1 枚を消す直前ごとに印が切れずに続いているかを確かめ、切れたかもしれない・延ばせないときは残りを消さずに部分反映として止める（`result` の `lockLost`）。消し終えた後にも確かめ、最後に消す間に切れていれば（その間に届き直した画像を消したかもしれない）、成功にせず `lockLost` の部分反映にする。消した後に、もう一度 2 の `ModifiedFrom` を確かめる。2 から消すまでの間に写しが REST・STOW-RS で置き換わっていれば、元はもう消えているが、`foreignCopies` を付けて部分反映として止める（成功にしない）。
  4. 消す前に元の検査にあった、書き換えていない画像（最中に届いた画像）が 1 枚でも消えていれば、部分反映として止める（`result` の `arrivalsLost`）。最中に届いた画像が元の検査に残っていれば、下の確かめが合わず、これも部分反映として止まる。
  5. 付け替えの印を外す（元を消した後は、画像ごとの確かめの前に外す。外すまでに印が切れた・途中の付け直しが失敗したと分かれば `lockLost` の部分反映にする）。失敗しても外す。外せなければログに残し、期限で切れるのを待つ（その間の C-STORE は断られ、送り手が後で送り直す。受ける側には倒さない）。
  - 仕事を待つ間・消す途中に印が切れた・付け直せなかったときは、その間の C-STORE を写しが黙って上書きしえたので、元を消さずに部分反映として止める（`result` の `lockLost`。照らし合わせも見回りも自動で解かず、人が `/api/hl7/resolve` で解く）。`lockLost`・`foreignCopies`・`arrivalsLost` を見つけた後は、続く画像ごとの確かめに失敗しても結果不明に戻さず、部分反映として残す（結果不明は照らし合わせが自動で解きうるため）。仕事がまだ写しているかもしれないときは、印を外さずに期限で切れるのを待つ。
  - 消す途中で答えが来ないときは結果不明（`result` の `unknown`。印は外す）。仕事の終わりを待ちきれないとき・書き換えを求めた答えが来ない（仕事ができたか分からない）ときも結果不明だが、仕事がまだ写しているかもしれないので印は外さず、期限で切れるのを待ち、そのときの期限を `result` の `lockUntil` に残す。仕事を作ったときの期限も `dispatch` の `lockUntil` に残す（BFF が仕事を待つ間に止まり `result` を残せなかったときに使う）。照らし合わせは、印を付けた書き換え（`dispatch` より前に `lock` の行がある）で、仕事の終わりの時刻（Orthanc の `CompletionTime`。秒までなので 1 秒の幅を見る）が最後の `lockUntil` より後か、どちらかを読めなければ、印の切れた後に写したかもしれないので、元を消さずに部分反映として止める（`lockLost`）。仕事の ID の無い結果不明（答えが来なかった）は、照らし合わせでは解かず、人が解く。次の照らし合わせ（前の設計の 10）は、仕事が Success なら、元の検査が残っていれば印を付けてから 2〜4 を同じ順で行い、印を外してから確かめる（消し終えた画像は飛ばす）。印を付けずに消す画像を見つけたとき（印を付けるかを決めた引き当てでは元の検査が無かったなど）は消さず、`lockLost` の部分反映にする。合わなければ部分反映として残り、人が `/api/hl7/resolve` で解く。
- **付け替えの印**（2026-10-25 に足した）。患者 ID の変わる書き換え（A40・見回り）の間は、元の検査に利用者のメタデータ `TsunagiLock`（値は期限の UNIX 秒）を `PUT /studies/{id}/metadata/TsunagiLock` で付ける。Orthanc の Lua（`deploy/orthanc/tsunagi-lock.lua`）の `ReceivedCStoreInstanceFilter` が、届いた画像の StudyInstanceUID を `/tools/lookup` で引き、期限の切れていない印のある検査があれば `0xA700`（Refused: Out of Resources。PS3.4 B.2.3）を返す。UID を保つ書き換えなので、元の患者 ID 宛ての画像も、統合した先の患者 ID 宛ての画像も、同じ StudyInstanceUID で止まる。
  - 期限は 120 秒。印を付けている間は、期限の 4 分の 1（30 秒）ごとに、残りが半分を切っていれば付け直す（仕事を待つ間・元の検査を読む間・写しを確かめる間・変更の記録を読む間も切らさない）。元の画像を 1 枚消す直前ごとに、期限を過ぎていないかを確かめ、過ぎていれば（その間に C-STORE が入りえた）付け直して続けずに、残りを消さずに部分反映で止める（`lockLost`）。付け直しに一度でも失敗すれば、それ以降は消さない。付けるたびに `GET /studies/{id}/metadata/TsunagiLock` で読み直し（書いたのと同じ資格情報）、付けた値と違う・読めなければ失敗とする（PUT の答えだけで印が立ったと信じない）。書き換えの仕事を作る直前にも、印が切れずに続いていることを確かめ、切れていれば（元の検査を読む間に付け直せなかったなど）書き換えを始めない。
  - Lua は Orthanc の時計で期限と比べるので、BFF は付けるたびに、先に Orthanc の時計（`GET /tools/now`。UTC の秒まで）を読み、この機の時計とのずれが 5 秒（`LOCK_CLOCK_TOLERANCE_MS`。読みの往復と秒の切り捨ての幅を含めて）を超えるか、読めなければ、印を付けない（書き換えない）。BFF は、印の期限の 5 秒前から、切れたかもしれないとみなす。切れたかは単調な時計（`performance.now()`）で見るので、付けた後にこの機の時計が巻き戻っても切れを見逃さない（付け直すときは、また Orthanc の時計とのずれを確かめる）。照らし合わせが比べる仕事の終わりの時刻と `lockUntil` は、どちらも Orthanc の時計の上の時刻（`lockUntil` は Orthanc に書いた期限以下）なので、ずれに依らない。
  - 付け直すときも、前の期限を過ぎていれば（BFF が止まっていた・付け直しの答えが遅れた）付け直して隠さず、失敗として残す。BFF が途中で止まっても、印は期限で切れる。元の画像を全部消すと、Orthanc は検査ごとメタデータも消す。
  - 印を付けた後 1 秒待つのは、印の前に Lua を通り、まだ保存の終わっていない画像を、変更の記録の位置（1）より前に入れきるため。1 秒より長く保存にかかる画像は、位置の後に入りうる（その画像は書き換えに含まれず元の検査に残り、確かめが部分反映として止める）。
  - `ReceivedInstanceFilter` は使わない。C-STORE で断ると送り手に Success が返り（黙って失われる）、REST で断ると書き換えの仕事の写しの保存（Orthanc の中では REST の扱い）まで止まる（2026-10-25 に Orthanc 1.13.0 で確かめた）。
  - Lua が印を確かめられないとき（引き当ての失敗・検査のメタデータ（`/studies/{id}/metadata?expand`）の読み取りの失敗・答えが読めない JSON か形が違う（引き当てが配列でない・要素が null・知らない Type・検査の ID が無い、メタデータが名前から値への物でない・値に null がある）・印の値が正の整数の文字列でない）は、C-STORE を断る（`0xA700`。fail-closed）。付け替えの最中に確かめられずに受けると、別の中身が写しに黙って上書きされうるため。断った理由は Orthanc のログに `tsunagi-lock: refused a C-STORE (<理由>)` の形で残る（`lookup failed`・`lookup unreadable`・`metadata unreadable`・`lock value unreadable`・`locked`）。
  - その代わり、Orthanc の REST の不具合（データベースの誤り・過負荷など）ひとつで、全部の C-STORE が断られうる（2026-10-25 までは受ける側に倒していた）。Lua を読み込んでいない Orthanc（`LuaScripts` に無い）では何も断らないので、印の仕組みを入れていない施設には効かない。入れた施設では、Orthanc のログの `tsunagi-lock: refused` の数を見張り、`locked` 以外の理由が続けば Orthanc の不具合を疑う（装置には失敗が返り、送り直しは装置しだい）。急いで受けを戻すときは、`LuaScripts` からこのファイルを外して Orthanc を起き直す（BFF は印を付け続けるが、何も断らなくなり、REST・STOW-RS と同じく `ModifiedFrom` の確かめだけが残る）。
  - Orthanc の設定に `UserMetadata`（`"TsunagiLock": 1024`）と `LuaScripts` が要る。無ければ `PUT` が 404 になり、BFF は書き換えない（印の無いまま書き換える道は持たない）。開発の一式（`docker/dev`）と結合の試験の Orthanc に入れる。配る compose（`deploy/compose.yaml`）と施設の Orthanc に入れる手順は、`tasks.md` の「施設の Orthanc に入れるときの手順の案」に書く。
  - 別の案は 2 つあった。`OverwriteInstances: Never` で上書きを止める形は、患者 ID を変えない書き換え（A08・ORM）が Orthanc に断られ、3 の変更の記録を読んでから `DELETE` までの隙も塞がらないので採らない。Python のプラグインで同じことをする形は、`/tools/lookup` の往復が要らないが、プラグインの版と組み込みを確かめていないので、Lua で重ければ移る先として残す。
- 監査の記録は前の設計の 13 と同じ行（`request`・`dispatch`・`result`）で、`detail.type` を `sweep`、`messageId` を見回りごとの ID にする。`request` に、同じ StudyInstanceUID ですでにある画像（`alongside`）を足す。
- 確かめ（前の設計の 4）は、同じ StudyInstanceUID の検査が 2 件以上あれば全部の画像を合わせて比べ、`alongside` と書き換えた画像の和が、Orthanc の画像と同じかを見る。書き換えの最中に同じ検査に画像が届くと合わないので、部分反映として止まる（取り違えて書くより止める）。
- 結果の分からない書き換えがあれば、見回りは何も書き換えない。見回りの書き換えが結果不明・部分反映になれば、HL7 のメッセージも止まる（前の設計の 10 と同じ照らし合わせを使う）。

#### 15.5 呼び方

- BFF に `POST /api/hl7/sweep` を足す。認証は `/api/hl7/messages` と同じ token だけ（前の設計の 3）。本文は読まない。メッセージと同じ列（16 通まで）で 1 つずつ処理する。`AUTH_MODE=dev` で `DEV_ALLOW_WRITE=true` でなければ書き換えない。
- 受け口が、起きてから 5 秒後と、その後 60 秒ごと（`HL7_SWEEP_INTERVAL_SECONDS`）に呼ぶ。前の呼び出しが終わるまで次を呼ばない。呼べなくてもログに残すだけで止まらない。
- 受け口は何も覚えない。BFF は Orthanc にある画像を見るので、受け口が止まっていた間に届いた画像も、起き直した後の最初の呼び出しで拾う。
- 別の案は、BFF が自分で時刻を見て回す形。Next.js の BFF にタイマーを持たせると、複数のプロセスで重なり、止めどころも増えるので採らない。Orthanc の Lua の仕掛け（届いたときに呼ぶ）は、Orthanc の設定の変更と、Orthanc から BFF への資格情報の受け渡しが要るので採らない。

### 16. ORM の CA・DC・XO

- ORC-1 は `NW`・`CA`・`DC`・`XO` を受け、ほかは AR。
- `CA`・`DC` は、検査と画像を消さずに、受付番号を空にする（IHE RAD TF-2 4.13 は、Image Manager が手続きの情報を StudyInstanceUID を鍵に更新するか、使わない印にするとしている）。
  - 受付番号を外す形を選んだ。tsunagi は検査の状態の印を持たない（原則 10）ので、「使わない検査の印」を置く場所が無い。受付番号を外せば、取り消した予約と画像の結び付きが Orthanc の値から消え、検査一覧の受付番号の列でも分かる。
  - 検査の患者 ID が PID-3 と違えば AE、受付番号が OBR-18 と違えば AE（取り違えの恐れがあるので、人が確かめる）。すでに空なら書き換えない（送り直しで AA）。
  - 書き方は ORM の NW と同じ（患者 ID を変えないので `KeepSource: false` は付けない。`OverwriteInstances: true` が要る）。
- `XO` は NW と同じ規則で受付番号を入れる（ris-emulator は手で送るときだけ使う）。

## Risks / Trade-offs

- **取り違えの恐れ。** 見回りは HL7 のメッセージと別の時に Orthanc を書き換える。15.3 の条件のどれかが緩むと、別の患者の検査に画像をまとめる。試験は、別の患者の画像・覚えに無い検査・期限の外・2 段の統合・先の決まらない統合・氏名の違い・同じ UID の別の患者（仮の患者 2 人と統合した先の 3 件を含む）・画像の患者 ID の違い・人が書き戻した統合・A40 より前の ORM・届き終えていない検査・書き換えの最中に届いた画像・受け口が止まっていた間に届いた画像・監査の記録の HL7 の行の改ざんを確かめる。
- **書き換えの最中に届いた画像。** C-STORE は 15.4 の付け替えの印で断られ、装置には失敗が返る（送り直しは印が外れた後に受ける）。REST・STOW-RS で届いた画像は 15.4 のとおり元の検査に残り、部分反映として止まる。人が `/api/hl7/resolve` で解くまで HL7 の書き換えが止まる。画像は失わない（元を Orthanc に消させず、書き換えた画像だけを名指しで消すため）。結合の試験（`tests/integration/orthanc.spec.ts` の 19）で、本物の Orthanc に書き換えの最中に C-STORE と REST で画像を送って確かめる。
- **装置に失敗が返る。** 付け替えの印の間（ふつうは仕事の数秒、長くて期限の 120 秒）に同じ検査へ C-STORE で送った装置には `0xA700` が返る。送り直すかは装置しだいで、DTG は設定の回数（既定 0 回）だけすぐに送り直し、それでも断られれば送信の失敗として残し、人が送り直す（2026-10-25 に DTG の main の `app/modality/service.py` を読んだ）。印の間は短いので、すぐの送り直しも断られうる。
- **同じ UID で中身の違う画像が、書き換えと同じ時に届いたとき（残る隙）。** C-STORE は付け替えの印で断るので、残るのは REST・STOW-RS で届く画像と、印の前に Lua を通り 1 秒より長く保存にかかった画像だけになる。(1) 元の画像の変更の記録を読んでから `DELETE` までの 1 往復の間に、同じ UID の画像が REST で元の検査へ届き直す（届き直した中身が消える）。(2) 統合した先に同じ画像が無いと確かめてから書き換えの仕事が写すまでの間に、同じ UID の画像が REST で統合した先の患者 ID で届く（`OverwriteInstances` で写した画像に置き換わり、届いた中身が消える。写しの後・`ModifiedFrom` の確かめの前に届けば見つけて元を消さず、確かめの後・消すまでの間に届けば元は消えるが、消した後の確かめで見つけて部分反映として止める）。どちらも、同じ SOP Instance UID で中身の違う画像（DICOM では同じ UID は同じ画像）が、REST で、秒より短い間に届いたときだけ起きる。tsunagi-dicom の中継は書き込みを通さないので、REST・STOW-RS で入れられるのは Orthanc の REST の口に直に入れる人と機械だけ（`docs/security-and-maintenance.md` の 4.1）。
- **印に頼る前提。** Lua が印を確かめられないときは C-STORE を断る（15.4。Orthanc の不具合ひとつで全部の C-STORE が断られうるので、Orthanc のログの `tsunagi-lock: refused` を見張る）。BFF と Orthanc の時計が 5 秒より大きくずれていれば、BFF は印を付けずに書き換えない（Lua は Orthanc の時計で比べる。15.4）。施設では両方の機の時計を NTP で合わせる。Lua を読み込んでいない Orthanc でも印は付くので、BFF からは Lua の有無が見えない。施設の Orthanc に入れるときに、C-STORE が断られることを確かめる。
- **取り込みの速さ。** Lua は C-STORE の 1 枚ごとに Orthanc の REST を 2 回読み、Lua の呼び出しは Orthanc の中で 1 つずつ流れる。試験の Orthanc（1.13.0・SQLite）で 500 枚を送った時間：1 本の association で印の確かめ無し 24.8〜25.0 秒・有り 24.9〜25.2 秒（3 回ずつ）。4 本で同時に送ったとき、無し 6.8〜8.8 秒（中央 6.9 秒）・有り 6.8〜9.2 秒（中央 8.5 秒）、ほかに有りで 1 回だけ 37.6 秒（9 回ずつ。原因は調べていない）。量の多い施設では、入れる前に施設の Orthanc で測る。重ければ Python のプラグインに移す。
- **監査の記録を書き換えられたとき。** 15.1 のとおり、合わない行が 1 つでもあれば HL7 の書き換えを全部止める。止まるのは改ざんに気づくためで、人が `/api/audit/verify` で確かめて直すまで続く。
- **24 時間を過ぎた後の画像**は、仮の患者 ID のまま残る（同じ StudyInstanceUID の検査が 2 件並び、引き当てが 409 になる）。人が値の修正（段 6）か、新しい A40 で直す。
- **見回りのたびに監査の記録を全部読む。** 開発の一式の量なら問題にならない。

## Migration Plan

- 開発の一式は、受け口と tsunagi-dicom のイメージを作り直し、Orthanc を作り直す（`docker/dev/hl7.override.yaml` が Lua と `UserMetadata` を足す）。
- 施設の Orthanc には、tsunagi-dicom の版を上げる前に、Lua と `UserMetadata` を入れる（`tasks.md` の手順の案）。先に tsunagi-dicom を上げると、印を付けられず A40 が AE になり、見回りが止まる（取り違えは起きない）。
- 戻すときは、受け口の前の版に戻す（見回りを呼ばなくなる）。覚えは `ack` の行に残るが、使われない。Orthanc の Lua は、tsunagi-dicom を前の版に戻しても残してよい（印が付かなければ何も断らない）。
