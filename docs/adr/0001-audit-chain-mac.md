# ADR 0001：監査の記録のつなぎを鍵つきにし、先頭の控えをデータベースの外に書き出す

- 状態：採用（2026-10-21）
- 決めた人：承認者（2026-10-21 19:25「進めて」）
- きっかけ：Claude Security の調査（main 3da55fb）の指摘 F1（LOW、CWE-345）

## 背景

監査の記録（`AuditLog`。[`spec.md`](../spec.md) の 3.6）の各行は、前の行の hash を `prevHash` に持ち、行の中身と `prevHash` の SHA-256 を `hash` にしていた。鍵の無い SHA-256 なので、データベースのファイル（`/data/tsunagi.db`）に書ける者は、次のことができた。

1. 追記だけの trigger を外す。
2. 行を書き換えるか、末尾を消す。
3. 書き換えた行から末尾までの `hash` を、同じ計算で作り直す。

`/api/audit/verify` は、こうして作り直したつなぎを本物と区別できず、`{"ok": true}` を返した。末尾の削除は、作り直さなくても見つからなかった。それでも、マイグレーション `20261018000000_audit_log` の注釈と [`security-and-maintenance.md`](../security-and-maintenance.md) の 5 は、「ファイルの直接の書き換えを見つけられる」と書いていた。

## 決めたこと

### 1. hash を HMAC-SHA256 にする

- 新しい行の `hash` は、行の中身と `prevHash` の HMAC-SHA256 にする（`src/lib/audit.ts` の `computeAuditMac`）。並びの形は固定で、先頭に形の印 `v1`、末尾に確かめていない接続元と鍵の印を入れる。
- 鍵は `SESSION_SECRET` から HKDF-SHA256 で導く（`src/lib/audit-key.ts`）。用途の名前（info）は `tsunagi-dicom/audit-chain/v1` で、セッション・画面へ渡す token・TOTP の秘密の暗号の鍵とは別の鍵になる。
- 行に鍵の印（`keyId`。鍵から導いた 16 桁の 16 進。鍵そのものではない）を持たせる。確かめるときは、行の印の鍵で計算し直す。
- データベースのファイルには鍵を置かない。鍵（`SESSION_SECRET`）を持たない者は、行を書き換えても `hash` を作り直せない。

#### 鍵の出どころの比べ方

| 案 | よいところ | わるいところ |
|---|---|---|
| A：`SESSION_SECRET` から用途の違う info で導く（採用） | 守る秘密のファイルを増やさない（TOTP の秘密の暗号と同じ考え方）。今の配る形（`deploy/init-secrets.sh`・compose）と、今動いている一式をそのまま使える | `SESSION_SECRET` を替えると、監査の鍵も替わる。前の鍵で書いた行を確かめるには、前の値を残しておく必要がある |
| B：監査だけの秘密を足す | セッションの秘密を替えても、監査の鍵は替わらない | 秘密のファイルが 1 つ増え、配る形の作り方（`init-secrets.sh`・compose の secret）と、今動いている一式の作り直しが要る。秘密を置く場所は A と同じ（同じコンテナに渡す）なので、守りの強さは変わらない |

A を選んだ。`SESSION_SECRET` を読める者はデータベースも読めることが多く、B にしても守りの強さはほとんど変わらない。秘密を増やさない利点のほうが大きい。

#### 鍵を替えたとき

- `SESSION_SECRET` を替えた後の最初の追記の前に、鍵が替わったことの行（`audit_key`。`detail` に前の鍵の印 `from` と新しい鍵の印 `to`）を1行書く。
- 前の鍵で書いた行は、前の `SESSION_SECRET` を `SESSION_SECRET_PREVIOUS_FILE`（1 行に 1 つ）で渡せば確かめられる。この値は監査の記録の確かめだけに使い、セッションや token には使わない。
- 渡さないと、`/api/audit/verify` は「この行の鍵が無いので確かめられない」と、その行の番号を返す（409）。
- 漏れた疑いで `SESSION_SECRET` を替えたときは、前の値で作り直された行を、前の値では見分けられない。前の値で確かめるのは、漏れていない値に替えたとき（定期の取り替えなど）にとどめる。漏れた疑いのときは、下の先頭の控えと照らす。

### 2. 既存の行からの移り方

- マイグレーション `20261021120000_audit_log_keyed_chain` は、`keyId` の列（空を許す）を足すだけにする。前の行は書き換えない（追記だけの決まりのため）。
- `keyId` が空の行は、これまでどおり鍵の無い SHA-256 で確かめる（`/api/audit/verify` の `legacy` に数を出す）。
- この版で最初に追記するとき、先に `audit_key` の行（`from` は `sha256`）を書く。その `prevHash` は、前の版の最後の行の `hash` になる。
- 鍵つきの行の後に鍵の無い行があれば、作り直しとして見つける。鍵の無い行を前から全部作り直されたとき（鍵つきの行を消して、鍵の無い行にした）は、つなぎだけでは見つからない。下の先頭の控えと照らして見つける。
- 既存のデータベースで起動しても、マイグレーションを当てるだけで動く。前の版の行も、そのまま確かめが通る（単体の試験で確かめた）。

### 3. 先頭の控えをデータベースの外に書き出す

鍵つきにしても、末尾の削除（切り詰め）と、鍵を持つ者による作り直しは、つなぎだけでは見つからない。そこで、最後の行の `seq` と `hash`（と `keyId`・書いた時刻）を、データベースの外へ定期に書き出す（`src/lib/audit-anchor.ts`）。

- 書き出す時：起動したとき1回と、その後は 10 分ごと。最後の行が変わっていなければ書かない。`AUTH_MODE=local` のときに書き出す。
- 書き出し先は次の2つ。
  - **コンテナのログ（標準出力）**：`tsunagi-dicom: audit-anchor {"seq":…,"hash":"…","keyId":"…","at":"…"}` の1行。
  - **`AUDIT_ANCHOR_FILE`**（設定したとき）：同じ JSON を1行ずつ追記するファイル（JSON Lines）。配る compose では、データベース（`tsunagi-data`）とは別のボリューム（`tsunagi-audit-anchors`）の `/audit-anchors/audit-anchors.jsonl` にする。
- `/api/audit/verify` は、`AUDIT_ANCHOR_FILE` の控えと照らし合わせる。
  - 控えの `seq` の行の `hash` が控えと違えば、作り直しとして見つける。
  - 控えより行が少なければ、末尾の削除として見つける。
  - 控えのファイルに読めない行や、同じ `seq` で食い違う控えがあれば、控えの書き換えとして返す。
  - `AUDIT_ANCHOR_FILE` を設定しているのに、行があって控えが1つも無ければ（控えのファイルが消えた・別のボリュームを見ている）、照らせないことを食い違いとして返す。照らさずに通すと、切り詰めや作り直しを見落とすため。起動の時の1回目の控えは、要求を受ける前に書き終える。

#### 製品が持つ範囲と、運用に任せる範囲

| 製品（tsunagi-dicom）が持つ | 運用（施設）に任せる |
|---|---|
| 鍵つきのつなぎ（HMAC-SHA256）と、鍵の印・鍵の取り替えの記録 | `SESSION_SECRET` と前の値（`SESSION_SECRET_PREVIOUS_FILE`）の保管。データベースとは別の守り（バックアップの写しに秘密を一緒に入れない） |
| 先頭の控えを、ログと `AUDIT_ANCHOR_FILE` に書き出すこと | コンテナのログを、外の置き場（syslog・追記だけのストレージ・別のホスト）へ送って残すこと。控えのボリュームを、データベースのボリュームと別に守ること |
| `/api/audit/verify` で、`AUDIT_ANCHOR_FILE` の控えと照らすこと | 外に残したログの控えと、`/api/audit/verify` の答え（または `AUDIT_ANCHOR_FILE`）を、時々照らすこと |

`AUDIT_ANCHOR_FILE` は同じホストのボリュームなので、ホストの管理者はデータベースと一緒に書き換えられる。それを見つけられるのは、外の置き場に送ったログの控えだけになる。

## 保証の言い方

- 鍵（`SESSION_SECRET`）を持たない者が鍵つきの行を書き換える・差し込む・途中を消すと、`/api/audit/verify` で見つかる。
- 末尾の削除と、鍵を持つ者による作り直しは、先頭の控えより前の行について見つかる。控えより後に書かれた行は、次の控えまで守られない（最大 10 分と、書き出しが止まっていた間）。
- どれも「見つける」ためのもので、防ぐものではない。データベースの trigger は、アプリの誤りによる更新・削除を断るためのもので、ファイルに書ける者を止めない。

## 考えたが選ばなかったこと

- **電子署名（公開鍵）**：確かめる側が秘密を持たずに済む。ただし、署名の鍵の保管と取り替えの手順が増える。今の脅威（データベースのファイルに書ける者）には、HMAC と外の控えで足りる。
- **外の WORM ストレージや syslog への直接の送り出しを製品が持つ**：置き場は施設ごとに違う。製品はログ（標準出力）に出すところまでにして、送り先は施設の仕組み（Docker のログのドライバー・syslog など）に任せる。
- **前の版の行を鍵つきに書き直す**：追記だけの決まりに反し、前の版のつなぎの確かめもできなくなる。

## 試験

- `tests/unit/audit.test.ts`：鍵の無い SHA-256 や別の鍵での作り直しはその行で、鍵を持つ者の1行の作り直しは次の行で見つかる。鍵の無い形への作り直し、鍵の印の書き換えも見つかる。先頭の控えと照らすと、末尾の削除と、鍵を持つ者の作り直しが見つかる。前の版の行のあるデータベースにマイグレーションを当てても確かめが通り、次の行から鍵つきになる。`SESSION_SECRET` を替えたときの `audit_key` の行と、前の値を渡したときの確かめも試す。
- `tests/unit/config.test.ts`：`SESSION_SECRET_PREVIOUS_FILE`・`AUDIT_ANCHOR_FILE` の読み方。
- 結合の試験の 9：`AUDIT_ANCHOR_FILE` に控えが書き出され、`/api/audit/verify` が照らし合わせる。
- 開発用の compose の流れの試験：配る compose の形で、ログと別のボリュームのファイルに控えが出て、`/api/audit/verify` が照らし合わせる。
