# tsunagi-dicom（つなぎだいこむ）仕様書

> 状態：段 1b（`AUTH_MODE=local`：利用者・パスワードの規則・TOTP・ログインの一時停止・画面のロック・利用者の棚卸し・役割ごとにできる操作・中継の役割の確かめ）まで実装した（2026-10-18）。段 1a は土台・BFF の画面の API と WADO-RS の読み取りだけの中継・監査の記録・`AUTH_MODE=dev`（モックだけ）・CI とイメージ。段の進め方は「6. 段階」。

DICOMweb に対応した画像サーバー（Orthanc など）を**改造せずにバックエンドとして使い**、日本の医療機関の画像の見方に合わせた一覧・時系列・ビューアの選び分けを提供する、独立した Web の画面と BFF（Backend For Frontend）。

> **Not for Diagnostic Use / 非医療機器。** 研究・教育・検証のためのソフトウェアで、医療機器としての承認・認証を受けていない。

## 1. 原則

1. **バックエンドを改造しない。** 画像サーバーとビューアのソースには手を入れない。つなぎ先はすべて設定（環境変数）で決める。画像サーバーとビューアが別のサーバーにあってもよい。
2. **標準を先に使う。** 検索・取得・表示の基本は DICOMweb（QIDO-RS・WADO-RS）で書く。Orthanc にしか無い機能（ワークリスト・分割・結合・統計・DICOM の作成）は「Orthanc のときだけ有効」な部品に分ける。
3. **どこでも動く。** 特定の施設・ネットワーク・名前に依らない。施設ごとの値は設定で渡す。リポジトリには例の名前（`pacs.example.org`）だけを書く。
4. **安全を既定にする。** 既定の設定は認証が有効。証明書の確かめは切らない（自前の CA は `*_CA_FILE` で渡す）。秘密の値に既定値を置かない。
5. **ガイドラインに沿った機能を持つが、「準拠」とは言わない。** 厚労省のガイドライン（第7.0版）の項目のうち、アプリケーションで担える部分を実装し、その対応表を文書と画面で示す。ガイドラインへの適合は、運用を含めて各施設が判断するもので、このソフトウェアだけで「準拠」とはならない。
6. **商用の製品の名前・画像・ロゴを使わない。** アイコンは Lucide、見た目は Tailwind CSS で作る。文書でも商用の製品の名前を出さない（「日本の医療機関で広く使われている画像の閲覧の慣習」のように書く）。
7. **医療の現場の言葉を言い換えない。** 未検像・検像済・未読・既読・緊急・簡易レポートなど、医療関係者のよく知っている言葉をそのまま使う（別の言葉にすると、使うときに混乱する）。診療に使うかどうかは使い手の判断で、機能ごとに「診断用ではない」の断り書きは足さない（共通の「非医療機器」の表示は出す）。
8. **BFF は、役割ごとに許可した項目だけをブラウザに返す。** 画面の API（一覧・詳細・検索・時系列・簡易レポートなど、BFF が組み立てて返す JSON）では、画像サーバーの応答をそのままブラウザに渡さない。役割ごとに「見せてよい項目の一覧（許可の一覧）」を持ち、載っていない項目は返さない（足し忘れたときは「出ない」側に倒れる）。
   - **既定の役割**（管理者・医師・技師・閲覧）の許可の一覧は、**その役割が使える画面に要る項目をすべて含む**。できる操作（3.6 の役割）は変えない。この決まりを入れても、既定の役割の見え方・検索・操作は変わらない。
   - 「**すべての DICOM の値を見る**」は、許可の一覧とは別の明示の権限にする。既定では管理者・技師に与える。この権限があるときだけ、DICOM の値の全部を返す画面（すべての値の一覧）を使える。
   - **画像と文書の本体**（画素・フレーム・Encapsulated PDF など）と、**ビューアへ渡す取得の道**（BFF の中継の WADO-RS の読み取り）は、この選別の対象にしない。ビューアは BFF の中継を通して画像を取る（3.2）。中継は取得だけを通し、**検索（QIDO-RS）は返さない**——検索の結果は画面の API（この許可の一覧の対象）から返す。
   - 開発用の切り替え（4）で選んだ役割にも、同じ規則を当てる。
   - この決まりは、のちの「ブラインド読影の役割」（6 の段 2b）を作り直し無しで足せるようにするためのもの。ブラインド読影の役割で、ビューアや取得の道からの値の漏れをどう止めるかは、その段で設計して確かめる。

## 2. 技術の構成

| 項目 | 選ぶもの | 理由・条件 |
|---|---|---|
| 画面と BFF | Next.js（App Router・TypeScript・`output: 'standalone'`） | 画面とサーバーの処理を1つのコンテナにまとめられる |
| 見た目 | Tailwind CSS・shadcn/ui（Radix UI）・Lucide | 商用の素材を使わない |
| データの取得 | TanStack Query | 段 2（一覧を作り込む段）から。段 1a の頁はサーバーの側で描く |
| BFF のデータベース | SQLite（WAL）＋ Prisma。PostgreSQL に切り替えられる | 小さく始め、件数が増えたら替える |
| 試験 | Vitest（単体）・Playwright（画面。モックのバックエンドに対して流す） | CI でもクラウドの開発環境でも、社内の画像サーバー無しで流せる |
| 配布 | コンテナのイメージ（GHCR）。版の番号のタグと digest で配る | 前の版にすぐ戻せる |
| ライセンス | MIT | 画像サーバーとは REST・DICOMweb でやり取りするだけで、そのコードを取り込まない |

画面の見た目の基準：
- **地の色は画面の役目で分ける。** 一覧・時系列・簡易レポート・管理など、文字を読む画面は**明るい地を既定**にし、暗い地にも切り替えられる（利用者ごとに覚える）。画像のサムネイルの並びは、まわりだけ暗い地にする。ビューア（OHIF など）は外の部品で、暗い地のまま。日本の医療機関で広く使われている画面でも、画像を見る画面は暗い地、一覧や事務の画面は明るい地が多い。
- 明るい地：地 `#ffffff`〜`#f6f8fa`、文字 `#1f2328`、ラベル `#59636e`、値 `#1f2328`（太字）、境界線 `#d1d9e0`。
- 暗い地：地 `#121417`〜`#1a1d21`、文字 `#e6edf3`、ラベル `#8a949e`、値 `#ffffff`（太字）。
- どちらの地でも、基準の文字は 14px（0.875rem）、行間 1.5、部品の間の余白は今のウェブの画面の感じ（詰めすぎない）。文字と地の対比は WCAG 2.2 の AA（4.5:1）以上にする。
- 色と文字の値は1か所（設計の値・design tokens）で持つ。同じ作者のモダリティのダミーの画面も、同じ値を使う。

画面の言葉：最初は日本語だけ。ほかの言葉への切り替えは後の段で決める。文書は日本語を主にし、README は日本語と英語。

### 2.1 設定（`.env.example`）

設定の正本はリポジトリの [`.env.example`](../.env.example)（値は例の名前だけ。秘密は空）。ここには要点だけを書く。

| 群 | 変数 | 要点 |
|---|---|---|
| バックエンド | `BACKEND_KIND` | `orthanc` か `dicomweb`（DICOMweb だけの汎用。Orthanc 固有の機能は無効） |
| | `BACKEND_DICOMWEB_URL`・`BACKEND_ORTHANC_URL` | 画像サーバーの URL（例 `https://pacs.example.org/dicom-web`）。`BACKEND_ORTHANC_URL` は `BACKEND_KIND=orthanc` のとき |
| | `BACKEND_USERNAME`・`BACKEND_PASSWORD`・`BACKEND_PASSWORD_FILE` | 空なら認証なし。パスワードは秘密で、既定値を置かない。ファイルでも渡せる |
| | `BACKEND_CA_FILE` | 自前の CA（例：施設の CA）。証明書の確かめを切る設定は持たない |
| | `BACKEND_MOCK` | `true` でモックのバックエンド（`tests/fixtures` の合成のデータ）。開発・CI 用 |
| ビューア | `VIEWER_OHIF_URL`・`VIEWER_STONE_URL`・`VIEWER_VOLVIEW_URL` | ブラウザから開く URL。別のサーバーでもよい。空ならそのビューアを出さない |
| | `VIEWER_WEASIS_ENABLED` | `true` で Weasis（`weasis://`）を出す。`false` なら出さない。Weasis は段 4 の後 |
| | `PUBLIC_DICOMWEB_URL` | 研究の道具へ渡す URL（コピー用） |
| 認証 | `AUTH_MODE` | `local`（アプリの利用者）・`oidc`（外部の認証。段 4）・`dev`（開発用。下の 4）。**既定は `local`**（設定しなければ認証が有効。原則 4）。`dev` は段 1a〜1b では `BACKEND_MOCK=true` のときだけ起動する |
| | `MFA_REQUIRED` | `true`：二要素が必須でパスワードは 8 文字以上。`false`：13 文字以上（第7.0版 14.1.1） |
| | `LOGIN_LOCK_THRESHOLD`・`LOGIN_LOCK_MINUTES` | 続けて失敗したら、一定時間ログインできなくする（既定 5 回・15 分） |
| | `SCREEN_LOCK_MINUTES` | 操作が無いときの画面のロック（既定 15 分。0 で無効） |
| | `LOGIN_RATE_LIMIT_PER_MINUTE`・`LOGIN_RATE_LIMIT_GLOBAL_PER_MINUTE` | ログイン（利用者名とパスワード）を遅らせ始める回数。1 分あたり、利用者名ごと（既定 10）と全体（既定 300）。超えた試みは**断らずに**、答えを指数的に遅らせる（最大 10 秒。3.6） |
| | `PASSWORD_HASH_CONCURRENCY`・`PASSWORD_HASH_QUEUE` | パスワードのハッシュ（argon2id）を、ログインの枠で同時に回す数（既定 2。1〜8）と、待たせる数（既定 32。0〜1024）。超えたログインの要求はすぐ 503 と `Retry-After` で断る。ログインした人の確かめ（ロックの解除・再認証など）は、別に取っておいた1本で先に通す（3.6）。同時に回す数は、libuv のスレッドの溜め（`UV_THREADPOOL_SIZE`、既定 4）より小さくする |
| | `INITIAL_ADMIN_USERNAME`・`INITIAL_ADMIN_PASSWORD_FILE` | 最初の管理者（`AUTH_MODE=local` で利用者が1人もいないときだけ使う。3.6）。パスワードは秘密で、ファイルでだけ渡す（値の変数は無い）。利用者が1人もいず、この2つも無ければ起動しない |
| | `OIDC_ISSUER`・`OIDC_CLIENT_ID`・`OIDC_CLIENT_SECRET`・`OIDC_CLIENT_SECRET_FILE` | `AUTH_MODE=oidc` のとき。`OIDC_CLIENT_SECRET` は秘密。ファイルでも渡せる |
| | `DEV_ALLOW_WRITE` | `AUTH_MODE=dev` のときだけ効く。`true` で書き込みも試す（既定は止める）。書き込みの道は段 4 まで無いので、それまでは `true` にすると起動しない |
| データ | `DATABASE_URL` | 既定 `file:/data/tsunagi.db` |
| | `SESSION_SECRET`・`SESSION_SECRET_FILE` | 秘密。必須。32 バイト以上の乱数。どちらも空なら起動しない。ファイルでも渡せる（`compose.yaml` の例は secret のファイル） |
| | `TZ` | 既定 `Asia/Tokyo` |

秘密を値と `*_FILE`（`BACKEND_PASSWORD` と `BACKEND_PASSWORD_FILE`、`SESSION_SECRET` と `SESSION_SECRET_FILE`、`OIDC_CLIENT_SECRET` と `OIDC_CLIENT_SECRET_FILE`）で同時に指定したら誤りとし、起動しない。

## 3. 機能（6つの部品）

### 3.1 検査の一覧
- **すぐ絞れる見出し**：検査日（今日・昨日・1週間・今月・全期間・期間の指定）、モダリティ（すべて・CT・MR・CR/DX・US・ES・MG・DOC・SR。色分け）、状態（未検像・検像済・未読・既読・緊急・ブックマーク）、横断の検索（患者 ID・氏名の漢字・かな・英字・受付番号・検査の記述）。
  - 状態（検像・読影・緊急・ブックマーク）は BFF のデータベースに持つ。画像サーバーの DICOM の値は書き換えない。
- **読みやすい一覧（14px）と日本式の整形**
  - **氏名の解析**：`Alphabetic=Ideographic=Phonetic` の標準の形のほか、崩れた形（ローマ字が無い、漢字が空、空白で区切る、半角カナ、敬称つき、前後の空白、4つ目以降の `=`）でも、エラーにせず読める字だけを出す。漢字の氏名（14px・太字・白）とかなの氏名（12px・灰色）に分けて出す。試験は `docs/patient-name-test-cases.md` の 30 の形（元の 23 の形に、空の入力などを足したもの）から始める。
  - **和暦・年齢・性別**：`1975/05/10（昭和50年・51歳・男）`。年齢は検査日の時点で数える。
  - **代表のサムネイルと、シリーズ数・画像数**。
- **詳細のパネル**（行のクリックで、動きの遅れ無しに開く）
  - 左：検査の情報（2列）、右：患者の情報（2列）、下：シリーズごとのサムネイルの並び。値は `…` で切らない。
  - StudyInstanceUID・SeriesInstanceUID は、行の幅いっぱいに 0.75rem・等幅・`#777` で控えめに出し、コピーのボタンを付ける。

### 3.2 ビューアの選び分けと記憶
- **ビューアの部品（ViewerAdapter）**：設定で URL が与えられたもの（Weasis は `VIEWER_WEASIS_ENABLED=true` のとき）だけを出す。
  - `ohif`：OHIF Viewer v3（CT・MR の多断面・過去との比較）
  - `stone`：Stone Web Viewer（単純 X 線・超音波の速い表示）
  - `volview`：VolView（3D の表示）
  - `weasis`：Weasis（`weasis://`。手元のアプリ。DICOMweb で開く。**段 4 の後**）
  - `dicomweb`：研究の道具（3D Slicer など）に渡す DICOMweb の URL のコピー
- **ビューアが画像を取る道**：基本は **BFF の中継**（`/api/dicom-web/...`）を通す。
  - 中継が通すのは **WADO-RS の読み取り（GET・HEAD）だけ**：検査・シリーズ・画像の取得と、その `metadata`・`rendered`・`thumbnail`・`frames`・大きな値（bulk data）。**検索（QIDO-RS）は返さない**（検索は画面の API を通し、原則 8 の許可の一覧の対象にする）。**書き込み（STOW-RS など）の道は段 4 まで作らない**（POST・PUT・PATCH・DELETE は 405 で断り、断ったことを記録する）。
  - 中継は、利用者のセッションで認可し（ログインしていなければ 401、画面のロック中は 423、役割に画像の取得が無ければ 403。段 1b）、取得のたびに監査の記録に残す（誰が・いつ・どの検査の・何を。画像サーバーの答えが出てから結果つきで残し、記録に失敗したら画像を渡さない）。画像サーバーの資格情報はサーバーの側で付け、ブラウザに渡さない。
  - これは、研究用の画像の集め先の前にこのアプリを置く使い方の要望（ビューアの取得も BFF を通す・読み取りだけ・セッションで認可・監査に残す）とそろえたもの。
  - **ブラウザが画像サーバーを直に開く形は、既定にしない。** BFF の認可と監査の外になり、画像サーバーの資格情報か別の認証をブラウザの側に持たせることになるため。研究の道具に渡す `PUBLIC_DICOMWEB_URL`（コピー用）は、画像サーバーの側で認証と記録を持つ施設のための別の道として残し、画面では「このアプリの監査の外」と示す（段 2）。
  - **未決（段 2 で決める）**：ビューアによっては、検査の中のシリーズ・画像を探す QIDO-RS（`studies/{uid}/series` など）を使う。これを中継に足すか（足すなら許可の一覧の対象にする）、ビューアを WADO-RS の `metadata` だけで開く設定にするかは、ビューアごとに実測してから決める。
- **選び方の3段**
  1. **その場で選ぶ**：行の `[▶ 開く | ▾]` から、ビューアを選んで別のタブで開く。詳細のパネルのシリーズからも開ける。
  2. **検査ごとに覚える**：「この検査は次から VolView」を StudyInstanceUID ごとに保存。行に `[既定: VolView]` を出し、ダブルクリックでそれを開く。
  3. **モダリティごとの既定**：覚えが無い検査は、モダリティの既定（例：CT・MR は OHIF、CR・DX・US は Stone）で開く。既定は管理の画面で変える。

### 3.3 患者ごとの時系列
- **表**：縦がモダリティ（CT・MR・CR/DX・US・ES・DOC・所見）、横が検査日。セルに代表のサムネイル・検査の記述・枚数・既定のビューア・所見の有無を出す。ダブルクリックで既定のビューア、▾ で別のビューア。
- **2つの検査の比較**：2つのセルを選んで「比較（1×2）」。2つの StudyInstanceUID を渡してビューアを開く（OHIF の複数の検査の指定を使う。**動作は実装の前に確かめる**）。

### 3.4 簡易レポートと文書
- **簡易レポート**：検査ごとに「検査目的」「画像所見」「結論・研究メモ」「読影の状態（未読・既読）」と、キー画像（SOPInstanceUID）を保存する。医療の現場で使われている言葉をそのまま使う（言い換えると、使うときに混乱する。原則 7）。
- **文書**（Orthanc のときだけ）：PDF・JPEG・PNG を落とすと、Orthanc の `/tools/create-dicom` で DICOM（Encapsulated PDF・Secondary Capture）にして入れる。時系列の DOC の行から画面の中で見る。文字のコードは UTF-8（ISO_IR 192）。

### 3.5 検像・取り込み・ワークリスト（Orthanc のときだけ）
- **他の施設のデータの取り込み**：取り込む前に元の値を一覧で出し、自施設の患者 ID・氏名（漢字・かな・英字）・受付番号に書き換えて取り込む。文字のコードは UTF-8（ISO_IR 192）にそろえる。
- **日本語の値の修正・シリーズの分割・検査の結合**：氏名を漢字・かな・英字に分けて直す画面。Orthanc の `/studies/{id}/split`・`/merge` を、確かめの画面を挟んで流す。
- **ワークリスト**：Orthanc の Worklists のプラグインで、予約の一覧・作成・削除。**作るときの文字のコードは UTF-8 だけにする**（JIS を指定すると漢字が黙って消えることを 2026-10-18 に確かめた。下の「既知の制約」）。

### 3.6 安全と運用の管理
**この節の項目は、第7.0版 システム運用編の該当の節に対応させる。** 番号は原文のもの（「14 遵守事項⑤」は 14 章の【遵守事項】の⑤、「14.1.1」は節の解説）。対応表は `docs/guideline-mapping.md` と、画面の「安全の機能」の頁に出す。

| 機能 | 中身 | 第7.0版 |
|---|---|---|

#### `AUTH_MODE=local` の決まり（段 1b）

- **最初の管理者**：利用者が1人もいないときだけ、起動の時に `INITIAL_ADMIN_USERNAME` と `INITIAL_ADMIN_PASSWORD_FILE`（秘密のファイル）から作る。利用者が1人でもいれば使わない（設定を残しても、パスワードを書き換えない）。作った管理者は、最初のログインで TOTP を登録し（`MFA_REQUIRED=true` のとき）、パスワードを本人のものに変える。
- **利用者**：利用者名（英小文字・数字・`.` `_` `-` の 3〜64 文字。作った後は変えない。監査の記録の「誰が」に使う）・表示の名前・役割・状態（有効・止めている）・最後のログイン。管理者が作るときに決めたパスワードは、最初のログインで本人が変える。**要らない利用者は消さずに止める**（監査の記録の「誰が」を後から追えるようにするため）。有効な管理者が1人もいなくなる変更（役割の変更・止める）は断る。
- **パスワード**：上の「パスワードの規則」。利用者名を含むものも断る。よくあるパスワードの一覧は `@zxcvbn-ts/language-common`（MIT）の一覧から、ほかの決まり（8 文字以上・英字と数字の混在）を満たす語だけを抜いて同梱する（`src/lib/auth/common-passwords.json`。作り方は `scripts/build-common-passwords.mjs`、ライセンスは同じ場所の `common-passwords.LICENSE.txt`）。ハッシュは argon2id（m=19 MiB・t=2・p=1）。いまの規則に合わなくなったパスワード（`MFA_REQUIRED` を `false` にしたときの 8〜12 文字など）は、次のログインで変える。
  - **ハッシュの強さ**：保存したハッシュの強さの値（記憶 8〜256 MiB・回数 1〜10・並び 1〜8・salt 8〜64 バイト・tag 16〜64 バイト）が範囲の外なら、確かめに回さず、合わないものとして扱う（壊れた・書き換えた行で、記憶と時間を使い切らせない）。いまの強さより弱いハッシュは、ログインに成功したとき（平文があるうち）に作り直す。作り直しはパスワードの変更ではないので、変更の時刻は変えない。同時にパスワードが変えられていたら書かない。
  - **同時に回す数**：argon2 は Node.js の libuv のスレッドの溜め（既定 4 本）で回るので、上限を置く。ログイン（まだ誰か分からない要求）の枠は、同時に `PASSWORD_HASH_CONCURRENCY` 本（既定 2）まで、待ちは `PASSWORD_HASH_QUEUE` 件（既定 32）まで。超えた要求は待たせずに **503 と `Retry-After`（5 秒）** で断る（下の「試みの遅らせ」で待たせる前にも見て、埋まっていればすぐ断る）。断った要求は、試みの枠を使わない（一時停止に数えない）。ログインした人の確かめ（ロックの解除・再認証・パスワードの変更・二要素が任意のときの登録・利用者を作る）は、ログインの枠とは別に取っておいた1本で回し、待ちもログインの待ちより先に通す（ログインの要求が溢れても、ロック中の職員は戻れる）。
- **二要素（TOTP）**：RFC 6238（HMAC-SHA1・6 桁・30 秒）。時計のずれのために前後1つの段まで受ける。使った段を利用者ごとに覚え、同じ段・前の段の使い回しを断る。登録は QR（サーバーの側で描く）と、手で入れる秘密。`MFA_REQUIRED=true` では未登録の利用者はログインの途中で登録する。`false` では任意（自分の設定から登録でき、登録したら次からログインで要る）。登録を確かめて書くのは、まだ登録していないときだけ（もう登録してあれば 409。登録の途中のセッションを2つ開いて、後から登録済みの TOTP を上書きできないように）。登録できたら、その利用者のほかのセッションを閉じる。
  - **秘密の保存**：AES-256-GCM（認証のタグは 16 バイトだけを受ける）で暗号化して持つ。鍵は `SESSION_SECRET` から HKDF-SHA256 で導く（用途の名前で分ける）。別の秘密を足さないのは、施設が守る秘密のファイルを増やさないため。そのため **`SESSION_SECRET` を替えると、保存した TOTP の秘密は読めなくなり、管理者が TOTP をやり直す**（利用者は次のログインで登録し直す）。
  - **回復の手段**：利用者が認証のアプリを失くしたときは、**管理者が「TOTP をやり直す」**（秘密を消し、その利用者のセッションを閉じ、次のログインで登録の段にする）。回復の符号（使い捨ての予備の番号）は持たない。**運用では管理者を2人以上置く**（互いに TOTP をやり直せるように）。
  - **未決（段 2b で決める）**：管理者が1人だけで、その管理者が認証のアプリを失くしたときの道。案：起動の時に秘密のファイル（`INITIAL_ADMIN_PASSWORD_FILE` と同じ渡し方）で、名指しした1人の利用者の TOTP をやり直す（次のログインで登録の段にする）。使ったことを監査の記録に残し、使い終えたら設定から外す。段 2b（閉じた網で動かす形・秘密をファイルで渡す形）と一緒に決める。それまでは、管理者を2人以上置く。
- **ログインの一時停止**：`LOGIN_LOCK_THRESHOLD` 回続けて失敗したら（パスワード・TOTP・画面のロックを解く・再認証の失敗を同じに数える）、`LOGIN_LOCK_MINUTES` 分ログインできない。時間が過ぎたら戻る（永久には止めない）。止めている間の試みは数えず、止める時間も延ばさない。一時停止にしたら、その利用者のセッションを閉じる。管理者は一時停止を解ける。失敗の文言は1つにして、利用者名の有無・一時停止の有無を答えの違いで知らせない。
  - **数え方**：確かめる前に、データベースの原子的な更新で「試みの枠」を1つ取る（失敗の数が決めた回数より少ないときだけ1つ増やす）。同時に多くの要求を送っても、枠を取れた要求だけが確かめに進むので、決めた回数より多くは試せない。パスワードが合ったら（TOTP が残っていても）枠を返し、ログイン・ロックの解除・再認証を終えたら数を0に戻す。
- **試みの遅らせ**：利用者ごとの一時停止とは別に、ログイン（まだ誰か分からない要求）の回数を、1 分あたり**利用者名ごと**（`LOGIN_RATE_LIMIT_PER_MINUTE`。確かめた接続元があれば「利用者名×接続元」も）と**全体**（`LOGIN_RATE_LIMIT_GLOBAL_PER_MINUTE`）で数え、超えた試みは**断らずに、答えを返すのを指数的に遅らせる**（0.25 秒から倍に、最大 10 秒）。ほかの人が失敗を重ねても、正しい利用者が締め出されることは無い（遅くなるだけ）。締め出すのは利用者ごとの一時停止だけ（時間で解け、管理者が解け、監査に残る）。遅らせ始めたことは、1 分の枠ごとに1回記録に残す（利用者名は残さない）。
  - `X-Forwarded-For` のような偽れる値は鍵に使わない（信じるプロキシの設定ができるまで、確かめた接続元はいつも無い）。
  - 利用者名は正規化（NFKC・小文字・空白の除去）してから数える（ログインで利用者を引くときも同じ形にそろえる）。大文字小文字・空白・全角半角を変えても同じに数える。
  - 利用者名ごとの数は、SHA-256 で決まった数（4096）の桶に入れて持つ。存在しない利用者名を次々に使っても記憶は増えず、鍵を替えて逃げても全体の数で遅らせる。存在する名前と存在しない名前を同じ形で数え、遅れ方で有無を知られない（存在しない名前を1つの共通の鍵にまとめると、その鍵だけが混んで有無が分かるので、そうしない）。
  - 利用者名を引く前に数えるので、存在しない利用者名でも同じに遅らせ、同じ答えを返す（知らない利用者名でもパスワードの確かめと同じほどの時間をかける）。
  - **失敗の答えの時間の下限**：ログインの失敗の答えは、遅らせの後、利用者を引き始めてから 250 ミリ秒より前には返さない。利用者名の有無で、データベースの仕事の量（試みの枠を取る・失敗を数える）が違うため。2026-10-18 に手元（16 本の CPU、argon2id m=19 MiB・t=2・p=1）で、間違ったパスワードの失敗を各 200 回測ると、答えまでの時間の中央値は、存在しない利用者名 27.8 ミリ秒・存在する利用者名 28.5 ミリ秒（差 0.7 ミリ秒、ばらつき 1.6〜2.1 ミリ秒）。下限を置くと、各 60 回で 251.0・251.0 ミリ秒（差は測りの精度より小さい）。下限はパスワードの確かめより十分に長いので、混んでいなければ差は出ない（ひどく混んで確かめが下限を超えるときは、上の「同時に回す数」で断る）。下限は保証ではない：確かめが 250 ミリ秒を超える遅い機械や、いまの強さより強いハッシュを持つ利用者（このアプリは既定の強さでしか作らない）では、差が出うる。
  - **失敗の記録の膨らみの抑え**：遅らせの上限を超えた試みの失敗は、1行ずつではなく、1 分の枠ごとに「誰が（存在する利用者名か `unknown`）・理由・回数・最初と最後の時刻」の1行にまとめて残す（`detail` の `aggregated`・`firstAt`・`lastAt`）。上限の中の失敗はこれまでどおり1行ずつ、一時停止にしたことはいつも1行で残す。混んで断った要求（503）も、理由 `busy` でまとめて残す。まとめる鍵は 1 分の枠×利用者×理由なので、持つ数は試された名前の数では増えず、枠をまたいだ失敗は混ぜない。全体の上限を超えた後は、遅らせ始めた印（`throttled`）も、全体で超えた1行のほかはまとめる。まとめた行は、終わった枠の分だけを、枠が替わった後の最初のログインの要求か、1 分ごとの片付けで書く（書けなかった分は戻して書き直す）（プロセスの記憶の中だけに持つので、書く前にプロセスが止まると、その枠の分は失われる）。
  - ログインの途中・ログインした後の確かめ（TOTP・ロックの解除・再認証・パスワードの変更）は遅らせず、利用者ごとの試みの枠で抑える（ほかの人のログインの試みで、ロック中の職員が戻れなくならないように）。
  - 数はプロセスの記憶の中だけに持つ（再起動で消え、複数のプロセスではそれぞれで数える）。1 分の枠が替わったら0に戻す。
- **再認証**：大事な操作の前に、もう一度パスワードと、登録していれば TOTP を求める。利用者の管理（作る・役割の変更・止める／戻す・TOTP のやり直し・一時停止の解除）は、直前 5 分の中に再認証していなければ 403 で断り、画面が再認証を求めてから同じ操作を送り直す（ログインした直後でも求める）。自分のパスワードの変更は、いまのパスワードと TOTP を、二要素が任意のときのログインした後の TOTP の登録は、いまのパスワードを、その場で求める。
- **画面のロック**：画面（ブラウザ）が、操作（マウス・キー・スクロールなど）の無い時間が `SCREEN_LOCK_MINUTES` 続いたら、画面をぼかしてロックし、BFF にも知らせる。ロックの間は、頁から中身（患者の情報）を外して、ぼかした地だけを出す（ぼかすだけでは、ブラウザの開発者の道具で読めるため）。画面の API と中継は 423 を返し、頁を開き直しても中身を描かない。解くのはパスワードと、登録していれば TOTP。同じブラウザのほかのタブとは、最後の操作の時刻とロック・解除を分け合う。BFF の側でも、画面が最後に操作を知らせてから（`/api/auth/activity`。画像の取得などの裏の要求では数え直さない）`SCREEN_LOCK_MINUTES` と 60 秒が過ぎたらロックにする（閉じた・離れたタブのための保険）。ヘッダーの「ロック」で、すぐにロックできる。BFF がロックしたら（ほかのタブのロックの知らせでも）、画面は頁を読み直す（描かないだけでは、ルーターのキャッシュと頁に残った描画の元のデータ（RSC の payload）に患者の情報が残るため。読み直した頁は中身を描かない）。
  - **ずれたら閉じる側に倒す**：画面の側と BFF の側のロックの状態がずれても、画面がロックされないまま中身を出し続けない。ロックの知らせ（POST）が届かなくても（網の切れ・BFF の失敗）、画面はロックのまま中身を外し、間隔ごとに送り直す（届いたら読み直す）。どの要求でも 423 が返れば、ロックの画面にして読み直す。画面は 10 秒ごとに BFF の状態（`/api/auth/status`。読むだけで、操作の時刻は数え直さない）を確かめ、ほかのタブの知らせを取りこぼしても閉じる。解くのは、BFF がパスワード（と TOTP）を確かめて通したときだけ（BFF の側がロックしていないずれのときも確かめる）。ほかのタブの「解いた」の知らせでは、BFF に聞き直してロックしていないと答えたときだけ戻す。操作の無い時間は、そのタブの時計の進み方（`performance.now`）で数え、ほかのタブの操作の時刻は延ばす向きにだけ使う（先の時刻は使わない）。
- **セッション**：cookie（`__Host-tsunagi_session`）は乱数の token で、`HttpOnly`・`Secure`・`SameSite=Strict`・`Path=/`、`Domain` は付けない（名前の `__Host-` で、ブラウザはこの形の cookie だけを受けるので、同じ親のドメインのほかのサーバーや TLS の無い頁から、同じ名前の cookie で上書き・固定されない）。CSRF の token は cookie ではなく、セッションの行に持って頁に渡す（下の「CSRF の対策」）ので、cookie はこの1つだけ。データベースには token の SHA-256 だけを持つ。ログインし終えたとき（ログインの途中の段から進んだとき）は、途中の token を捨て、新しい token と CSRF の token のセッションに替える。途中のセッションを消せたとき（まだ残っていたとき）だけ新しいセッションを作る（同じ途中のセッションから二度ログインさせない。もう無ければ 409）。作った後に、利用者が確かめた時のまま（有効・一時停止でない・パスワードの変更の時刻と TOTP の秘密が同じ）かを見て、違えば作ったセッションを消す（確かめている間にパスワードを変えた・TOTP をやり直した・止めた利用者の古いログインを、後から生き残らせない。利用者を変える操作は、どれも利用者の行を変えた後にセッションを消すので、どの順に重なっても残らない）。データベースの transaction の隔たりには頼らない（SQLite の adapter は1つのつなぎを使い、transaction の途中にほかの要求の文が入りうる。わざと取り消すと、その文まで消えるので、transaction の中で断るときも取り消さない）。TOTP の登録とパスワードの変更は、確かめと書き込みを1つの文（条件つきの更新）にし、利用者が有効・パスワード（と TOTP の秘密）が読んだ時のまま・そのセッションがまだ使える（残っていて、同じ段で、期限の前）ときだけ書く。書けたら、ほかのセッションを閉じる。ログインし直したら、そのブラウザが持っていた前のセッションを消す。ログインの途中（TOTP の入力・登録・パスワードの変更の待ち）は 10 分、ログインした後は 12 時間で切れる。期限の切れたセッションは、起動の時と 1 分ごとに片付ける（片付ける前でも使わせない）。役割と状態は要求のたびにデータベースから読み、管理者の変更は次の要求から効く（止めた利用者・TOTP をやり直した利用者のセッションは閉じる）。`Secure` なので、TLS の外では送られないことがある（手元の `127.0.0.1`・`localhost` を除く）。施設ではリバースプロキシで TLS にする。
- **CSRF の対策**：`SameSite=Strict` に加え、状態を変える要求（POST・PATCH）は `Origin` がこのアプリと同じであることと、セッションごとの token（`x-csrf-token`）を確かめる。ログインの要求は、まだセッションが無いので `Origin` だけを確かめる。`Origin` は要求の `Host` と比べるので、リバースプロキシは `Host` を書き換えずに渡す。
- **監査の記録**：ログイン（成功・失敗とその理由）・ログアウト・ログインの一時停止とその解除・回数の上限で断ったこと・画面のロックと解除・再認証・TOTP の登録とやり直し・パスワードの変更・利用者を作る・止める／戻す・役割の変更を残す。**パスワード・TOTP の値・セッションの token は記録しない。** 知らない利用者名の失敗は、打ち間違えたパスワードであることがあるので、名前を記録しない（`unknown` として残す）。遅らせの上限を超えた試みの失敗と、混んで断った要求は、1 分の枠ごとにまとめて1行で残す（上の「失敗の記録の膨らみの抑え」）。

**このアプリでは担えないもの**（文書に書く）：サーバーの OS のログインの二要素（14 遵守事項⑤・表14-1）、ネットワーク・端末の管理、バックアップと復旧の手順、委託先の管理。

## 4. 開発用の認証の切り替え（`AUTH_MODE=dev`）
- ログインを省き、画面の上に `[検証モード｜役割：管理者・医師・技師・閲覧]` の切り替えを出す。画面の全体に「検証モード」の帯を出し続ける。
- **書き込み（修正・削除・取り込み・ワークリストの作成）は止める。** 書き込みも試すときは `DEV_ALLOW_WRITE=true` を足す。ただし書き込みの道は段 4 まで作らない（中継は WADO-RS の読み取りだけ。3.2）ので、段 4 より前は `DEV_ALLOW_WRITE=true` にすると起動しない。
- **`AUTH_MODE=dev` は、段 1a〜1b では `BACKEND_MOCK=true` のときだけ起動する**（モックでなければ、待ち受けの住所が手元だけでも起動しない）。実の画像サーバーには `local`（段 1b）を使う。段 2 より後で、実の画像サーバーに対する検証の形を足すかは、その段で決める。
- 監査の記録は、検証モードでも取る（役割の切り替えも記録する）。

## 5. 公開と配布
- リポジトリは公開。**社内の名前・秘密・実の患者のデータを入れない。** 見本のデータ（`tests/fixtures`）は合成の患者だけで、公開の前に中身を人が確かめる。
- CI（GitHub Actions）：PR で lint・型・Vitest・Playwright（モック）。`main` への merge と版のタグで、イメージを作って GHCR へ。週に1回、`main` を作り直して出す（イメージの中の包みの更新を取り込む）。**`permissions: packages: write` は、イメージを作る仕事と古いイメージを片付ける仕事にだけ**付け、`id-token: write`（署名）はイメージを作る仕事にだけ付ける（リポジトリ全体を読み書きにしない）。
- イメージのタグ：`vX.Y.Z` と `sha-<短い hash>`、作り直しには `rebuild-YYYYMMDD` も付ける。作り直しは版のタグを付けない・上書きしない。`latest` は付けてもよいが、配備は版のタグか digest を指定する。イメージは CI（lint・型・Vitest・Playwright・イメージの試しの起動）が通ってから出す。
- イメージの署名：出したイメージの digest に、cosign の鍵の要らない署名（GitHub Actions の OIDC）を付ける。確かめ方は README。
- イメージの片付け：版のタグの付いたイメージは消さない。ほかのタグのイメージは新しい順に 10 個と、2 日より新しいものを残し、残りとタグの無いイメージを週に1回消す（署名などの子は親と一緒）。いまは dry-run で、消す候補を記録に出すだけ（記録を確かめてから消す形にする）。範囲は README と `.github/workflows/image-cleanup.yml`。
- **仕様の外で足した道**（アプリの機能ではないもの）：`/api/health`（コンテナの生死の確かめ。認証なし・画像サーバーにつながない）、`/api/audit/verify`（監査の記録のつなぎの確かめ。管理者だけ）。3.6 を参照。
- **アプリの設定の外の変数**（`.env.example` に入れない。アプリは読まない）：`TSUNAGI_IMAGE`（`compose.yaml` で使うイメージ。既定は手元で作る `tsunagi-dicom:local`）、`PLAYWRIGHT_CHROMIUM_EXECUTABLE`（試験だけ。入っている Chromium を使うとき）、`E2E_INITIAL_ADMIN_PASSWORD`・`E2E_SKIP_PREPARE`（試験だけ。`scripts/e2e-server.mjs` が `AUTH_MODE=local` の試験のサーバーを起こすとき）。

## 7. 既知の制約（2026-10-18 時点の実測）
- Orthanc の Worklists のプラグインで、REST でワークリストを作るとき、SpecificCharacterSet に `ISO 2022 IR 87` を指定すると漢字とかなが消える（エラーにならない）。`ISO 2022 IR 13\ISO 2022 IR 87` は断られる（400 `Unknown encoding`）。指定しなければ UTF-8（ISO_IR 192）で正しく入る。UTF-8 に対応しない古い装置へ JIS で渡すことは、この段の範囲外。
- Orthanc の設定の氏名の整形（1本の正規表現）では直せない形が3つある（`^Taro` の頭の空白など）。このアプリの氏名の解析では直す。
