Orthanc を**改造せずにそのまま使い**、日本の医療機関の画像の見方に合わせた検査の一覧とビューアの選び分けに、PACS の運用の操作（ほかの機器へ送る・書き出す・削除する・取り込む・値を直すなど）を足して、1つの画面で行えるようにする、Orthanc 専用の Web の画面と中継のサーバー（BFF：Backend For Frontend）。中継のサーバーは、ブラウザと Orthanc の間に立ち、ログイン・役割の確かめ・監査の記録をしてから Orthanc に問い合わせる部分。

> **医療機器としての承認・認証を受けていない。** 治験・研究・システムの試験の環境で使うためのソフトウェア（0）。医療機器プログラムに当たるかは、この仕様では決めない（0）。

## 0. 目的と使う場面

- **目的**：Orthanc の日本式の画面のラッパー、つまり PACS の画面を作る。画像を受ける・保管する・送る仕事は Orthanc が行い、tsunagi-dicom はその操作と見え方を、日本の現場の言葉と流れで1つの画面にまとめる。
- **Orthanc 専用にする。** 汎用の DICOMweb のバックエンドは持たない。DICOMweb の規格（PS3.18）の Studies Service の取引は、取得（Retrieve。WADO-RS）・保存（Store。STOW-RS）・検索（Search。QIDO-RS）の3つだけで、削除・値の修正・ほかの機器へ送る取引は無い（PS3.18 の 10.3 の Table 10.3-1。2026-10-19 22:45 に本文を取り出して確かめた）。PACS の運用の操作は、Orthanc の REST で行う。
- **使う場面は、治験・研究・システムの試験の環境の PACS にとどめる。** 診療の PACS として使う場面は、いまの範囲の外。
- **医療機器プログラムに当たるかは、確かめてから広げる。** 診療の PACS に広げる前に、厚生労働省の「プログラムの医療機器該当性に関するガイドライン」などの公開の資料で、使い方ごとに当たるかを確かめる。この仕様では当たるとも当たらないとも決めない。
- この文書の「画像サーバー」は Orthanc を指す。
- **参考にするもの**：Orthanc Explorer 2（AGPL-3.0）の機能と画面の流れは読んで参考にする。**コードは写さない**（tsunagi-dicom は MIT）。
- **持たないもの**：検査の状態の印（未検像・検像済・未読・既読・緊急・ブックマーク）と簡易レポート。検像・読影・緊急の正本は、tsunagi-dicom の外の仕組み（検像の端末・RIS・レポートの仕組み・オーダ）にあり、tsunagi-dicom の中に持つと、その仕組みと食い違う2本目の記録になる。レポートはレポートの仕組みの仕事とする（2026-10-19 に承認者が決めた）。

## 1. 原則

1. **Orthanc を改造しない。書き込みは必ず役割の確かめと監査の記録を通す。** Orthanc とビューアのソースには手を入れない（プラグインの追加と設定の変更は、施設が行う運用の範囲）。つなぎ先はすべて設定（環境変数）で決める。Orthanc とビューアが別のサーバーにあってもよい。
   - 書き込み（送る・書き出す・削除・取り込み・値の修正など）は、**決めた操作ごとの Orthanc の REST だけを、BFF から呼ぶ。** ブラウザから Orthanc へ直に書かせない。どの操作も、役割の確かめ（3.6 の役割ごとにできる操作）と監査の記録を必ず通し、断った要求も記録に残す。
   - ビューアが画像を取る中継（`/api/dicom-web/...`）は、これまでどおり読み取り（WADO-RS の GET・HEAD）だけを通す。書き込みの道は中継に足さず、操作ごとの画面の API として作る。
2. **Orthanc の標準の道と独自の道を使い分ける。** ビューアの取得は Orthanc の DICOMweb のプラグインの WADO-RS、検査の検索は QIDO-RS を使う。PACS の運用の操作（送る・書き出す・削除・取り込み・値の修正・結合・分割・機器の一覧と疎通の確かめ・受け取りの記録・保管の状態）は、Orthanc の独自の REST を使う。汎用の DICOMweb のバックエンドは持たない（0）。
3. **どこでも動く。** 特定の施設・ネットワーク・名前に依らない。施設ごとの値は設定で渡す。リポジトリには例の名前（`pacs.example.org`）だけを書く。
4. **安全を既定にする。** 既定の設定は認証が有効。証明書の確かめは切らない（自前の CA は `*_CA_FILE` で渡す）。秘密の値に既定値を置かない。書き込みの操作は、既定で使える役割を狭くする（削除・利用者の管理・システムの設定は管理者だけ。3.6）。
5. **ガイドラインに沿った機能を持つが、「準拠」とは言わない。** 厚労省のガイドライン（第7.0版）の項目のうち、アプリケーションで担える部分を実装し、その対応表を文書と画面で示す。ガイドラインへの適合は、運用を含めて各施設が判断するもので、このソフトウェアだけで「準拠」とはならない。
6. **商用の製品の名前・画像・ロゴを使わない。** アイコンは Lucide、見た目は Tailwind CSS で作る。文書でも商用の製品の名前を出さない（「日本の医療機関で広く使われている画像の閲覧の慣習」のように書く）。ほかの OSS の画面（Orthanc Explorer 2 など）は機能と画面の流れを参考にするだけで、コードを写さない。
7. **医療の現場の言葉を言い換えない。** 検査・シリーズ・モダリティ・受付番号・送信・インポートなど、医療関係者のよく知っている言葉をそのまま使う（別の言葉にすると、使うときに混乱する）。画面の言葉は 2.2 の用語集から選ぶ。同じ理由で、**現場で別の意味を持つ言葉を、違う意味で使わない**（例：現場の「既読」は、依頼医が読影レポートを読んだことの記録で、レポートの仕組みが持つ。そのため tsunagi-dicom は「既読」の印を持たない。0）。機能ごとに「診断用ではない」の断り書きは足さず、画面に共通の注意の表示も出さない。医療機器としての承認・認証を受けていないことと、使う場面（治験・研究・システムの試験の環境。0）は、README と仕様書にまとめて書く。
8. **BFF は、役割ごとに許可した項目だけをブラウザに返す。** 画面の API（一覧・詳細・検索・時系列・受け取りの記録・機器の一覧など、BFF が組み立てて返す JSON）では、Orthanc の応答をそのままブラウザに渡さない。役割ごとに「見せてよい項目の一覧（許可の一覧）」を持ち、載っていない項目は返さない（足し忘れたときは「出ない」側に倒れる）。
   - **既定の役割**（管理者・一般。3.6）の許可の一覧は、**その役割が使える画面に要る項目をすべて含む**。できる操作（3.6 の役割）は変えない。この決まりを入れても、既定の役割の見え方・検索・操作は変わらない。
   - 「**すべての DICOM の値を見る**」は、許可の一覧とは別の明示の権限にする。既定では管理者・一般の両方に与える（施設の決まりで絞るときは、一般の割り当てから外す）。この権限があるときだけ、DICOM の値を返す画面（詳細のパネルの「DICOM タグ」の検査単位の要約と、サムネイルから開く画像の場所の画像の一覧・主なタグ・すべてのタグ。3.1）を使える。
   - **画像と文書の本体**（画素・フレーム・Encapsulated PDF など）と、**ビューアへ渡す取得の道**（BFF の中継の WADO-RS の読み取り）は、この選別の対象にしない。ビューアは BFF の中継を通して画像を取る（3.2）。中継は取得だけを通し、**検索（QIDO-RS）は返さない**——検索の結果は画面の API（この許可の一覧の対象）から返す。
   - **許可の一覧で項目を隠すだけでは、取得の道からの秘匿は保証しない。** 画像と WADO-RS の `metadata`（ビューアが取る DICOM の値の全部）・画素に焼き込まれた文字は、この選別の外にあるので、画面の API で隠した項目も取得の道からは読める。取得の道で何をどう隠すかは、ブラインド読影の役割（3.8）で扱う論点にする。
   - 開発用の切り替え（4）で選んだ役割にも、同じ規則を当てる。
   - 許可の一覧は `src/lib/fields.ts`（段 2）。項目は画面に出す形の名前で持ち（氏名は漢字・かな・ローマ字に分けたもの。PN の元の文字列は返さない）、BFF が画像サーバーの応答から組み立てる。一覧に無い役割には何も返さない。
   - 書き込みの操作の画面（送り先の機器の一覧・受け取りの記録・削除の確かめの画面など）も、同じ許可の一覧で絞る。機器の住所（Host・Port）は、機器の管理に要る役割にだけ返す（3.3）。
   - この決まりは、のちの「ブラインド読影の役割」（3.8）を作り直し無しで足せるようにするためのもの。ブラインド読影の役割で、ビューアや取得の道からの値の漏れをどう止めるかは、その段で設計して確かめる。
9. **機能は足すより削る。** この道具は治験・研究・システムの試験の環境の PACS の画面で、診療の現場の全部を置き換えるものではない。足すかどうか迷う機能は後ろに回し（消さずに「後ろ」に置く）、小さく保つ。
10. **正本が外にあるものは持たない。** BFF のデータベースに持つのは、利用者・画面の設定・ビューアの覚え・監査の記録だけ。画像と DICOM の値の正本は Orthanc、検像・読影・緊急・レポートの正本は外の仕組みにある。Orthanc で分かること（受け取りの記録・機器・保管の状態）は、その都度 Orthanc から読み、BFF に写して持たない。

## 2. 技術の構成

| 項目 | 選ぶもの | 理由・条件 |
|---|---|---|
| 画面と BFF | Next.js（App Router・TypeScript・`output: 'standalone'`） | 画面とサーバーの処理を1つのコンテナにまとめられる |
| 見た目 | Tailwind CSS・shadcn/ui（Radix UI）・Lucide | 商用の素材を使わない |
| データの取得 | TanStack Query | 段 2（一覧を作り込む段）から。段 1a の頁はサーバーの側で描く |
| BFF のデータベース | SQLite（WAL）＋ Prisma。PostgreSQL に切り替えられる | 小さく始め、件数が増えたら替える |
| 試験 | Vitest（単体）・Playwright（画面。モックのバックエンドに対して流す）。結合の試験は Playwright で、試験の中で立てた Orthanc と DCMTK のコンテナに対して流す（[`integration-test.md`](integration-test.md)） | CI でもクラウドの開発環境でも、社内の画像サーバー無しで流せる |
| 配布 | コンテナのイメージ（GHCR）。版の番号のタグと digest で配る | 前の版にすぐ戻せる |
| 導入の形 | Orthanc とセットで導入する。tsunagi-dicom と Orthanc は別々のコンテナにし、1つの compose（`deploy/compose.yaml`）で配る（5 の「Orthanc とセットで導入する形」） | Orthanc を改造せずに、Orthanc の REST を外に出さない形を既定にできる。Orthanc を別の場所に置く形（環境変数でつなぐ）も残す |
| ライセンス | MIT | Orthanc とは REST・DICOMweb でやり取りするだけで、そのコードを取り込まない。Orthanc Explorer 2（AGPL-3.0）のコードも写さない |

画面の見た目の基準：
- **地の色は画面の役目で分ける。** 一覧・時系列・受け取りの記録・機器・管理など、文字を読む画面は**明るい地を既定**にし、暗い地にも切り替えられる（利用者ごとに覚える）。画像のサムネイルの並びは、まわりだけ暗い地にする。ビューア（OHIF など）は外の部品で、暗い地のまま。日本の医療機関で広く使われている画面でも、画像を見る画面は暗い地、一覧や事務の画面は明るい地が多い。
- 暗い外枠（暗いヘッダー・サイドバー）は使わない。上の帯と左のナビは控えめな地（`#f6f6f6`、暗い地は `#242424`）にする。モダリティ MR の印は赤紫 `#9333ea`（暗い地は `#c084fc`）にして、青い CT と見分ける。
- グレーは赤・青に振れない中立の灰（R=G=B）にする。面の区別は枠線より地の濃淡で付ける（地 → 控えめな地 → muted → muted-strong）。
- 明るい地：地 `#ffffff`、控えめな地 `#f6f6f6`、muted `#eeeeee`、muted-strong（検索の条件の帯など）`#e2e2e2`、文字 `#262626`、ラベル `#5f5f5f`（白・`#f6f6f6`・`#eeeeee`・`#e2e2e2` の上で 6.39・5.91・5.50・4.93:1）、値 `#1a1a1a`（太字）、境界線 `#d2d2d2`、入力欄・ボタンの輪郭 `#8c8c8c`（border-input。白い地で 3.36:1）、主の色（リンク・強調。ボタンの地は白い字）`#4b4fbf`（白い地で 6.62:1、`#f6f6f6` の上で 6.13:1、`#eeeeee` の上で 5.71:1）。ボタンの地の hover は `#3b3ea3`、押している間は `#2f3288`。選んだ行の地は主の色の薄い地 `#ededf9`。
- 暗い地：地 `#1b1b1b`〜`#242424`、muted `#2d2d2d`、muted-strong `#383838`、境界線 `#3a3a3a`、入力欄・ボタンの輪郭 `#777777`（`#1b1b1b` の上で 3.74:1）、文字 `#e8e8e8`、ラベル `#a3a3a3`（`#1b1b1b` の上で 6.83:1、`#242424` の上で 6.15:1）、値 `#ffffff`（太字）、主の色（ボタンの地で白い字）`#4b4fbf`（白い字との対比は 6.62:1）。暗い地の上のリンクの文字は `#a5a8ff`（`#1b1b1b` の上で 7.91:1、`#242424` の上で 7.13:1）。選んだ行の地は主の色を 25% だけ地に重ねた `#272844`。
- 選んだ行・サムネイルの縦線や枠、進みの帯は、地との対比 3:1 以上を保つため、ボタンの地の主の色ではなく ring（明るい地は `#4b4fbf`、暗い地は `#a5a8ff`）にする。
- 主の色は、選択・主のボタン・リンクにだけ使い、状態の意味（正常・注意・異常）には使わない。状態の色（誤りと終わったこと）は主の色とは別の枠で持つ。
- 誤りの文言の色：明るい地 `#d1242f`（白い地で 5.24:1）、暗い地 `#ff7b72`（`#1b1b1b` の上で 6.83:1）。
- どちらの地でも、基準の文字は 14px（0.875rem）、行間 1.5、部品の間の余白は今のウェブの画面の感じ（詰めすぎない）。文字と地の対比は WCAG 2.2 の AA（4.5:1）以上にする。
- 色と文字の値は1か所（設計の値・design tokens。`src/app/globals.css`）で持つ。対比は `tests/unit/design-tokens.test.ts` で確かめる。同じ作者のモダリティのダミーの画面も、同じ値を使う。
- 途中のこと（実施中・送信中）の印の色は warning：明るい地 `#9a6700`、暗い地 `#d29922`。状態の札の枠と印に使い、文字と形の印を必ず添える。
- 画面の部品・並び・メニューの決まりは [`docs/design-system`](design-system/README.md) にある。画面を触る前に読む。色の値は同じ文書の `tokens.md` と `globals.css` を一致させる（`tests/unit/design-system.test.ts` が確かめる）。
- 地の色の切り替えは見出しの「表示」（「ライト」「ダーク」の2つのボタンの並び。押している側が今の地）。選んだ地は BFF のデータベースに利用者ごとに覚える（検証モードは1つの利用者 `dev` として覚える）。ログインの前の頁は明るい地。

画面の言葉：最初は日本語だけ。ほかの言葉への切り替えは後の段で決める。文書は日本語だけ（英語の README は、段 3 で承認者の指示により外した）。画面に出す言葉は 2.2 の用語集から選ぶ。

### 2.1 設定（`.env.example`）

設定の正本はリポジトリの [`.env.example`](../.env.example)（値は例の名前だけ。秘密は空）。ここには要点だけを書く。

| 群 | 変数 | 要点 |
|---|---|---|
| バックエンド | `BACKEND_KIND` | `orthanc` だけ（省ける）。`dicomweb`（汎用の DICOMweb）は段 3 で外した。書いてあれば起動しない |
| | `BACKEND_ORTHANC_URL`・`BACKEND_DICOMWEB_URL` | Orthanc の REST の URL（例 `https://pacs.example.org`）と、Orthanc の DICOMweb のプラグインの URL（例 `https://pacs.example.org/dicom-web`）。どちらも必須（`BACKEND_MOCK=true` のときだけ省ける） |

### 2.2 画面の言葉（用語集）

画面に出す言葉は、この節の用語集から選ぶ。例外は1件で、仕様書・README・コードのコメントの地の文は、これまでの書き方のままにする（文書の言葉と画面の言葉を分ける）。用語集の言葉は、PACS・医療情報システムの画面で普通に使う漢語・カタカナ語から選び、2026-10-20 に承認者が確かめた（原則 7）。表に無い言葉を画面に足すときは、先にこの表に足す。

**文言の決まり**

- ボタン・列名・項目名・状態は体言にする（「送信」「接続確認」「送信完了」）。動詞の連用形（「送る」「確かめる」）は使わない。「開く」「閉じる」「キャンセル」「ログイン」「ログアウト」は慣用なので、そのまま使う。
- 確かめの画面の実行のボタンは「〜する」にし（「送信する」「削除する」）、確かめの画面を開くボタン（「送信」「削除…」）と分ける。
- 知らせと誤りは敬体にする。1文目に起きたことを書き、次にすることが要るときだけ2文目に書く（「接続できませんでした。ネットワークと接続先の設定を確認してください。」）。
- **画面に説明の文を原則置かない。** 要るときは1行にする（欄の下の注記か、見出しの横の短い補い）。操作と仕組みの説明は、この仕様書と README に書く。
- 件数は「直近 100 件」「6 件」の形で書く。
- 日時は `yyyy/MM/dd HH:mm`（秒が要る画面は `HH:mm:ss`。時は0で埋める）で、サーバーの時間帯（`TZ`）の時刻で出す。Orthanc が UTC で返す時刻（変更の記録の `Date` など）も、`TZ` に直してから出す。
  - 検査の時刻（DICOM の TM）は、`HH`・`HHMM`・`HHMMSS`・`HHMMSS.F…`（小数は 1〜6 桁）のどれか（PS3.5 6.2）。時だけの値（`07`）は分が分からないので `07:--` と出す（`07:00` と出すと、無い値を足すことになる）。形の違う値は出さない。
- 英字の内部名（`admin`・`Success` など）を画面に出さない。DICOM の属性の名前（StudyInstanceUID など）と、設定の変数の名前は、そのまま出してよい。
- 「患者ID」「ユーザーID」「要求ID」「AEタイトル」は、英字と日本語の間に空白を入れない（用語の名前だけ。文の中の語は、これまでどおり）。
- 「既定」は画面に出さない。いつも使う 1 件は「標準」、最初に入っている値は「初期設定」と書く。「頁」も画面に出さず、「ページ」と書く。
- 語の選び方と、製品をまたいだ対照は [`docs/design-system/glossary.md`](design-system/glossary.md)。この表と食い違うときは、先に両方をそろえる。

### 2.3 画面の振る舞いの決まり

画面の状態（今いる頁・押せる物・待っている間・終わった後・選んだ行）は、色だけでなく形でも示す。どれも 2026-10-20 の画面の見直しで決めた。

- **今いる頁**：画面への入り口は、本文の左の「左のナビ」（群は業務・接続・管理。幅 208px で、上の帯の左端のボタンで 56px に閉じられる）に置く。今いる頁の項目を、選んだ行の地・左の線・太字で示し、`aria-current="page"` を付ける。上の帯には画面への道を置かない（2026-10-25。それまでは上の帯のタブ）。ブラウザのタブの題名は頁ごとに変える（「検査一覧 - tsunagi-dicom」）。頁の見出しの大きさは1つにそろえる。
- **押せる物**：ボタンとリンクは、カーソルを指の形にし、hover・押している間・フォーカスで見た目を変える。hover の地は、ボタンの地と見分けられる対比にする。押せないときは薄くし、カーソルを禁止の形にする。リンクは頁の移動だけに使い、操作はボタンにする。
  - 地のあるボタンと枠のボタンは、小さな影で浮かせる（枠のボタンの地は白）。押している間は 1px 沈めて影を消す。絞り込みの並びの中のボタンは、並びを崩さないよう沈めずに内側に影を付ける。手応えの指定は共通の部品（`src/components/ui/button.tsx` の `pressFeedback`・`pressInset`）の1か所に置き、Button を使わない押せる物もそれを使う（2026-10-21。承認者が「全体にクリック感が無い」と指摘した）。
- **待ちの表示**：操作から 0.3 秒たっても結果が出なければ待ちの印（スピナーと「読み込み中」などの文字）を出し、一度出した印は 0.5 秒は消さない（すぐ終わる操作でちらつかないように）。印は押したボタンの中か、一覧の上の細い帯に出し、画面全体を覆う幕にはしない。部品は1つにし、どの画面も同じ部品を使う。書き込みの操作は、待ちの表示のついでに自動で送り直さない（3.5）。
- **選んだ行**：検査一覧で選んだ行は、主の色の薄い地と左の縦線で示し、hover の地と分ける。
- **終わった後**：送信と削除は、終わったことを残る知らせで示す（送信は送信先と時刻、削除は消した検査）。送信を受け付けた後は、同じ確かめの画面から重ねて送らない（3.4）。

### 3.1 検査の一覧
- **すぐ絞れる見出し**：検査日（今日・昨日・過去7日・今月・すべて・期間指定。画面の言葉は 2.2）、モダリティ（すべて・CT・MR・CR/DX・US・ES・MG・DOC・SR。色分け）、横断の検索（患者 ID・氏名の漢字・かな・英字・受付番号・検査の記述）。
  - モダリティの見出しは、DICOM の Modality の定義語（PS3.3 C.7.3.1.1.1）で分ける。DOC は Modality が `DOC`（Document）の検査だけ。`OT`（Other）は文書とは限らないので、どの見出しにも入れない（「すべて」には入る。2026-10-21 の規格の監査で直した。それまでは DOC に入れていた）。
  - 検査の状態の見出し（未検像・検像済・未読・既読・緊急・ブックマーク）は持たない（0。段 3 で外した）。
  - **1 行の並び・件数の見出し**：検査日・モダリティは、1 つの並びのボタン（高さ 28px。押せる大きさの下限 24px 以上）にし、**件数を添える**（`今日 (3)`、`CT (6)`）。幅が足りなければ折り返す。「8 件」の見出し（一覧の件数）は同じ行に置く。
  - **件数は BFF が数える**（`/api/studies` の `facets`）。各見出しの件数は、**数えきれた（画像サーバーが条件に合う検査を全部返した）ときは**「その見出しを押したあとの一覧の件数」と同じ：ほかの見出しと横断の検索は、いまの値のまま当てる（モダリティの件数は検索を、検査日の件数はモダリティと検索を当てる）。数えるのは許可の一覧で絞った後の項目だけで、**許可されていない項目の見出しの件数は、キーごと返さず、画面も出さない**（見えない項目の件数を漏らさない。原則 8）。期間の指定には件数を添えない。
  - **上限に届いたとき**：一覧は、条件に合う検査のうち、検査日の新しい順に上限（1000 件）まで。
    - QIDO-RS の `limit` は返す数の上限で、**どの検査を返すかの順は規格が決めていない**。続きがあるときは、答えに `Warning: 299 …` を付ける（PS3.18 8.3.4.4・8.3.4.4.1）。実の Orthanc（イメージ 26.9.1。Orthanc 1.13.0）は、1007 件のうち `limit=1000` で、検査日の順でない 1000 件を返し、`Warning` は付けなかった（2026-10-21 に結合の試験の 13 で測った）。だから、`limit` で切った答えを「新しい順の 1000 件」とみなさない。
    - BFF は、上限より 1 件多く（1001 件）求める。返した数が求めた数に届いたとき、または `Warning: 299` があったときは「続きがある」と読む。続きがあれば、検査日の範囲で区切って、新しい側から問い合わせ直す（明日より後 → 今日までの 7 日 → 30 日 → 1 年 → 5 年 → それより前）。区切った範囲にも続きがあれば、範囲を半分に分けて新しい側から問い合わせる。上限に届いたら止める。1 回の検索で問い合わせる回数は 40 回までで、届いたら、そこまでに集めた新しい側の検査を出す（`src/lib/backend/newest-studies.ts`）。
    - 1 日に収めても続きがあると（その日に上限より多い検査がある、または画像サーバーが 1 回に返す数を上限より少なく切る。規格は画像サーバーの側の上限を認めている）、その日の中は画像サーバーが返したものになる（その日の全部とは限らない）。そのときは、その日で止め、古い日の検査は足さない（新しい側に読み残しを抱えたまま古い検査を出さない）。続きがあるとき、検査日の無い検査（範囲の条件に合わない）は一覧に出ないことがある。
    - 件数を確定と出すのは、**画像サーバーが条件に合う検査を全部返したとき**（続きが無いとき）だけ。返した数（1000 件に届いたか）では決めない。上限ちょうど（1000 件）でも、続きが無ければ確定。最初の答えに続きがあっても、検査日の条件があり、区切った範囲を全部読みきり、上限で切り捨てた検査が無ければ確定（検査日の条件が無いときは、検査日の無い検査を引けたか分からないので「以上」）。
    - 数えきれない件数は、確定の数として出さず **「以上」**（`すべて (1000 以上)`）にする（`facets.atLeast`。一覧の件数の `exact` と同じ考え方）。モダリティの件数は、いまの一覧を数えきれなかったとき全部が「以上」。検査日の件数は、読んだ範囲に全部が入る見出し（読んだいちばん古い検査の日より後に始まる見出し。読んだ検査は検査日の新しい側から欠けなく並ぶため）だけが確定で、そうでない見出しと「すべて」が「以上」。「以上」のときは「押したあとの件数と同じ」とは限らない（押すと、より多く出うる）。
  - **検査日の件数のための追加の検索**：検査日の件数は、いまの一覧が「全期間」でないときだけ、全期間の検索（日付の条件なし・上限 1000 件）をもう 1 回、画像サーバーへ求めて数える。検査日を許されていない役割には求めない。**追加の検索が失敗したときは、検査日の件数だけを出さず、一覧とモダリティの件数は出す**（最初の検索の失敗は、これまでどおり一覧ごと失敗）。
  - **件数を数えたことの監査の記録**：件数から知れること（例：「今日＋患者 ID」で一覧は 0 件でも、全期間の件数から過去の検査の有無が分かる）を後から追えるよう、検索の記録（`search`）の補足に `facets` を足す：数えた範囲（`dateScope`）・追加の検索をしたか・読んだ数と上限に届いたか・失敗したか・数えたときの絞り込み（検索の語は有無だけ。詳細条件は、効かせた条件の名前だけ（`conditions`））・返した件数（検査日・モダリティ）・「以上」があったか。患者の値は入れない（返した検査の患者 ID と UID の組は、これまでどおり `returned` に残る）。
  - **比べた案と推奨**：(A) 件数の範囲は今のままにして、上のとおり監査に残す。(B) 患者 ID・氏名などで絞っているときは、検査日の件数を今の検査日の範囲の外では数えない。**推奨は A**。理由：B は検索の語があるときに検査日の件数が「押したあとの件数」と合わなくなり（「昨日」を押すと違う数が出る）、件数の見出しの目的が崩れる。A は、その役割が全期間を押せば見られるものと同じ範囲の件数に限り、足りなかった「後から追えること」を監査で補う。B のほうが漏れは少ないので、施設の運用で件数からの推測まで避けたい場合は B に替えられる（変えるのは `listStudies` の追加の検索の条件だけ）。
  - **使うことの少ない条件は「詳細条件」の中**：期間指定（開始日・終了日）と、生年月日・性別・受付番号・検査名（2026-10-21。それまでは期間指定だけで、承認者が「詳細と呼べない」と指摘した。同じ日に、確かめた承認者が「依頼医は不要」「絞れる項目が一覧の列に無いと使いにくい」と指摘したので、依頼医を外し、受付番号の列を一覧に足した）。詳細条件で絞れる項目は、どれも一覧の列に見える（生年月日・性別は各列、受付番号は受付番号の列、検査名はモダリティと検査名の列）。「詳細条件」を押したときだけ出し、どれかで絞っているときは最初から開く。閉じていても、絞っている条件の数を「詳細条件（2）」のように添える。横断の検索は並びと同じ行に置く。
    - **選んだ条件と理由**：PACS の検査一覧で一般的な条件のうち、Orthanc の QIDO-RS で引けるもの（Orthanc が検査・患者の単位の主な値として持つ項目）を選んだ。生年月日と性別は、氏名・患者 ID と並ぶ本人の確かめの手がかり（3.1 の和暦・年齢・性別）。受付番号・検査名は、横断の検索（上限 1000 件の中を BFF で探す）と違い、Orthanc の検索の条件になるので、上限の外の古い検査も引ける。
    - **足さなかった条件**：送り元の AE タイトルは、Orthanc の DICOM の値ではなく、画像のメタデータ（`RemoteAET`）なので QIDO-RS では引けない（受信一覧に出す。3.3）。施設名（InstitutionName）は、シリーズの単位の値で、検査の単位の検索の条件に向かないため外した。
    - **当て方**：生年月日・性別は一致。受付番号・検査名は、値を含むもの（QIDO-RS の `*値*`。空白で区切った語は、その順に含むもの：「chest ct」は `*chest*ct*`）。大文字と小文字は区別しない（Orthanc 26.9.1 の QIDO-RS で、受付番号・検査名のどちらも区別しないことを、2026-10-21 に結合の試験の 11 で測った）。BFF は Orthanc の答えを、全角と半角・大文字と小文字を区別せずに確かめ直す（Orthanc が合うとした検査は落とさない）。
    - **受けない値**：生年月日は日付の形、性別は M・F・O、文字は 64 字まで。文字の欄では、QIDO-RS の値で特別の意味を持つ字（ワイルドカードの `*` `?`、区切りの `\` `,`）と制御文字を受けない（画面では打っても入らず、URL にあれば条件にしない）。
    - **許可の一覧**：許可されていない項目の条件が付いていたら、条件を外して広げず、画像サーバーへ求めずに 0 件にする（隠した項目で探せない。原則 8。横断の検索が隠した項目では合わないのと同じ向き。監査の記録の `facets.filter.blocked` に条件の名前を残す。2026-10-21 の独立レビューの指摘で、黙って外す形から直した）。件数の見出しも、同じ条件で数える（検査日の件数のための追加の検索にも、詳細条件を当てる）。
- **読みやすい一覧（14px）と日本式の整形**
  - **氏名の解析**：`Alphabetic=Ideographic=Phonetic` の標準の形のほか、崩れた形（ローマ字が無い、漢字が空、空白で区切る、半角カナ、敬称つき、前後の空白、4つ目以降の `=`）でも、エラーにせず読める字だけを出す。漢字の氏名（14px・太字・値の色。暗い地では白）とかなの氏名（14px・ラベルの色）に分け、**一覧では別の列**（かなは漢字の右）に出す。試験は `docs/patient-name-test-cases.md` の 30 の形（元の 23 の形に、空の入力などを足したもの）から始める。
  - **和暦・年齢・性別**：一覧では、生年月日・年齢・性別を3つの短い列に分ける（`1975/05/10`・`51歳`・`男`）。和暦は詳細のパネル（`1975/05/10（昭和50年）`）と、一覧の生年月日の `title` に出す。年齢は検査日の時点で数える。生年月日と性別は、氏名・患者 ID と並ぶ本人の確かめの手がかりなので、1つの列にまとめて切れる形にしない（2026-10-20 に、1つの列にまとめた形から直した）。
  - **シリーズ数・画像数**。
  - **1 件を 1 行に**：一覧の行の高さは 28px（14px の文字、上下に 4px の余白）。列は、検査日時・患者 ID・受付番号（2026-10-21 に、段 8 から前倒しして足した。値に合わせた幅で、160px を超える値だけを切る。受付番号で絞る詳細条件の値が見えるように）・氏名（漢字）・かな・生年月日・年齢・性別・モダリティと検査の記述・シリーズ数と画像数・ビューア（▶ 開く と ▾。ボタンは 24px）。インポートした検査には「インポート」の印を出す（段 6。3.5）。**患者 ID・生年月日・年齢・性別は切らない**（列の幅を値に合わせる）。氏名とかなの列も、出している行のいちばん長い値に幅を合わせ、上限（氏名 240px・かな 200px）を超える値だけを切る。ほかの値が 1 行に収まらないときは `…` で切り、全文は `title` に出す（一覧の行だけ。詳細のパネルでは切らない）。モダリティと検査の記述の列が、残りの幅を取る（狭い画面では一覧の中で横にスクロールし、この列も最小の幅より縮めない）。
  - **選んだ行**：主の色の薄い地と、左の縦線（3px）で示す。hover の地はそれより薄くし、選んだ行と見分けられるようにする（2.3）。
  - **サムネイルの列は、一覧から外した**（1 行 28px では見分けられないため。要求も減らせる）。サムネイルは詳細のパネルのシリーズの並びに出す。
  - **0 件のとき**：表の枠と見出しの行を出し、表の中に「該当する検査はありません」を出す（一覧の場所が分かるように。2026-10-21 に、空の場所が真っ白だったのを直した）。「条件をクリア」は、絞り込みが既定でないときだけ出す。
- **自動更新**（2026-10-21 に承認者が決めた。それまでは、新しく届いた検査を出すには頁を読み直すしかなかった）
  - 一覧は `STUDY_LIST_REFRESH_SECONDS`（既定 30 秒。`0` で止める）ごとに、**一覧の版**（画面の API `GET /api/studies/version`。Orthanc の変更の記録の最後の番号 `/changes?last` の `Last`）を読み、**版が変わったときだけ**一覧（`/api/studies`）を読み直す。版は Orthanc の変更の記録の番号なので、検査・シリーズの追加と削除のほか、画像の 1 枚ごとの受信、検査やシリーズが落ち着いたこと（`StableStudy` など）、送信などのジョブ、メタデータの更新でも進む。受信が続く間は、ほぼ間隔ごとに一覧を読み直す。
  - 版だけを読む理由：一覧の読み直しは、Orthanc へ検査の検索（上限 1000 件。検査日の件数のための検索も足すと 2 回。検査が上限を超えると、検査日の範囲で区切るので、1 回の検索が数回の問い合わせになる）を求め、返した検査の組を監査の記録（`search`）に残す。版を挟まずに間隔ごとに一覧を読み直すと、受信が無い間も画面を開いているだけで、1 台あたり 1 日に約 2,900 回の検索と同じ数の監査の行（1 行に最大 1000 件の組）が積もる。版を挟むと、Orthanc に変化が無い間（夜間など）は読み直さない。受信が続く日中は、版を挟まない形とほぼ同じ回数を読み直す。版は患者の情報を含まないので、読めたことは監査の記録に残さない（権限で断ったものは残す）。
  - 自動更新の読み直しは、一覧の要求に `refresh=auto` を付け、監査の記録（`search`）の `detail` に `trigger: "auto"` を残す（利用者が絞り込み・開き直しで求めた検索と分けて追えるように。2026-10-21 の独立レビューの指摘）。返した検査の組は、これまでどおり残す（画面に出した患者の情報なので省かない）。`refresh=auto` はブラウザが付ける名乗りなので、監査を名乗りで薄めない（3.6 の「監査の記録」）。
  - 基準の版は、頁を描くときに一覧を取る**前**に読む（間に入った検査は、次の版の読み取りで拾う）。読めなければ、画面が最初に読んだ版を基準にする。
  - 読み直しても、選んだ行・開いている詳細・スクロールの位置は保つ。詳細は読み直さない（「詳細を開いた」の記録を増やさない）。スクロールしているときは、見えている先頭の行が同じ高さに来るように戻す（新しい検査が上に足されても、見ていた行が動かない）。いちばん上にいるときは保たない（新しい検査が上に出て、目に入る）。
  - 自動更新の読み直しには、待ちの印（細い帯・薄い行・件数の「—」）を出さない。件数の横に「自動更新（30秒）」を出し、版を読めないときは「自動更新：接続できません」にする。
  - ブラウザのタブを隠している間は読まず、戻ったらすぐ読む。版の読み取りは画面の操作ではないので、画面のロックまでの時間は数え直さない（ロック中は 423 で止まる）。
- **受付番号の列とバーコード**（段 8）
  - **受付番号の列**：一覧に受付番号（AccessionNumber）の列を足し、受付番号で絞れるようにする（列と詳細条件の受付番号は、2026-10-21 に前倒しして入れた。横断の検索の対象にはすでに含めている。検索の語の当て方は、下の「段 2 の実装の決まり」と同じ）。受付番号は許可の一覧（原則 8）の項目で、載っていない役割には列も検索の対象も出さない。オーダとの照合は、ワークリスト（3.8）のときに考える。ここでは照合しない。
  - **バーコードの読み取り機で絞る**：読み取り機はキーボードとして働き、読んだ文字を打ち込んで最後に Enter を送る。患者 ID・受付番号の読み取りで、横断の検索の欄から一覧を絞れることを試験で確かめる。新しく作る部品はほぼ無く、段 2 の範囲の確かめにあたる。確かめる点は次のとおり。
    - 読み取り機の入力は人の打鍵よりずっと速い。入力の途中の文字で何度も検索を送らず、止まった値か Enter で絞る。
    - 前後の空白・改行・Tab を除いてから比べる。
    - 全角で入っても、横断の検索の NFKC の正規化で同じに絞れる。
    - 試験では、読み取り機の代わりにキーを素早く送って確かめる（実機は必須にしない）。
- **URL で直に開く**（段 8）：電子カルテなど外の仕組みから起動するために、決まった形の URL で一覧・詳細を開けるようにする。
  - **形**：患者 ID・受付番号・検査の UID（StudyInstanceUID）を、それぞれ決まったパラメーターで渡す（`patientId`・`accession`・`studyUid`）。患者 ID か受付番号を渡すと、その値で絞った一覧を開く。`studyUid` を渡すと、その検査を選んだ状態で詳細を開く。パスとパラメーターの正確な名前は、作る段で決める。
  - **ログインと監査の記録はそのまま効く。** ログインしていなければログインの頁へ送り、ログインし終えたら元の URL へ戻す。戻り先は、このアプリの中の決まった形の相対パスだけを受け、外の URL・別のオリジンは受けない。画面のロック中は、ロックを解いてから開く。URL で開いても、検索（`search`）・詳細を開いた（`view_study`）の記録は、画面から開いたときと同じに残る。役割の許可の一覧（原則 8）も、画面から開いたときと同じく適用する。
  - **外の仕組みへ送る道は持たない。** 受けるだけで、このアプリから外の仕組みへ結果を返す道・呼び戻す道は作らない。
  - **URL の値は信用しない。** 値の形を確かめ（患者 ID・受付番号：制御文字を含まない 64 文字以内。UID：数字と `.` だけ、64 文字以内）、合わなければ絞らずに誤りを示す。画面に出すときはエスケープする（React の既定の出力のまま、HTML として解釈しない）。Orthanc への検索には、値を文字列としてつなげず、パラメーターとして渡す。
  - **残る点**：URL に患者 ID が入るので、ブラウザの履歴・リバースプロキシのログに残る。外へ送られる参照元の情報（Referer）は止める。ブラウザの履歴とプロキシのログの扱いは、施設の運用で決める。
  - 外の仕組みからの起動は、ログインの手間を減らす外部の認証（`AUTH_MODE=oidc`。後ろ）と一緒に使うことが多い。段 8 では、ローカルのログイン（`AUTH_MODE=local`）の戻り先だけを作り、外部の認証の流れは、その認証を作るときに合わせる。
- **上下に分ける形**：頁全体は画面の高さに収め（頁そのものはスクロールさせない）、上に絞り込みと検査の一覧（一覧の中だけでスクロール）、下に選んだ検査の詳細のパネルを置く。行の下に詳細を開く形はとらない。
  - 理由：確かめた範囲では、国内の製品に定まった作法は見つからなかった。一覧の読みやすさと、行が動かずちらつかないことを優先して、上下に分けた。
  - 境目は上下に動かせる（WAI-ARIA の separator。矢印の上下・Home・End、ドラッグ）。位置は上の高さの百分率（20〜80%、既定 60%）で、ブラウザの localStorage に覚える（サーバーの利用者の設定には持たない）。
  - 行を選んでも一覧の行は動かない。矢印の上下で行を移すと、詳細が付いて替わり、選んだ行は一覧の見える所にスクロールする。Enter か行のダブルクリックで既定のビューアを開く。Escape で選びを外す。何も選んでいないときの下の場所は、短い案内だけを出す。
  - 「詳細を開いた」監査の記録（`view_study`）は、詳細を実際に読んだときだけ残す。行のクリックはすぐ読む。矢印で移すときは、止まって 300 ミリ秒たった行だけを読む（通り過ぎた行は読まない）。詳細の中身（シリーズの並びなど）は、そのときの読み込みが終わってからでないと出さない（キャッシュの中身は出さず、A→B→A と戻っても、止まってから読み直して記録する）。
  - 上の場所は、絞り込みの高さに一覧の最小の高さ（見出しと 7 行ほど。224px）を足した高さより縮まない。低い画面では境目の動く範囲がその分だけ狭まり、詳細の場所が先に縮む。
  - 狭い画面（幅 768px 未満）では、上下に分けず一覧だけを出し、行を選ぶと詳細を一覧の上に重ねて出す（閉じるボタンあり）。開いたら詳細へフォーカスを移し、背後の一覧は操作できなくし（`inert`）、閉じる（ボタン・Escape）と元の行へフォーカスを戻す。
  - 縦のスクロールバーが出入りしても、画面が左右に寄らない（`scrollbar-gutter: stable`）。
- **詳細のパネル**（選んだ行に付いて、動きの遅れ無しに替わる）
  - **業務で毎回見る値は見出し（患者バナー）に常に出し、詳細の下に「UID」と「DICOM タグ」の開け閉めのボタンは置かない**（2026-10-20 に、「すべての項目」を開け閉めする形から直した。2026-10-24 に、「UID」「DICOM タグ」のボタンもやめた。#57）。StudyInstanceUID はバナーの下の 1 行、SeriesInstanceUID は画像の場所の見出しに出し、DICOM タグは画像の場所の切り替えで見る。同じ情報の入口を 1 つにするため。
  - **見出しは患者バナー（3 製品で共通。docs/design-system/components.md）とその下の UID の 1 行**（2026-10-25 に、氏名などを数行に並べる形から替えた）：バナーに、氏名（漢字・太字）とその下のかな、患者 ID・生年月日と年齢・性別・受付番号・検査日時・モダリティと検査名を並べ、UID の行に StudyInstanceUID（コピーのボタンつき）を出す。右にビューアの部品と、役割に許された PACS の操作（送信・エクスポート・削除など。3.4・3.5）。値は `…` で切らず、折り返す。
    - 値の無い項目は、項目ごと省く（バナーを短くする）。例外は受付番号で、無いときも「受付番号 —」を出す（無いこと自体が、照合の手がかりになるため）。
    - 英字氏名・生年月日の和暦・紹介医・Study ID・シリーズ数と画像数は、バナーに足さず、下のタブ「検査の情報」に置く（値の無い項目は出さない。出す項目が 1 つも無ければ、タブを出さずシリーズだけを出す）。
    - 見出しの左に、選んだ行と同じ縦線を付けて、どの行の詳細かを示す。
  - その下に、タブ「シリーズ」「検査の情報」（左右の矢印のキーで移る。選んでいないタブの中身も描いておき、開いた画像の場所などの状態を切り替えても失わない）。「シリーズ」には、**シリーズのサムネイルを横に 1 列**（横にスクロール。キーボードでもフォーカスを受ける。まわりだけ暗い地）。シリーズごとに、サムネイル・番号とシリーズ名・モダリティと部位と画像数を出す。
  - 下に「UID」「DICOM タグ」の開け閉めのボタンは置かない（2026-10-24。サムネイルから開く画像の場所と役割が重なっていた。#57）。ブラウザの localStorage に覚えていた「UID」の開閉も、無くなった。
  - **画像の場所の「検査のタグ」は、検査単位（要約）の値だけを出す**（画像の場所のタグの切り替えは「主なタグ」「すべてのタグ」「検査のタグ」の3つ。切り替えの並びの位置は動かさない）。QIDO-RS の検査の検索（StudyInstanceUID と `includefield=all`）の1行。検査の単位にまとめた値で、どの画像の値かは分からない（2つの検査をまとめた検査のように、画像ごとに値が違うこともある）。中身の名前に「要約」と示す。画面の API は `GET /api/studies/{uid}/values`。画像ごとの値は、下のサムネイルから開く画像の場所で見る（同じ役目の場所を2つ持たない）。
  - **サムネイルを押すと、サムネイルの並びの下に、そのシリーズの画像の場所を開く**（すべての DICOM の値を見る権限のある役割だけ。権限の無い役割では、サムネイルをボタンにせず、絵のまま出す）。押したサムネイルは主の色の枠と `aria-pressed` で示す。別のサムネイルを押すとそのシリーズに替わり、同じサムネイルをもう一度押すと閉じる。行を替えると閉じる。画面は別の頁に移らない。
    - 左に画像の一覧（画像の番号の順。番号が無ければ SOPInstanceUID。複数フレームの画像はフレームの数を添える）、右に選んだ画像の SOPInstanceUID（コピーのボタン付き）とタグの表（タグ・タグ名・VR・値）。最初は先頭の画像を選ぶ。一覧は上下の矢印のキーで選ぶ画像を替える（キーで通り過ぎる画像の値は読まず、0.3 秒止まった画像の値を読む。クリックで選んだ画像はすぐ読む。読むたびに監査の記録に残るため）。タグの表は列の幅を決めておき、表を替えても列の境目を動かさない。タグの表は行を選べ（クリック・Shift・Ctrl／Cmd で複数。矢印のキーも）、選んだ行を、表の上の「コピー」・右クリックのメニュー・Ctrl／Cmd + C で、1 行 1 タグのタブ区切りにして写す（「全部の列」「タグと値」「値だけ」。写すのは画面に出ている値で、新しく読まないので、監査の記録は増えない。docs/design-system/components.md の「タグの表」）。日時の値は DICOM の値のまま出す（時間帯で直さない）。幅が 768px 未満のときは、一覧を上、表を下に重ねる。

    - 画像の一覧は BFF が QIDO-RS（`studies/{study}/series/{series}/instances`）で引き、画像の番号（InstanceNumber）の順に、選ぶのに要る値（SOPInstanceUID・SOPClassUID・画像の番号・フレームの数）だけを返す（`GET /api/studies/{uid}/series/{series}/instances`）。値は BFF が WADO-RS の `metadata`（`studies/{study}/series/{series}/instances/{sop}/metadata`）で読み、答えの3つの UID が求めたものと同じときだけ返す。主なタグは `GET /api/studies/{uid}/series/{series}/instances/{sop}/tags`（設定に無いタグは返さない。タグ名つき）、すべてのタグは `GET /api/studies/{uid}/series/{series}/instances/{sop}/values`。Orthanc の REST（`/instances/{id}/tags`）は使わない。
    - 値の出し方：
      - 値は文字として出す（HTML として解かない）。複数の値は `\` でつなぎ、人の名前は `Alphabetic=Ideographic=Phonetic` の形にする。
      - 日本語の値は、Orthanc が SpecificCharacterSet に従って Unicode に直した値をそのまま出す。BFF は文字コードを読み替えない（ISO 2022 IR 87 は結合の試験の 14 で確かめた）。
      - 1 つの値が 1024 文字を超えるときは、画面の API が先頭の 1024 文字と全体の文字数を返し、画面は「…（全 N 文字）」を添える。
      - バイナリの値（InlineBinary・BulkDataURI と、VR が OB・OD・OF・OL・OV・OW・UN のもの）は「（バイナリ）」とし、中身を読みに行かない。シーケンスは「（シーケンス N 件）」とする。
    - タグ名は日本語で出す（2.2 の「タグ名」の表。表に無いタグ・私的タグは空）。訳は公開の資料（[標準DICOM画像タグセット一覧](https://www.liberworks.co.jp/know/know_dicomTag.html)・[DICOM用語集](https://ja.sonicdicom.com/dicom-glossary/)）を参考にし、2.2 の用語集の言葉があればそれを使う。
  - 検査単位・画像の一覧・主なタグ・すべてのタグは、どれも読み取りだけで、同じ権限（すべての DICOM の値を見る。`dicom.all_values`）のときだけ使え、断ったものも含めて監査の記録（`view_study`。`detail` に `level`・SeriesInstanceUID・SOPInstanceUID と、画像の値では出したタグの組 `set`：`configured`・`all`）に残す。画像サーバーへは BFF が求め、中継（3.2）の道は足さない（中継は QIDO-RS を通さない決まりのまま）。
  - StudyInstanceUID は見出しの 3 行目、SeriesInstanceUID は画像の場所の見出しに、行の幅いっぱいに折り返して 0.75rem・等幅・控えめの色で出し、コピーのボタンを UID のすぐ右に付ける（行の右端には離さない。UID の値を押しても写せる。写したら値の地を一瞬光らせ「コピーしました」を出す）。色はラベルの色（明るい地 `#5f5f5f`・暗い地 `#a3a3a3`）にする（`#777` は白い地で 4.48:1、`#121417` の上で 4.12:1 で、2 の AA に届かないため。段 2）。
- **段 2 の実装の決まり**
  - 一覧の既定の検査日は「すべて」（段 1 の一覧と同じ見え方。検査日の新しい順に上限 1000 件まで。集め方は 3.1 の「上限に届いたとき」）。絞り込みの値は頁の URL（`?date=…&modality=…&q=…`）に持つ。「今日」はサーバーの時間帯（`TZ`）で数え、「過去7日」は今日を含む7日。
  - 検査日の絞り込みは Orthanc への QIDO-RS の `StudyDate` の範囲で求め、詳細条件は QIDO-RS の `PatientBirthDate`・`PatientSex`・`AccessionNumber`・`StudyDescription` で求める（2026-10-21）。モダリティ・横断の検索は BFF で、許可の一覧で絞った後の項目に当てる（許可されていない項目では探せない）。横断の検索は NFKC・小文字・カタカナをひらがなに・空白を除いてから比べる。
  - シリーズのサムネイルは、BFF の中継の WADO-RS の `thumbnail`（`…/series/{uid}/thumbnail`）を、詳細のパネルから取る（取得は監査の記録に残る）。取れなければ印だけを出す。一覧の行では取らない（検査ごとの `studies/{uid}/thumbnail` は、一覧のサムネイルの列を外したので使わない）。
  - 詳細を開いたことは `view_study`、ビューアで開いたことは `open_viewer` に残す。段 2 で作った検査の状態の印（検像・読影・緊急は検査ごと、ブックマークは利用者ごと）の道は段 3 で外した（表は migration `20261020000000_remove_study_state` で外し、ビューアの覚えは `StudyViewer` に移した）。監査の記録の名前 `study_state` は、検査ごとのビューアの覚え（`detail` の `flag` は `viewer`）に使い続ける。記録済みの状態の印の行は、監査の記録の追記だけの決まりのため消さずに残る。

### 3.2 ビューアの選び分けと記憶
- **ビューアの部品（ViewerAdapter）**：設定で URL が与えられたもの（Weasis は `VIEWER_WEASIS_ENABLED=true` のとき）だけを出す。
  - `ohif`：OHIF Viewer v3（CT・MR の多断面・過去との比較）
  - `stone`：Stone Web Viewer（単純 X 線・超音波の速い表示）
  - `volview`：VolView（3D の表示）
  - `weasis`：Weasis（`weasis://`。手元のアプリ。DICOMweb で開く。**後ろ**）
  - `dicomweb`：研究の道具（3D Slicer など）に渡す DICOMweb の URL のコピー
- **ビューアが画像を取る道**：基本は **BFF の中継**（`/api/dicom-web/...`）を通す。
  - 中継が通すのは **WADO-RS の読み取り（GET・HEAD）だけ**：検査・シリーズ・画像の取得と、その `metadata`・`rendered`・`thumbnail`・`frames`・大きな値（bulk data）。**検索（QIDO-RS）は返さない**（検索は画面の API を通し、原則 8 の許可の一覧の対象にする）。**中継には書き込み（STOW-RS など）の道を作らない**（POST・PUT・PATCH・DELETE は 405 で断り、断ったことを記録する）。PACS の書き込みの操作は、操作ごとの画面の API（3.4・3.5）で行う。
  - **画像サーバーへ渡す Accept**：`thumbnail`・`rendered`（path の最後の段）は **BFF が決める**。既定は `image/jpeg`、ブラウザが `image/png` を名指し（q が 0 より大きい）し、`image/jpeg` を名指ししていないときだけ `image/png`。ブラウザの `<img>` の Accept（`image/avif,…` とワイルドカード）をそのまま渡すと、Orthanc の DICOMweb のプラグインが 400（Unsupported MIME type）を返すため（結合の試験で実測）。それ以外（`metadata`・`frames`・bulk data などビューアの取得）は **ブラウザの Accept をそのまま渡す**。モックも、`thumbnail`・`rendered` では `image/jpeg`・`image/png` 以外の Accept に 400 を返し、`image/png` には PNG、`image/jpeg` には JPEG を返す（求めた型と違う型を返さない）。
  - **規格に合わない Accept は、画像サーバーへ渡さずに断る**（PS3.18 8.7.5。2026-10-21 の規格の監査で足した。断ったことも監査の記録に残す）。
    - Accept の無い `thumbnail`・`rendered` の要求は **406**（規格は Accept の無い要求をすべて 406 とする。ブラウザの `<img>`・`fetch` はいつも Accept を付けるので、BFF が型を決める `thumbnail`・`rendered` の道にだけ当てる。ビューアの取得の道は、これまでどおり画像サーバーの答えをそのまま返す）。
    - DICOM の型（`application/dicom`・`application/dicom+json`・`application/dicom+xml`・`multipart/related`・`application/octet-stream`。PS3.18 8.7.3）と、画像などに変換した型（rendered media type。`image/*`・`video/*`・`text/*`・`application/pdf`。8.7.4）が混じった Accept は **400**（q=0 の型は数えない）。
    - query の `accept`（PS3.18 8.3.3.1 の Accept Query Parameter）は、画像サーバーへ渡さない。受け取る型は、上の決め方の Accept のヘッダーだけで求める（BFF が確かめていない型の答えを中継しない）。
  - 中継は、利用者のセッションで認可し（ログインしていなければ 401、画面のロック中は 423、役割に画像の取得が無ければ 403。段 1b）、取得のたびに監査の記録に残す（誰が・いつ・どの検査の・何を。画像サーバーの答えが出てから結果つきで残し、記録に失敗したら画像を渡さない）。画像サーバーの資格情報はサーバーの側で付け、ブラウザに渡さない。
  - これは、研究用の画像の集め先の前にこのアプリを置く使い方の要望（ビューアの取得も BFF を通す・読み取りだけ・セッションで認可・監査に残す）とそろえたもの。
  - **ブラウザが画像サーバーを直に開く形は、既定にしない。** BFF の認可と監査の外になり、画像サーバーの資格情報か別の認証をブラウザの側に持たせることになるため。研究の道具に渡す `PUBLIC_DICOMWEB_URL`（コピー用）は、画像サーバーの側で認証と記録を持つ施設のための別の道として残し、画面では「操作ログの対象外」と示す（段 2。画面の言葉は 2026-10-20 に 2.2 の用語集に合わせた）。
  - **未決（段 2 で決める）**：ビューアによっては、検査の中のシリーズ・画像を探す QIDO-RS（`studies/{uid}/series` など）を使う。これを中継に足すか（足すなら許可の一覧の対象にする）、ビューアを WADO-RS の `metadata` だけで開く設定にするかは、ビューアごとに実測してから決める。
- **段 2 の実装**：開くのは BFF の `/api/viewers/open`（どの検査をどのビューアで開いたかを記録してから、ビューアの URL へ移す）。ビューアの URL の形は `src/lib/viewers.ts`（OHIF は `/viewer?StudyInstanceUIDs=`、Stone は `/index.html?study=`、VolView は `?urls=[中継の検査の URL]`）。ビューアが BFF の中継から画像を取るのは、ビューアの側の設定（データの取り先を `/api/dicom-web` にする）。DICOMweb の URL のコピー（`PUBLIC_DICOMWEB_URL`）は、▾ の中で「操作ログの対象外」と示す。Weasis は後ろなので、まだ出さない。
  - 上の**未決**（ビューアが使う QIDO-RS を中継に足すか）は、段 2 ではモックで分かる範囲だけを確かめ、決めていない。中継はこれまでどおり QIDO-RS を返さない。実のビューアと実の Orthanc で、どの要求が出るかを測ってから決める（段 2 の PR に、確かめることとして残した）。
- **選び方の3段**
  1. **その場で選ぶ**：行の `[▶ 開く | ▾]` から、ビューアを選んで別のタブで開く。詳細のパネルのシリーズからも開ける。
  2. **検査ごとに覚える**：「この検査は VolView で開く」を StudyInstanceUID ごとに保存。行に `[この検査: VolView]` を出し、ダブルクリックでそれを開く。
  3. **モダリティごとの既定**：覚えが無い検査は、モダリティの既定（例：CT・MR は OHIF、CR・DX・US は Stone）で開く。既定は管理の画面で変える。

### 3.3 受け取ったものを見る・機器・保管の状態
画像を受ける（C-STORE を受ける）のは Orthanc の仕事。tsunagi-dicom は、**受け取ったことが分かる画面**と、受け元・送り先の機器の一覧、つながるかの確かめを持つ。どれも Orthanc から読むか、Orthanc に確かめさせるだけで、BFF に写して持たない（原則 10）。

- **受け取りの記録**（段 4）：Orthanc が受け取った検査を、新しい順に並べる（上限 100 件。数は作る段で決め直してよい）。1 行に、いつ（受け取った時刻）・どの機器から（呼んできた AE タイトル。登録した機器と合えば、その名前も）・何件（画像の数）・どの検査か（患者 ID・氏名・検査日・モダリティ・検査の記述。許可の一覧で絞る）を出す。行から、その検査の詳細のパネルへ移れる。
  - **読む元**：Orthanc の変更の記録（`/changes`。新しい検査・新しい画像・検査が落ち着いた（`StableStudy`）の出来事に、時刻と続き番号が付く）と、画像（インスタンス）のメタデータの `RemoteAET`（C-STORE で送ってきた側の AE タイトル）。どちらも Orthanc Book（REST API の「Tracking changes」、「Terminology of advanced features」の Metadata の節。2026-10-19 22:45 に本文を取り出して読んだ）で確かめた。REST で入ったか DICOM で入ったか（`Origin`）・受け取った時刻（`ReceptionDate`）・呼ばれた側の AE タイトル（`CalledAET`）などのほかのメタデータは、Orthanc の版で実測してから使う（Lua の `OnStoredInstance` の `origin` には `RequestOrigin`・`RemoteAet`・`CalledAet`・`RemoteIp` があると Orthanc Book の Lua の頁にある）。
  - 変更の記録は Orthanc の中で数に限りがあり、古い出来事は残らないことがある。受け取りの全部の記録の正本は Orthanc とその記録で、tsunagi-dicom の画面は「いまの Orthanc から読める範囲」を見せるものと示す。
  - 開いたことは監査の記録（`receive_log`）に残す。返した検査の患者 ID と StudyInstanceUID の組を、検索の記録と同じ形で残す。
  - **段 4 の実装**：頁は `/received`、画面の API は `GET /api/receive-log`（役割の操作 `receive.view`）。BFF は `/changes?last` で最後の番号を読み、その 5000 件前を `since` にして、Orthanc Book の追い方（答えの `Last` を次の `since` にし、`Done` まで読む。1 回に 100 件を求める）で読み切る。Orthanc が 1 回に返す数を切り詰めても、区間の中は抜けない。読む範囲の前にも記録があり、受け取りの検査が上限の数に届かなかったとき（直近の変更が受け取りの検査のほかの出来事で埋まったときなど）と、読む回数の上限（200 回）に届いたとき、`Done` でないのに空の頁か `Last` が進まない答えが来たとき（そこで読むのを止める）は、画面に一部を読み込めなかったことを出す（読み切ったとするのは `Done` の答えのときだけ）（API の `complete` が `false`）。検査ごとに `/studies/{id}`・`/studies/{id}/series`・最初の画像の `/instances/{id}/metadata?expand` を読む。行の「検査一覧で表示」は、患者 ID で絞った検査の一覧へ移す（決まった URL で直に開く形は段 8。移り先で検査を選ぶことは、下の「件数が多いときの使いやすさ」）。REST で入った検査（`Origin` が `RestApi`）には「インポート」の印を出す（`Origin` の名前は実測の前の想定）。返す項目は許可の一覧の `receive`（`receivedAt`・`remoteAet`・`origin`・`receivedInstances`）と `study`。
  - **時刻**：受信の時刻は、サーバーの時間帯（`TZ`）で `yyyy/MM/dd HH:mm:ss` の形に出す（2.2）。Orthanc の変更の記録の `Date` は UTC で、時間帯の印の無い `YYYYMMDDTHHMMSS` の形で来る（2026-10-20 に、画面で UTC のまま出ていたのを承認者が見つけた）。BFF は UTC として読み、画面の API の `receivedAt` は UTC と分かる形（ISO 8601 の `Z` つき）で返す。頁はサーバーで描くときに `TZ` の時刻に直す。
  - 頁の見出しの横の補いは「直近 100 件」だけにする（2.2）。
  - **件数が多いときの使いやすさ**（2026-10-21。承認者が「表示が文字のリンクで、移っても検査が選ばれていない。不親切」と指摘した）
    - 「検査一覧で表示」は、ボタンの形のリンクにする（頁の移動なのでリンクのまま。2.3）。押すと、患者 ID で絞った検査一覧を、その検査を選んだ形（詳細のパネルを開き、一覧の中でその行が見える位置で、行にフォーカス）で開く。移り先の URL は `/?q=<患者ID>&studyUid=<StudyInstanceUID>`。`studyUid` は UID の形（数字と `.`、64 字まで）を確かめ、最初の一覧にある検査のときだけ選ぶ。選ぶと、行をクリックしたときと同じく詳細を読み、「詳細を開いた」（`view_study`）を記録する。`studyUid` は開いた後に URL から外す（開き直すと選ばない一覧）。段 8 の「URL で直に開く」で名前を決めるときは、この名前を出発点にする（外の仕組みからの起動・ログインの後の戻り先は段 8）。
    - 絞り込み：送信元 AE（読んだ行にある AE タイトルと「インポート」から選ぶ）と、検索（患者ID・氏名（漢字・かな）・検査名。検査一覧の横断の検索と同じ比べ方）。読んだ範囲（直近 100 件）の中で、画面で絞る（Orthanc へは求め直さない）。件数は「3／100 件」の形で出す。
    - 新着の印：前にこの頁を開いたとき（このブラウザ）より後に受信した行に「新着」を付け、「新着のみ」で絞れる。前に見た受信日時はブラウザの localStorage に覚える（境目の位置と同じ。サーバーの利用者の設定には持たない。初めて開いたときと、覚えを読めないときは、新着の印を出さない）。頁を開いている間は基準を替えない。
    - 再読み込み：頁を読み直さずに、画面の API（`/api/receive-log`）から読み直す（開いたことは、これまでどおり操作ログに残る）。自動で読み直すことは、検査一覧の自動更新（一覧の版の API）が入った後に、同じ版を使って足す。
    - 頁送りは持たない。読む範囲が直近 100 件で、画面の中の絞り込みで足りるため。見出しの行は、表の中でスクロールしても上に残す。
- **機器の一覧**（段 4）：Orthanc に登録された機器（`/modalities?expand`）を出す。名前（Orthanc の中の ID）と AE タイトルは、送る操作の役割に出す。住所（Host・Port）と、機器ごとの許可（`AllowEcho` など）は、機器の管理の役割にだけ返す（原則 8）。
  - **段 4 の実装**：頁は `/modalities`、画面の API は `GET /api/modalities`（役割の操作 `modality.check`）。返す項目は許可の一覧の `modality`（既定では、管理者に `id`・`aet`・`host`・`port`・`manufacturer`・`allowEcho`・`allowStore`、ほかの役割に `id`・`aet`）。
- **つながるかの確かめ**（段 4）：機器を選んで「接続確認」を押すと、Orthanc から機器へ C-ECHO を送る（`POST /modalities/{id}/echo`、本文に `{"Timeout": 10}`。Orthanc 1.7.0 からは本文の JSON が要る）。結果（成功・失敗と、確かめた時刻）を出し、監査の記録（`echo`）に残す。
  - **段 4 の実装**：画面の API は `POST /api/modalities/{id}/echo`（`modality.check`。Orthanc の中身は変えないが、Orthanc に機器への通信をさせるので CSRF を確かめる）。機器の名前は英数字と `_` `.` `-` の 64 字までだけを受ける。
- **保管の状態**（段 7）：Orthanc の件数と容量（`/statistics`：患者・検査・シリーズ・画像の数と使っている容量）、Orthanc の版（`/system`）、最近の仕事（`/jobs`：送る・書き出しなどの状態）を出す。容量の警告（80%・90%）は、施設が容量の上限を設定で渡したときだけ出す。
- **機器の登録**（段 7）：機器を足す・直す・外す（`PUT`・`DELETE /modalities/{id}`）。管理者だけ、再認証の後。Orthanc の既定では、REST で変えた機器は Orthanc の記憶の中だけにあり、再起動で消える（Orthanc の設定 `DicomModalitiesInDatabase` を `true` にすると残る）。画面にもこのことを示す。

### 3.4 ほかの機器へ送る（段 4）
- 詳細のパネルの「送信」から、登録された機器を選んで、検査をまるごと送る。Orthanc の C-STORE の送信（`POST /modalities/{id}/store`）を、非同期（本文に `"Synchronous": false`）で求め、Orthanc の仕事（job）の ID を受ける。
- **結果を見せる**：仕事の状態（`/jobs/{id}` の `State`：Pending・Running・Success・Failure・Paused・Retry と、`Progress`・`ErrorCode`・`ErrorDescription`）を、終わるまで数秒ごとに読んで出す。返すのは状態・進み・誤りの番号と文言・始めと終わりの時刻だけにする（仕事の中身の `Content` はそのまま返さない。原則 8）。
  - 仕事の ID は、BFF が求めた送信のものだけを読めるようにする（ほかの仕事を、ID を替えて覗けないように）。**段 4 で決めた形**：BFF が仕事の ID・要求の ID・検査・送り先・送った利用者・期限（24 時間）を、`SESSION_SECRET` から HKDF で導いた鍵の AES-256-GCM で暗号化した token にして画面へ渡し、読むとき（`GET /api/jobs/{token}`）に、書き換えられていないこと・期限・利用者を確かめる（BFF のデータベースに写さずに済む。token は URL に入るが、中身の UID・利用者名は読めない）。書き換えた token・期限の過ぎた token・ほかの利用者の token は 404。`SESSION_SECRET` を替えると、それまでの token は読めなくなる（送った結果は監査の記録と Orthanc の仕事の記録に残る）。
  - **段 4 の実装**：画面の API は `POST /api/studies/{uid}/send`（本文は `modality` と `requestId`。役割の操作 `study.send`）。答えは 202 と `outcome`（`accepted`：仕事を受けた・`unknown`：結果不明・`failed`：Orthanc が断った）。同じ要求の ID の結果は `GET /api/studies/{uid}/send?requestId=…` で、送り直さずに確かめる。要求の ID は、同じ操作の直近 7 日の記録の中から探す（索引 `action`・`occurredAt`）。同じ要求の ID で別の検査・別の送り先・別の利用者を求めると 409。断った行（役割・検証モード）は「求めた」と数えない。**結果不明の送信があるうちは、同じ検査を同じ送り先へ、新しい要求の ID でも送らない**（BFF が 409 で断り、断ったことを記録する。画面も、結果不明の間は「送信」を押せない）。仕事の ID が分かっていれば、仕事の状態を読んで照らす。仕事の ID も分からないものは、管理者が送り先（受け取る側の記録）で届いたかを確かめ、確かめた内容と結果を記録に足す（`POST /api/studies/{uid}/send/resolve`。役割の操作 `pacs.reconcile`。Orthanc には何も求めない）。照らすまで、同じ検査を同じ送り先へは送れない。
  - Orthanc が受けなかったと確かめられない答え（時間切れ・接続の切れ・手前の入口の 502・503・504・移す答え（3xx）・答えに仕事の ID が無い）は、どれも結果不明にする。Orthanc が断ったと分かる答え（400・404・500 など）だけを失敗にする。
- **確かめの画面**：送る前に、検査（患者 ID・氏名・検査日・モダリティ・画像の数）と送り先（機器の名前・AE タイトル）を2行の表に並べ、「送信する」を押して始める。
- **送った後**：送信を受け付けたら、同じ確かめの画面から重ねて送らない（実行のボタンを外し、「閉じる」だけを出す）。続けて送るときは、送信先を選び直す（新しい要求の ID になる）。結果には、状態（2.2 の送信の状態）・送信先・時刻を出し、送信完了は印つきで示す（2.3。2026-10-20 に、送った後も「送る」が押せるまま残っていたのを直した）。
- **送信の手応え**（2026-10-21。承認者が「押した直後に反応が分からない」「もう一度送る導線が無い」「送っている間に閉じたらどうなるか分からない」と指摘した）
  - 「送信する」を押した直後から、状態の枠（待ちの印・送信先・流れる進みの帯）を出す。待ちの表示の 0.3 秒の遅れ（2.3）は、この枠には当てない（押したことが分からなくなるため）。
  - 送信を開始している間（Orthanc が受け付ける前）は「閉じる」を押せない。BFF や Orthanc に断られた（400・403・409 など）ときに、その知らせを画面に出すため（2026-10-21 の独立レビューの指摘。閉じられると、断られた送信がどこにも出なかった）。
  - Orthanc が受け付けた後の送っている間（受け付けた・待機中・送信中・一時停止中・再試行待ち）は、待ちの印と進みの帯（送信中は Orthanc の `Progress` の割合）を出し、「閉じる」の横に「閉じても送信は続きます」を出す。閉じても Orthanc の送信は続き、画面も状態を読み続ける。閉じた後は「送信」のボタンの横に、送信中・送信完了・送信失敗・結果不明を出す（開くと詳しい状態）。ジョブの状態を読めずに止まったとき（開くと「再読み込み」）は、送信中と見せずに「状態を取得できません」を出す。検査の行を替えると画面は状態を読むのをやめるが、Orthanc の送信は続く（結果は上の監査の記録と Orthanc の仕事の記録で確かめる）。
  - 送信完了は印つきの枠、送信失敗は誤りの色の枠に印と Orthanc の誤りの文言を出す。終わった後（送信完了・送信失敗・再送できると分かった照らし合わせの後）は「再送信…」を出す。押すと確かめの画面に戻り、「送信する」を押したときに新しい要求の ID で送る（自動では送り直さない。3.5）。
- 検査の UID から Orthanc の中の ID を引くのは `POST /tools/lookup`（答えの `Type` が `Study` のものだけを使う）。
- 送ったことは監査の記録（`send`）に残す（下の「書き込みの操作の共通の決まり」）。仕事の終わり（成功・失敗）は、BFF が初めて終わりを読んだときに記録する。画面を閉じて終わりを読まなかった送信の結果は、Orthanc の仕事の記録（数に限りがある）で確かめる。

### 3.5 PACS の書き込みの操作（書き出し・削除・取り込み・値の修正・結合と分割）
**書き込みの操作の共通の決まり**（段 4 から。送る操作にも当てる）：
- 役割の確かめ（3.6 の役割ごとにできる操作）を通す。断った要求も監査の記録に残す（`denied`）。
- 状態を変える要求は、これまでと同じ CSRF の対策（`Origin` と `x-csrf-token`）を通す。画面のロック中は 423。
- **Orthanc を呼ぶ前に「求めた」ことを監査の記録に残し、記録できなければ呼ばない。** 呼んだ後に、結果（成功・失敗と Orthanc の答えの要点）を残す。記録には、誰が・いつ・どの患者と検査に・何を（送り先・理由など）を入れる。
- **要求の ID**：画面は、書き込みの操作ごとに要求の ID（乱数の UUID）を付けて送る。BFF は、その ID を「求めた」の行と結果の行の両方に入れ、Orthanc の仕事（job）を作る操作では、仕事の ID も同じ行に入れる（記録の行と Orthanc の仕事を結ぶ）。
- **同じ要求を二度流さない**：BFF は、同じ要求の ID の「求めた」の行がもうあれば、Orthanc を呼び直さず、前の記録と、Orthanc から読んだいまの状態を返す（ボタンの二度押し・通信の切れた後の送り直しで、同じ操作が重ならない）。画面は書き込みの要求を自分で送り直さない。もう一度流すのは、利用者が結果を見てから、新しい要求（新しい ID）として選んだときだけ。
- **結果不明**：Orthanc を呼んだ後に、答えが来ない（時間切れ・通信の切れ）か、結果を記録できなかったときは、その要求を「結果不明」とする。結果の行に `unknown` として残し（記録できたとき）、画面には「結果不明」と、「状態を確認」のボタンと、要求の ID を出す（画面の言葉は 2.2）。成功とも失敗とも出さない。
- **照らし合わせ**：結果不明の要求は、BFF が Orthanc の状態を読んで照らし、分かった結果を記録に足す（要求の ID を入れた「照らした」の行）。照らすのは、同じ要求の ID で状態を求められたとき（画面が結果を読みに来たとき）と、管理者が記録から照らしを求めたとき。
  - 送る：仕事の ID が分かっていれば `/jobs/{id}` の状態を読む。仕事の ID も分からなければ、送り先の機器と検査で、自動では送り直さない（同じ検査を同じ機器へ二度送ると、受ける側によっては重なる。利用者が確かめてから新しい要求で送る）。
  - 削除・値の修正・結合と分割：**送り直さない。** 削除は、検査が Orthanc にまだあるかを読んで照らす（無ければ成功。まだあるだけでは失敗と確定しない。下の「削除」）。値の修正・結合と分割は、作られた検査を Orthanc で探して照らす（探し方は段 6・7 で Orthanc の版で実測して決める）。照らせないうちは、同じ検査への同じ操作を断り、管理者に照らしを求める。
  - **解いていない要求は、期限なしで止めになる。** 同じ検査の要求は、期間で切らずに探す（「求めた」の行と結果不明の行を、操作と検査の索引で引く）。何日たっても、照会・手で解く道から見え、解くまで同じ検査への同じ操作を断る（送るは同じ送り先へ、削除は同じ検査へ）。ほかの検査で同じ要求の ID が使われていないかは、直近 7 日だけを探す。
- 削除・値の修正・結合と分割・機器の登録は、大事な操作として**再認証**を求める（`REAUTH_MINUTES` の中。利用者の管理と同じ）。削除・値の修正・結合と分割の再認証はパスワードだけで、一度通れば `REAUTH_MINUTES`（既定 5 分）の間は聞き直さない。機器の登録はシステムの設定なので、利用者の管理と同じく TOTP も求める（3.6 の「再認証」）。
- `AUTH_MODE=dev`（モックだけ）では、`DEV_ALLOW_WRITE=true` のときだけ書き込みの操作を通す（4）。
- 決めた操作のほかは、Orthanc の書き込みの REST を呼ばない（呼ぶ道を作らない）。

**書き出し（ZIP）**（段 5）：
- 詳細のパネルの「エクスポート（ZIP）」で、検査の画像の全部を ZIP で落とす（Orthanc の `/studies/{id}/archive` を BFF が受けて、そのままブラウザへ流す）。落とす検査は、削除と同じく URL の StudyInstanceUID から引いたちょうど1件で、UID が合うものだけ。答えが始まるまでは 10 分を待ち、流す間は、次の塊が 2 分来なければ切る（全体の長さでは切らない）。
- ZIP は患者の情報を含んだまま施設の外へ持ち出せる形になる。Orthanc に求める前に「求めた」を監査の記録（`export`）に残し、記録できなければ渡さない（中継の取得と同じ）。結果は別の行に、流し終えた（成功・渡した大きさ）・Orthanc の側で途中で切れた・時間切れ（失敗・`interrupted`）・ブラウザの側で切った（失敗・`cancelled`）を分けて残し、要求の ID で結ぶ。流し始めた後は、結果を記録できなくても流れは止めない（BFF のログに残す）。ファイルの名前に患者の情報を入れない。
- 紹介の CD・DVD の形（DICOMDIR。`/studies/{id}/media`）は後ろ。

**削除**（段 5）：
- **管理者だけ。理由を必須にする**（前後の空白を除いて 1〜500 字。空は断る）。再認証の後（`AUTH_MODE=local`）。
- 確かめの画面：消す検査（患者 ID・氏名・検査日・モダリティ・シリーズ数と画像数）を並べ、「この操作は取り消せません」と示し、理由を書いてから「削除する」を押す（確かめの画面を開くボタンは「削除…」）。並べる値は、一覧の行の値ではなく、BFF が確かめの画面を開いたときに Orthanc から読み直した値にする（開いたことは `view_study` として記録する）。
- **違う検査を消さない。** 消す検査は、BFF が URL の StudyInstanceUID から Orthanc で引いたものだけにする。画面や本文から Orthanc の ID・患者 ID を受けない。
  - 引いた結果（`/tools/lookup` の Study）が**ちょうど1件**で、その検査（`/studies/{id}`）の StudyInstanceUID が求めた UID と一致することを確かめる。0件は 404、2件以上（患者違いで同じ UID の検査があるなど）と不一致は 409 で、消さずに断り、断ったことを記録する。2件以上のときは、送る・書き出しも、どれかを選ばずに 409 で断る。
  - 確かめの画面は、見せた検査の **Orthanc の中の ID・StudyInstanceUID・患者 ID・版**（Orthanc の `LastUpdate`）と、見せた利用者を、サーバーの秘密（`SESSION_SECRET` から用途ごとに導いた鍵。AES-256-GCM）で暗号化した **確かめの token**（期限 10 分）にして返す。画面は削除の要求に token を添える。token が無効（書き換え・期限切れ・別の利用者・別の UID）なら 409 で断る。
  - 消す前に読んだ検査が、token の中身の**全部**と一致するときだけ消す。どれかが違えば 409 で断り、違った項目の名前を記録する。Orthanc の中の ID は患者 ID と UID から作られる（Orthanc Book の「Orthanc identifiers」）ので、確かめの後に、同じ UID・同じ版の**別の患者の検査**に替わっても、ID と患者 ID で見分ける。版は、確かめの後に画像が足された・値が直されたのを見分ける。
  - 「求めた」を記録した後、Orthanc を呼ぶ直前に、もう一度引いて読み直し、token の中身と全部同じであることを確かめる。違えば消さずに、結果を失敗として記録する。
  - その後、`DELETE` を送る直前に、記録の並びの中で、自分の要求がまだ有効か（ほかで解かれていない・求めてから 2 分の中）を確かめ、「送る」の行（`dispatch`）を足してから送る。解かれていれば送らない（409）。2 分を過ぎていれば送らずに、失敗（`stale`）として記録する。
- Orthanc の `DELETE /studies/{id}` を呼ぶ。監査の記録（`delete`）に「誰が・いつ・どの検査を（患者 ID と StudyInstanceUID）・理由・版・Orthanc の中の ID・シリーズ数と画像数」を残す（消す前と、消した後の結果）。
- Orthanc の答えが来ない、502・503・504・3xx、結果を記録できないときは結果不明とし、送り直さない。画面が同じ要求の ID で状態を求めると、BFF は消したはずの検査（「求めた」の行に残した Orthanc の中の ID）が Orthanc にまだあるかを読む。無ければ消えたと記録する。
- **まだあるだけでは、「消えていない」と確定させない。** 先の `DELETE` が止まった・終わったと言える証拠が無く（BFF の時間切れの後も、Orthanc は消し続けることがある。`DELETE` は Orthanc の仕事（job）を作らないので、仕事の状態でも確かめられない）、新しい削除と重なりうるため。時間がたっても自動では確定させず、結果不明のまま返す（記録にも足さない）。
  - 解くのは、**管理者が手で解く操作**（`POST /api/studies/{uid}/delete/resolve`。役割の操作 `pacs.reconcile`）だけ。管理者は Orthanc の側（ログ・再起動の有無など）で、先の削除の処理が終わっていることを確かめ、確かめた内容（必須。500 字まで）を書いて解く。解けるのは、元の処理が `DELETE` を送った後（結果不明、または「送る」の行がある）か、「求めた」から 2 分を過ぎて「送る」の行が無い（もう送られない）ときだけ。「求めた」のまま動いている要求は解かない（409）。解くときに Orthanc をもう一度読み、検査が無ければ「消えた」、まだあれば「消えていない」として、確かめた内容とともに記録に足す（`manual`）。
  - 照らせる（状態を読む）のは、求めた本人と照らし合わせの役割（管理者）。
- 同じ検査の削除で、まだ結果の分からない要求（処理中・結果不明）があれば、新しい要求の ID でも 409 で断る（解くまで）。画面は、その要求を確かめる道と、管理者には解く道を出す。
- 消した検査の画像は Orthanc に残らない。戻すには、取り込み直すか、送り元から送り直す。
- **消した後**：消すと一覧から行が消え、詳細のパネルも閉じるので、消したことは一覧の上（件数の横）の知らせで示す（「検査を削除しました」と、患者 ID・検査日・モダリティ）。知らせは次の操作までか 10 秒残す（2.3。2026-10-20 に、消したことが画面に一度も出なかったのを直した）。
- 残る危うさ：Orthanc の `LastUpdate` は秒の単位なので、同じ秒の中の、同じ患者・同じ ID の検査の中身の変化は見分けられない。読み直しと `DELETE` の間に Orthanc で変わったものも見分けられない（Orthanc の REST に、版を条件にした削除が無い。「7. 既知の制約」）。

**取り込み**（段 6）：
- 画面から DICOM のファイルを落として、Orthanc へ入れる（`POST /instances`）。大きさの上限（`IMPORT_MAX_MB`）を超えたものと、DICOM でないもの（128 バイトの前置きの後に `DICM` が無いもの）は、Orthanc へ渡す前に断る。ZIP をほどいて入れるかは段 6 で決める。
- 取り込んだ検査は、一覧で「インポート」の印で分かる形で出す（画面の言葉は 2.2。画面ではこの操作を「インポート」と呼ぶ）。判別の元は、案 A：Orthanc のメタデータ（REST で入ったか DICOM で入ったか。上の `Origin`。実測してから）、案 B：取り込んだ時に Orthanc のラベル（1.12.0 から）を付ける。**推奨は A**（Orthanc に書き足さずに済む）。A が実測で使えなければ B にする。
- 取り込んだことは監査の記録（`import`）に残す（ファイルの数・大きさ・Orthanc の答え（新しく入った・もうあった）・入った検査）。
- マルウェアの検査は、このアプリでは行わない（施設が取り込む前に行う。第7.0版 8 遵守事項①）。
- 他の施設のデータを、自施設の患者 ID・氏名（漢字・かな・英字）・受付番号に書き換えて取り込む形は、下の「値の修正」と組み合わせて段 6 で決める。文字のコードは UTF-8（ISO_IR 192）にそろえる。

**患者・検査の値の修正**（段 6）：
- **一般と管理者**（3.6。2026-10-20 に、管理者だけから改めた）。理由を必須にし、再認証の後。直せる値は、患者（患者 ID・氏名（漢字・かな・英字に分けて直す）・生年月日・性別）と検査（検査の記述・受付番号・検査日）。
- Orthanc の `/studies/{id}/modify`（`Replace`。患者 ID を変えるときは `Force` が要る）で、直した検査を作る。
- **UID は新しくする（推奨）。** Orthanc の modify は、`Keep` で UID を保たなければ、新しい StudyInstanceUID・SeriesInstanceUID・SOPInstanceUID を作る。UID を保つと、中身の違う同じ UID の版が、送った先の機器と Orthanc の間に並びうるため。画面の値の修正には、UID を保つ形を持たない（HL7 による患者情報の更新だけは UID を保つ。下の項）。
- 元の検査が Orthanc に残るか（`KeepSource` に当たる扱い）は、段 6 で Orthanc の版で実測して決める。推奨は、直した検査を確かめてから、元の検査を削除の操作（理由つき）で消す形。どちらに決めても、**一般の要求では元の検査を必ず残す**（元を消すのは削除の操作で、管理者だけ。BFF は、一般の要求で元を消す指定を断る）。
- 監査の記録（`modify`）に、直した項目ごとの前と後の値、元と新しい StudyInstanceUID、理由を残す。

<a id="hl7-patient-update"></a>

**HL7 による患者情報の更新**（段の外。IHE の PIR を試すため。2026-10-24 に承認者が決めた。設計は `openspec/changes/add-hl7-patient-update-receiver/design.md`）：
- RIS が送る HL7 v2.3.1 の ADT^A40（患者の統合）・ADT^A08（患者の属性の更新）・ORM^O01 の NW（予約の知らせ）を受け、Orthanc の検査の患者 ID・氏名・生年月日・性別・受付番号を書き換える。RAD-13（ORM の CA・DC・XO）と HL7 v2.5.1 は扱わない。
- **待ち受けは別の小さなコンテナ（HL7 の受け口）に置き、BFF の公開の面に足さない。** MLLP には認証が無いので、受け口は開発の一式の内側だけで待ち受け、送り手の住所を許可の一覧で絞り、1 通の大きさ（1 MiB）と読む時間（30 秒）に上限を置く。配る compose には入れない。
- 受け口は中身を読まずに、BFF の内部の道（`/api/hl7/messages`。`HL7_RECEIVER_TOKEN_FILE` の token で受け口だけを通す）へ渡す。解析・Orthanc の書き換え・ACK（AA・AE・AR）・監査の記録は BFF が行う。この道は画面の利用者と別の機械の主体として扱い、役割には割り当てない。cookie を使わず token だけで通すので、CSRF の対策は当てない。`AUTH_MODE=dev` では `DEV_ALLOW_WRITE=true` のときだけ書き換える。
- **UID を保つ。** PIR では Study Instance UID が照合の鍵になるため。Orthanc の `/studies/{id}/modify` に `Keep`（Study・Series・SOP の UID）・`Force` を渡す。患者 ID が変わる A40 だけは `KeepSource: false` も渡し、元の検査を残さない（同じ UID の検査が 2 件並ぶと、引き当てが 409 になる）。患者 ID を変えない書き換え（A08・ORM）は、Orthanc の設定 `OverwriteInstances: true` で元の画像を置き換え、`KeepSource: false` は渡さない（渡すと、置き換えた画像ごと消える）。`OverwriteInstances: true` は（開発の一式と結合の試験の Orthanc だけで入れる。配る compose は変えない）。
- 旧い患者が Orthanc に無い A40・患者の無い A08・検査の無い ORM は、何もせずに AA を返す。ORM の患者 ID が検査と違うとき、別の受付番号がすでに入っているとき、A40 の替え先の患者がすでにあって属性が違うときは、書き換えずに AE を返す。患者 ID は、設定した 1 つの発番元のものだけを受ける。
- 同じ送り手・同じ MSH-10 のメッセージの送り直しには、Orthanc を呼ばずに前と同じ ACK を返す（古い更新で値を巻き戻さない）。書き換えは Orthanc の仕事として流し、終わった後に全部の画像の UID と値を確かめる。結果の分からない書き換え（仕事の終わりを読めない・画像の一部だけが書き換わった）は、次のメッセージの前に照らし、照らせなければ新しいメッセージに AE を返して止める。自動で照らせないものは、管理者が `/api/hl7/resolve` で確かめた内容を書いて解く（書き込みの操作の共通の決まりの「結果不明」「照らし合わせ」と同じ考え）。
- 監査の記録（`hl7`）に、断った接続・AR・Orthanc を呼ぶ前と後（前と後の値、元と新しい Orthanc の ID）を残す。外から来た値は、ログと記録の理由に出す前に、制御文字を見える形（`\uXXXX`）にする。

**結合・分割**（段 7）：
- 一般と管理者（3.6。2026-10-20 に、管理者だけから改めた）、理由を必須、再認証の後。Orthanc の `/studies/{id}/merge`（ほかの検査・シリーズをこの検査へ）と `/studies/{id}/split`（シリーズを新しい検査へ）を、確かめの画面を挟んで流す。どちらも UID を新しく作る（Orthanc Book の「Split/merge of DICOM studies」）。元を残すか（`KeepSource`）は、管理者だけが確かめの画面で選ぶ（既定は残す）。**一般の要求では元を必ず残し**、BFF は一般の要求の `KeepSource=false` を断る（元を消すのは削除と同じく管理者だけ。3.6）。

#### `AUTH_MODE=local` の決まり（段 1b）

- **最初の管理者**：利用者が1人もいないときだけ、起動の時に `INITIAL_ADMIN_USERNAME` と `INITIAL_ADMIN_PASSWORD_FILE`（秘密のファイル）から作る。利用者が1人でもいれば使わない（設定を残しても、パスワードを書き換えない）。作った管理者は、最初のログインで TOTP を登録し（`MFA_REQUIRED=true` のとき）、パスワードを本人のものに変える。
- **利用者**：利用者名（英小文字・数字・`.` `_` `-` の 3〜64 文字。作った後は変えない。監査の記録の「誰が」に使う）・表示の名前・役割・状態（有効・止めている）・最後のログイン。管理者が作るときに決めたパスワードは、最初のログインで本人が変える。**要らない利用者は消さずに止める**（監査の記録の「誰が」を後から追えるようにするため）。有効な管理者が1人もいなくなる変更（役割の変更・止める）は断る。
- **パスワード**：上の「パスワードの規則」。利用者名を含むものも断る。よくあるパスワードの一覧は `@zxcvbn-ts/language-common`（MIT）の一覧から、ほかの決まり（8 文字以上・英字と数字の混在）を満たす語だけを抜いて同梱する（`src/lib/auth/common-passwords.json`。作り方は `scripts/build-common-passwords.mjs`、ライセンスは同じ場所の `common-passwords.LICENSE.txt`）。ハッシュは argon2id（m=19 MiB・t=2・p=1）。いまの規則に合わなくなったパスワード（`MFA_REQUIRED` を `false` にしたときの 8〜12 文字など）は、次のログインで変える。
  - **ハッシュの強さ**：保存したハッシュの強さの値（記憶 8〜256 MiB・回数 1〜10・並び 1〜8・salt 8〜64 バイト・tag 16〜64 バイト）が範囲の外なら、確かめに回さず、合わないものとして扱う（壊れた・書き換えた行で、記憶と時間を使い切らせない）。いまの強さより弱いハッシュは、ログインに成功したとき（平文があるうち）に作り直す。作り直しはパスワードの変更ではないので、変更の時刻は変えない。同時にパスワードが変えられていたら書かない。
  - **同時に回す数**：argon2 は Node.js の libuv のスレッドの溜め（既定 4 本）で回るので、上限を置く。ログイン（まだ誰か分からない要求）の枠は、同時に `PASSWORD_HASH_CONCURRENCY` 本（既定 2）まで、待ちは `PASSWORD_HASH_QUEUE` 件（既定 32）まで。超えた要求は待たせずに **503 と `Retry-After`（5 秒）** で断る（下の「試みの遅らせ」で待たせる前にも見て、埋まっていればすぐ断る）。断った要求は、試みの枠を使わない（一時停止に数えない）。ログインした人の確かめ（ロックの解除・再認証・パスワードの変更・二要素が任意のときの登録・利用者を作る）は、ログインの枠とは別に取っておいた1本で回し、待ちもログインの待ちより先に通す（ログインの要求が溢れても、ロック中の職員は戻れる）。
- **二要素（TOTP）**：RFC 6238（HMAC-SHA1・6 桁・30 秒）。時計のずれのために前後1つの段まで受ける。使った段を利用者ごとに覚え、同じ段・前の段の使い回しを断る。ログインの TOTP の番号を1回間違えたら、その途中のセッションを捨てる（6 桁は総当たりされやすいので、次の番号を試すにはパスワードからログインし直す）。登録は QR（サーバーの側で描く）と、手で入れる秘密。`MFA_REQUIRED=true` では未登録の利用者はログインの途中で登録する。`false` では任意（自分の設定から登録でき、登録したら次からログインで要る）。登録を確かめて書くのは、まだ登録していないときだけ（もう登録してあれば 409。登録の途中のセッションを2つ開いて、後から登録済みの TOTP を上書きできないように）。登録できたら、その利用者のほかのセッションを閉じる。
  - **秘密の保存**：AES-256-GCM（認証のタグは 16 バイトだけを受ける）で暗号化して持つ。鍵は `SESSION_SECRET` から HKDF-SHA256 で導く（用途の名前で分ける）。別の秘密を足さないのは、施設が守る秘密のファイルを増やさないため。そのため **`SESSION_SECRET` を替えると、保存した TOTP の秘密は読めなくなり、管理者が TOTP をやり直す**（利用者は次のログインで登録し直す）。監査の記録のつなぎの鍵も替わるので、前の値を `SESSION_SECRET_PREVIOUS_FILE` に残さないと、前の鍵で書いた行を `/api/audit/verify` で確かめられなくなる（[`adr/0001-audit-chain-mac.md`](adr/0001-audit-chain-mac.md)）。
  - **回復の手段**：利用者が認証のアプリを失くしたときは、**管理者が「TOTP をやり直す」**（秘密を消し、その利用者のセッションを閉じ、次のログインで登録の段にする）。回復の符号（使い捨ての予備の番号）は持たない。**運用では管理者を2人以上置く**（互いに TOTP をやり直せるように）。
  - **未決（閉じた網で動かす形と一緒に決める。後ろ）**：管理者が1人だけで、その管理者が認証のアプリを失くしたときの道。案：起動の時に秘密のファイル（`INITIAL_ADMIN_PASSWORD_FILE` と同じ渡し方）で、名指しした1人の利用者の TOTP をやり直す（次のログインで登録の段にする）。使ったことを監査の記録に残し、使い終えたら設定から外す。閉じた網で動かす形・秘密をファイルで渡す形（後ろ）と一緒に決める。それまでは、管理者を2人以上置く。
- **ログインの一時停止**：`LOGIN_LOCK_THRESHOLD` 回続けて失敗したら（パスワード・TOTP・画面のロックを解く・再認証の失敗を同じに数える。画面のロックを解くパスワードの誤りも、TOTP を求めない既定のときを含めて数える）、`LOGIN_LOCK_MINUTES` 分ログインできない。時間が過ぎたら戻る（永久には止めない）。止めている間の試みは数えず、止める時間も延ばさない。一時停止にしたら、その利用者の**ログインの途中のセッションだけを閉じる。ログインし終えたセッションは閉じない**（ほかの人がその利用者名で失敗を重ねても、使っている職員を締め出さない）。一時停止の間は、パスワードを確かめる操作（画面のロックの解除・再認証・パスワードの変更・二要素が任意のときの TOTP の登録）を断る（画面のロック中のセッションはロックのまま残り、一時停止が解けたら同じセッションで解ける）。（2026-10-18 に承認者が決めた。）管理者は一時停止を解ける。失敗の文言は1つにして、利用者名の有無・一時停止の有無を答えの違いで知らせない。
  - **数え方**：確かめる前に、データベースの原子的な更新で「試みの枠」を1つ取る（失敗の数が決めた回数より少ないときだけ1つ増やす）。同時に多くの要求を送っても、枠を取れた要求だけが確かめに進むので、決めた回数より多くは試せない。パスワードが合ったら（TOTP が残っていても）枠を返し、ログイン・ロックの解除・再認証を終えたら数を0に戻す。ただし、TOTP を登録した利用者の、TOTP を確かめなかったロックの解除（既定）と再認証（2026-10-20 から TOTP を求めない）は、枠を返すだけで数を0に戻さない（下の「再認証」と「ロックを解く確かめ」）。
  - **総当たりの道**：ログインのパスワード・ログインの TOTP の番号・画面のロックの解除（パスワード。`SCREEN_UNLOCK_REQUIRE_TOTP=true` のときは TOTP も）・再認証・パスワードの変更のときのいまのパスワード（と TOTP）の5つの道の失敗を、どれも同じ数え上げに入れ、一時停止の間はどの道も確かめない。混んで断った要求（503）は、確かめる前に断るので、答えはパスワードが合っても違っても同じで、失敗に数えない（取った枠は返す）。503 を繰り返させても、確かめは1回も進まない。
- **試みの遅らせ**：利用者ごとの一時停止とは別に、ログイン（まだ誰か分からない要求）の回数を、1 分あたり**利用者名ごと**（`LOGIN_RATE_LIMIT_PER_MINUTE`。確かめた接続元があれば「利用者名×接続元」も）と**全体**（`LOGIN_RATE_LIMIT_GLOBAL_PER_MINUTE`）で数え、超えた試みは**断らずに、答えを返すのを指数的に遅らせる**（0.25 秒から倍に、最大 10 秒）。ほかの人が失敗を重ねても、正しい利用者が締め出されることは無い（遅くなるだけ）。締め出すのは利用者ごとの一時停止だけ（時間で解け、管理者が解け、監査に残る）。遅らせ始めたことは、1 分の枠ごとに1回記録に残す（利用者名は残さない）。
  - `X-Forwarded-For` のような偽れる値は鍵に使わない（信じるプロキシの設定ができるまで、確かめた接続元はいつも無い）。
  - 利用者名は正規化（NFKC・小文字・空白の除去）してから数える（ログインで利用者を引くときも同じ形にそろえる）。大文字小文字・空白・全角半角を変えても同じに数える。
  - 利用者名ごとの数は、SHA-256 で決まった数（4096）の桶に入れて持つ。存在しない利用者名を次々に使っても記憶は増えず、鍵を替えて逃げても全体の数で遅らせる。存在する名前と存在しない名前を同じ形で数え、遅れ方で有無を知られない（存在しない名前を1つの共通の鍵にまとめると、その鍵だけが混んで有無が分かるので、そうしない）。
  - 利用者名を引く前に数えるので、存在しない利用者名でも同じに遅らせ、同じ答えを返す（知らない利用者名でもパスワードの確かめと同じほどの時間をかける）。
  - **失敗の答えの時間の下限**：ログインの失敗の答えは、遅らせの後、利用者を引き始めてから 250 ミリ秒より前には返さない。利用者名の有無で、データベースの仕事の量（試みの枠を取る・失敗を数える）が違うため。2026-10-18 に手元（16 本の CPU、argon2id m=19 MiB・t=2・p=1）で、間違ったパスワードの失敗を各 200 回測ると、答えまでの時間の中央値は、存在しない利用者名 27.8 ミリ秒・存在する利用者名 28.5 ミリ秒（差 0.7 ミリ秒、ばらつき 1.6〜2.1 ミリ秒）。下限を置くと、各 60 回で 251.0・251.0 ミリ秒（差は測りの精度より小さい）。下限はパスワードの確かめより十分に長いので、混んでいなければ差は出ない（ひどく混んで確かめが下限を超えるときは、上の「同時に回す数」で断る）。下限は保証ではない：確かめが 250 ミリ秒を超える遅い機械や、いまの強さより強いハッシュを持つ利用者（このアプリは既定の強さでしか作らない）では、差が出うる。
  - **失敗の記録の膨らみの抑え**：遅らせの上限を超えた試みの失敗は、1行ずつではなく、1 分の枠ごとに「誰が（存在する利用者名か `unknown`）・理由・回数・最初と最後の時刻」の1行にまとめて残す（`detail` の `aggregated`・`firstAt`・`lastAt`）。上限の中の失敗はこれまでどおり1行ずつ、一時停止にしたことはいつも1行で残す。混んで断った要求（503）も、理由 `busy` でまとめて残す。まとめる鍵は 1 分の枠×利用者×理由なので、持つ数は試された名前の数では増えず、枠をまたいだ失敗は混ぜない。全体の上限を超えた後は、遅らせ始めた印（`throttled`）も、全体で超えた1行のほかはまとめる。まとめた行は、終わった枠の分だけを、枠が替わった後の最初のログインの要求か、1 分ごとの片付けで書く（書けなかった分は戻して書き直す）（プロセスの記憶の中だけに持つので、書く前にプロセスが止まると、その枠の分は失われる）。
  - ログインの途中・ログインした後の確かめ（TOTP・ロックの解除・再認証・パスワードの変更）は遅らせず、利用者ごとの試みの枠で抑える（ほかの人のログインの試みで、ロック中の職員が戻れなくならないように）。
  - 数はプロセスの記憶の中だけに持つ（再起動で消え、複数のプロセスではそれぞれで数える）。1 分の枠が替わったら0に戻す。
- **再認証**：大事な操作の前に、もう一度本人を確かめる。**削除など検査の操作の再認証は、パスワードだけを求める**（TOTP は求めない。二要素の確かめはログインで行う。2026-10-20 に承認者が決めた。それまでは、登録していれば TOTP も求めた）。**例外は1つで、利用者の管理の再認証は、TOTP を登録した利用者には、これまでどおり TOTP も求める**（下の理由）。この決定は再認証だけのもので、パスワードの変更（いまのパスワードと TOTP）と、`SCREEN_UNLOCK_REQUIRE_TOTP=true` のときのロックの解除は、これまでどおり TOTP を求める。一度通れば `REAUTH_MINUTES` 分（既定 5 分）の間は聞き直さない。確かめた時刻は、サーバーの側のそのセッションの行だけに持ち（cookie・本文から読まない）、ほかのセッションには効かず、認証の世代が上がったら（パスワードの変更・TOTP の登録）消す。役割を変えたら、その利用者のどのセッションの印も使えなくする（役割の世代を上げ、印には通した時の世代を添えて比べる）。確かめている間に資格情報・役割が変わっていたら、印を書かない。ログインの途中のセッションからは再認証を通さない。削除の確かめの画面の理由の入力と、確かめの画面そのものは、再認証とは別に残す（3.5）。
  - 利用者の管理だけ TOTP を求める理由：パスワードだけで通すと、管理者のセッションとパスワードを得た人が、新しい管理者を作り足す・役割を格上げする・ほかの管理者の TOTP をやり直すことで、元の管理者の二要素を知らずに、管理者の権限を長く持ち続けられる（2026-10-20 の独立レビューの指摘）。削除は戻せない操作だが、権限そのものは増やさない。承認者の 07:14 の決定（削除の再認証はパスワードだけ）の範囲を、削除などの検査の操作に読んだ（推奨。承認者に確かめていただく）。
  - TOTP を求めない理由：再認証が防ぐのは、ログインしたまま離れた席で、ほかの人が大事な操作をすることで、ログインした本人がまだ席にいるかの確かめにあたる。二要素はログインで済んでいる。画面のロックの解除（下）と同じ考え方にそろえる。
  - **TOTP を登録した利用者の再認証の成功は、失敗の数を消さない**（取った試みの枠を返すだけ。下の「ロックを解く確かめ」の、TOTP を確かめなかった解除と同じ）。パスワードだけの成功で数を消せると、パスワードの変更で TOTP の番号を試し、一時停止の手前で再認証を通して数を消すことを繰り返せるため。
  - **自分の TOTP のやり直しは断る**（別の管理者が行う。断ったことも記録に残す）。管理者のセッションとパスワードを得た人が、自分の TOTP をやり直し、自分の認証のアプリを登録し直せないようにするため。自分のログインの一時停止を自分で解けないのと同じ形にする。
  - データベースの役割が知らない名前（誤記・前の役割の名前など）なら、そのセッションを使わせない（一般に読み替えない）。前の役割の名前の移し替えは migration だけが行う。
  - 利用者の管理（作る・役割の変更・止める／戻す・TOTP のやり直し・一時停止の解除）は、直前 `REAUTH_MINUTES` 分（既定 5 分）の中に再認証していなければ 403 で断り、画面が再認証を求めてから同じ操作を送り直す（ログインした直後でも求める）。ログインの一時停止の間は、再認証の有効時間の内でも、これらの操作を 403 で断る（一時停止の間は再認証を止める、という承認者の決定に合わせる）。自分のログインの一時停止は、一時停止の有無に関わらず自分では解けない（別の管理者が解く）。自分のパスワードの変更は、いまのパスワードと TOTP を、二要素が任意のときのログインした後の TOTP の登録は、いまのパスワードを、その場で求める。
- **画面のロック**：画面（ブラウザ）が、操作（マウス・キー・スクロールなど）の無い時間が `SCREEN_LOCK_MINUTES` 続いたら、画面をぼかしてロックし、BFF にも知らせる。ロックの間は、頁から中身（患者の情報）を外して、ぼかした地だけを出す（ぼかすだけでは、ブラウザの開発者の道具で読めるため）。画面の API と中継は 423 を返し、頁を開き直しても中身を描かない。解くのはパスワード（下の「ロックを解く確かめ」）。同じブラウザのほかのタブとは、最後の操作の時刻とロック・解除を分け合う。**ロックはサーバーの側を正にする。** BFF は、画面が最後に操作を知らせてから（`/api/auth/activity`。操作があれば 15 秒に1回まで。画像の取得などの裏の要求では数え直さない）`SCREEN_LOCK_MINUTES` が過ぎたら、猶予を置かずに、その要求の時点でロックにする（閉じた・離れたタブ、ロックの知らせが届かなかったときのため。画面の側より最大 15 秒早くロックしうる）。ヘッダーの「画面ロック」で、すぐにロックできる。BFF がロックしたら（ほかのタブのロックの知らせでも）、画面は頁を読み直す（描かないだけでは、ルーターのキャッシュと頁に残った描画の元のデータ（RSC の payload）に患者の情報が残るため。読み直した頁は中身を描かない）。
  - **ロックを解く確かめ**：**既定ではパスワードだけで解く。** 例外は1つ：`SCREEN_UNLOCK_REQUIRE_TOTP=true` のとき、TOTP を登録した利用者には、これまでどおりパスワードと TOTP を求める（施設の決まりで要るとき）。画面のロックは、席を外した間に、ほかの人が画面を覗く・操作することを防ぐもので（12 遵守事項⑥）、解くときに確かめるのは「ログインした本人が戻ったか」である。二要素はログインで済んでいる（14 遵守事項⑤の二要素・⑥の認証の決まりは、ログインの認証の話）。ロックの間もセッションは BFF の側に残り（ログインし直すのではない）、解く要求はそのセッションの cookie と CSRF の token が要るので、ほかの端末から解くことはできない。TOTP を求めない既定のときは、送られた TOTP の番号を確かめず、使った段にも数えない（解く画面に6桁の欄を出さない）。ロックを解くパスワードの誤りは、これまでどおりログインの一時停止に数え（上の「ログインの一時停止」）、一時停止の間は解けない。
    - **TOTP を確かめなかった解除の成功は、失敗の数を消さない**（取った試みの枠を返すだけ）。TOTP を登録した利用者に限る（登録していない利用者は、パスワードが持つ確かめの全部なので、これまでどおり0に戻す）。消すと、セッションとパスワードを持つ人が、パスワードの変更で TOTP の番号を試し、一時停止の手前でパスワードだけの解除を通して数を消すことを繰り返し、TOTP の試みの上限を迂回できるため。パスワードの失敗の分だけを消す形にしないのは、失敗の数が1つの数で、どの失敗がパスワードのものかを持たないため（数を分けるより、消さない方が単純で、閉じる側に倒れる）。前の失敗の数は、ログインなど、TOTP まで確かめた成功で0に戻る。
    - **ロックしていないセッションからの解除の要求も、断らずに確かめる。** 画面だけがロックしているずれ（ロックの知らせと印の cookie が BFF に届かなかったとき）でも、本人が戻れるように、閉じる側の作りに合わせる（下の「ずれたら閉じる側に倒す」）。断っても、`/api/auth/lock` でロックしてから送れば同じ確かめに届くので、守りは増えない。迂回の芽は、上の「失敗の数を消さない」で摘む。
    - ログインは、この設定に関わらず、登録していれば TOTP を求める（再認証は TOTP を求めない。上の「再認証」）。解いたことは監査の記録に残し、`detail` の `totp` に TOTP を確かめたか（`true`・`false`）を残す。（2026-10-19 に承認者が決めた。）
  - **ロックの画面からのログアウト**：ロックの画面に「ログアウト」を置く。共用の端末で前の利用者が離席してロックされたままのとき、次の利用者が（前の利用者のパスワードを知らなくても）ログインし直せるようにするため。押すと確認の窓を挟み（本文は 1 行：ロックの前に入力して保存していない内容は残らない。ロックの間は頁に中身を描いていないので、ログアウトで新しく失われる画面の内容は無い）、BFF がセッションを消してから、ログインの頁へ移す。ロックした利用者の情報は、ロックの画面にも出さない。ロックの印の cookie とブラウザに置いたロックの覚え（localStorage・sessionStorage）は消す。ログアウトの要求はロックの間も通す（それ以外の要求は 423）。**監査の記録**には、ふつうのログアウトと同じ `logout` の行に、`detail` の `from` に `screen_lock` を残す（ロック中かどうかは BFF の状態で決め、画面の申し出は使わない）。
  - **ずれたら閉じる側に倒す**：画面の側と BFF の側のロックの状態がずれても、画面がロックされないまま中身を出し続けない。画面はロックするとき、BFF へ知らせる前に**ロックの印の cookie**（`__Host-tsunagi_lock`。`Secure`・`SameSite=Strict`・`Path=/`。値は理由だけ。`src/lib/auth/lock-cookie.ts`）を置く。知らせが届かなくても、次にこのブラウザから BFF へ届く要求（頁の読み直し・別のタブで開く・画像の取得）に必ず付くので、BFF はその要求の時点でロックし、中身なしで描く。印を消すのは、BFF がロックの解除を確かめたとき・ログイン・ログアウトのときだけ（印はロックの側にしか働かないので、偽っても害が無い）。届いていないロックは、タブの sessionStorage にも持って読み直しの後も閉じたまま送り直し、BroadcastChannel で開いているほかのタブにも閉じてもらう。ロックの知らせ（POST）が届かなくても（網の切れ・BFF の失敗）、画面はロックのまま中身を外し、届くまで 10 秒ごとに送り直す（届いたら読み直す。読み直した後も sessionStorage から送り直す）。
    - **守れないもの**：BFF にまだ届いていないボタンのロック（無操作の期限の前）は、その端末を操作している人がブラウザの側でロックの印の cookie を消すと、別のタブから中身が出る（BFF が知らないロックは、BFF の側では守れない）。BFF に届いて記録したロック・無操作の期限を過ぎたロックは迂回できない。印を消せるのはその端末を操作している人に限られるので、直さずにここに書く。どの要求でも 423 が返れば、ロックの画面にして読み直す。画面は 10 秒ごとに BFF の状態（`/api/auth/status`。読むだけで、操作の時刻は数え直さない）を確かめ、ほかのタブの知らせを取りこぼしても閉じる。解くのは、BFF がパスワード（`SCREEN_UNLOCK_REQUIRE_TOTP=true` のときは TOTP も）を確かめて通したときだけ（BFF の側がロックしていないずれのときも確かめる）。ほかのタブの「解いた」の知らせでは、BFF に聞き直してロックしていないと答えたときだけ戻す。操作の無い時間は、そのタブの時計の進み方（`performance.now`）で数え、ほかのタブの操作の時刻は延ばす向きにだけ使う（先の時刻は使わない）。
- **セッション**：cookie（`__Host-tsunagi_session`）は乱数の token で、`HttpOnly`・`Secure`・`SameSite=Strict`・`Path=/`、`Domain` は付けない（名前の `__Host-` で、ブラウザはこの形の cookie だけを受けるので、同じ親のドメインのほかのサーバーや TLS の無い頁から、同じ名前の cookie で上書き・固定されない）。CSRF の token は cookie ではなく、セッションの行に持って頁に渡す（下の「CSRF の対策」）ので、cookie はこの1つだけ。データベースには token の SHA-256 だけを持つ。ログインし終えたとき（ログインの途中の段から進んだとき）は、途中の token を捨て、新しい token と CSRF の token のセッションに替える。途中のセッションを消せたとき（まだ残っていたとき）だけ新しいセッションを作る（同じ途中のセッションから二度ログインさせない。もう無ければ 409）。作った後に、利用者が確かめた時のまま（有効・一時停止でない・パスワードの変更の時刻と TOTP の秘密が同じ）かを見て、違えば作ったセッションを消す（確かめている間にパスワードを変えた・TOTP をやり直した・止めた利用者の古いログインを、後から生き残らせない。利用者を変える操作は、どれも利用者の行を変えた後にセッションを消すので、どの順に重なっても残らない）。データベースの transaction の隔たりには頼らない（SQLite の adapter は1つのつなぎを使い、transaction の途中にほかの要求の文が入りうる。わざと取り消すと、その文まで消えるので、transaction の中で断るときも取り消さない）。TOTP の登録とパスワードの変更は、確かめと書き込みを1つの文（条件つきの更新）にし、利用者が有効・パスワード（と TOTP の秘密）が読んだ時のまま・そのセッションがまだ使える（残っていて、同じ段で、期限の前）ときだけ書く。書けたら、ほかのセッションを閉じる。
  - **認証の世代**：利用者は認証の世代（`credentialVersion`）を持ち、パスワードの変更・TOTP の登録・TOTP のやり直しで 1 つ上げる（上の条件つきの更新と同じ文で）。セッションは作った時の世代を持ち、要求のたびに照らし合わせて、違えば使わない（401。その場で消す）。そのため、ほかのセッションの削除は後片付けで、削除が止まった・失敗したときも古いセッションは使えない。変えた人のいまのセッションは、新しい世代に合わせる。セッションを作るときも、確かめた時の世代を持たせ、作った後に世代が上がっていれば消す。
  - **期限と片付け**：ログインし直したら、そのブラウザが持っていた前のセッションを消す。ログインの途中（TOTP の入力・登録・パスワードの変更の待ち）は `LOGIN_PENDING_MINUTES` 分（既定 10 分）、ログインした後は `SESSION_MAX_HOURS` 時間（既定 12 時間）で切れる。期限の切れたセッションは、起動の時と 1 分ごとに片付ける（片付ける前でも使わせない）。役割と状態は要求のたびにデータベースから読み、管理者の変更は次の要求から効く（止めた利用者・TOTP をやり直した利用者のセッションは閉じる）。`Secure` なので、TLS の外では送られないことがある（手元の `127.0.0.1`・`localhost` を除く）。施設ではリバースプロキシで TLS にする。
- **CSRF の対策**：`SameSite=Strict` に加え、状態を変える要求（POST・PATCH）は `Origin` がこのアプリと同じであることと、セッションごとの token（`x-csrf-token`）を確かめる。ログインの要求は、まだセッションが無いので `Origin` だけを確かめる。`Origin` は要求の `Host` と比べるので、リバースプロキシは `Host` を書き換えずに渡す。
- **監査の記録**：ログイン（成功・失敗とその理由）・ログアウト・ログインの一時停止とその解除・回数の上限で断ったこと・画面のロックと解除・再認証・TOTP の登録とやり直し・パスワードの変更・利用者を作る・止める／戻す・役割の変更を残す。**パスワード・TOTP の値・セッションの token は記録しない。** 知らない利用者名の失敗は、打ち間違えたパスワードであることがあるので、名前を記録しない（`unknown` として残す）。遅らせの上限を超えた試みの失敗と、混んで断った要求は、1 分の枠ごとにまとめて1行で残す（上の「失敗の記録の膨らみの抑え」）。

**このアプリでは担えないもの**（文書に書く）：サーバーの OS のログインの二要素（14 遵守事項⑤・表14-1）、ネットワーク・端末の管理、バックアップと復旧の手順、委託先の管理。

### 3.7 患者ごとの時系列と比べ（段 8）
- **一人の患者の検査を、1 画面で見渡す。** 患者ごとの時系列は、その患者の検査の並びを同じ画面に出す。画面を替えながら探す形にはしない。
- **表**：縦がモダリティ（CT・MR・CR/DX・US・ES・DOC・SR）、横が検査日。セルに代表のサムネイル・検査の記述・枚数・既定のビューアを出す。ダブルクリックで既定のビューア、▾ で別のビューア。
- **詳細のパネルに、同じ患者の過去の検査を出す。** 3.1 の詳細のパネルに、選んだ検査と同じ患者の過去の検査の一覧（検査日・モダリティ・検査の記述）を出し、そこから比べる相手を選べる。過去の検査の一覧は、許可の一覧（原則 8）で絞った項目だけで組み立てる。
  - **過去の画像の先読みはしない。** 比べる相手を選んで開くまで、過去の検査の画像は取りに行かない。先読みは、取り出しの遅い保管庫のための機能で、この道具の想定する画像サーバーでは要らないため。一覧のための問い合わせ（検索）だけを行う。

### 3.8 後ろに回すもの
原則 9 により、段を決めずに後ろへ回す。作るときに、段と完了の線を決める。
- **ワークリスト**：Orthanc の Worklists のプラグインで、予約の一覧・作成・削除。**作るときの文字のコードは UTF-8 だけにする**（JIS を指定すると漢字が黙って消えることを 2026-10-18 に確かめた。下の「既知の制約」）。オーダと受付番号の照合は、このときに考える。
- **外部の認証**（`AUTH_MODE=oidc`）。つなぐ先（FreeIPA・Keycloak・Authelia などの OSS）は、作る前に決める。
- **ブラインド読影の役割**（下）と、閉じた網で動かすための設定（外へ出る通信をしない・読み取りだけのファイルシステムと root でない利用者で動く・秘密をすべてファイルで渡せる）、監査の記録の持ち出し（ハッシュのつなぎを確かめられる CSV か JSON Lines と、確かめの手順）。

- **文書の取り込みと表示**：PDF・JPEG・PNG を落とすと、Orthanc の `/tools/create-dicom` で DICOM（Encapsulated PDF・Secondary Capture）にして入れる。文字のコードは UTF-8（ISO_IR 192）。
- 紹介の CD・DVD の書き出し（DICOMDIR）、ほかの PACS へ問い合わせて取りに行く道（C-FIND・C-MOVE。外へ出る道が増えるので、要るかを改めて決める）、Weasis（`weasis://`）、Passkey、日本語のほかの画面の言葉。
- **ブラインド読影の役割**（候補）：研究・教育で、読む人に元の患者の情報を見せずに画像を見せる役割。研究用の ID だけを出し、元の患者 ID・氏名・生年月日・施設・臨床の情報を BFF から返さない。隠した項目での検索もできなくする。どの項目を隠すかは設定で決める。**既定では無効。** 有効にしても、ほかの役割の見え方・検索・操作は変わらない（ブラインド読影の役割の利用者にだけ効く）。使い方の例：臨床研究の画像の集め先（研究用の Orthanc）の前に置き、読む人はこのアプリだけを通る。書き込みの操作は、この役割には与えない。

## 4. 開発用の認証の切り替え（`AUTH_MODE=dev`）
- ログインを省き、画面の上に `[検証モード｜役割：管理者・一般]` の切り替えを出す。画面の全体に「検証モード」の帯を出し続ける。
- **書き込みの操作（送る・書き出し・削除・取り込み・値の修正など）は止める。** 書き込みも試すときは `DEV_ALLOW_WRITE=true` を足す（`AUTH_MODE=dev` はモックだけなので、書くのはモックの中だけ）。検証モードのほかで `DEV_ALLOW_WRITE=true` にすると起動しない（段 4 から。段 3 までは、検証モードでも起動しなかった）。止めているときは、画面の帯に「書き込み：無効」と出し、送信のボタンを出さない。書き込みを止めているときも、役割の確かめと監査の記録は通し、止めたことを記録に残す。
- **`AUTH_MODE=dev` は、いつも `BACKEND_MOCK=true` のときだけ起動する**（モックでなければ、待ち受けの住所が手元だけでも起動しない）。実の画像サーバーには `local`（段 1b）を使う。実の画像サーバーに対して `dev` を使う形は持たない（書き込みの操作を持つので、ログインの無い形で実の Orthanc に書かせない）。
- 監査の記録は、検証モードでも取る（役割の切り替えも記録する）。

## 5. 公開と配布
- リポジトリは公開。**社内の名前・秘密・実の患者のデータを入れない。** 見本のデータ（`tests/fixtures`）は合成の患者だけで、公開の前に中身を人が確かめる。
- **Orthanc とセットで導入する形**（`deploy/compose.yaml`。2026-10-20 に承認者が決めた）：
  - tsunagi-dicom と Orthanc は別々のコンテナにし、1つの compose で配る。Orthanc のイメージは `orthancteam/orthanc` を版と digest で固定する（結合の試験と同じ）。
  - 2つは内部ネットワーク `backend`（`internal: true`）でつなぐ。`backend` に入るのは tsunagi-dicom と Orthanc だけで、tsunagi-dicom は `http://orthanc:8042` の REST と DICOMweb を使う（Basic 認証。利用者 `tsunagi`）。
  - **Orthanc の REST（8042）はホストに公開しない。** ホストに公開するのは、tsunagi-dicom の画面（3000）と Orthanc の DICOM（4242）だけ。待ち受けの既定は 127.0.0.1 で、施設で検査装置から受けるときは `ORTHANC_DICOM_BIND` を変える。画面を施設のネットワークに公開するときは、TLS を終端するリバースプロキシを前に置く。
  - Orthanc は DICOM のネットワーク `dicom` にも入る。`internal: true` のネットワークだけでは、DICOM のポートをホストに公開できず、ほかの機器への送信（C-STORE）もできないため。Orthanc の REST は `dicom` の側でも待ち受ける。`dicom` はコンテナどうしの通信を止める（`com.docker.network.bridge.enable_icc: false`。変数 `ORTHANC_DICOM_ICC`。開発用の compose だけが `true` にする）ので、`dicom` にほかのコンテナを足しても、その中から Orthanc には届かない。
  - **Docker のホストの上の利用者とプロセスは、Orthanc のコンテナの IP アドレスで REST（8042）に届く**（`backend` の側も `dicom` の側も。認証は要る）。ホストにログインできる人を絞る。
  - Orthanc の設定：DICOMweb のプラグインを有効にし、認証を必須にする。利用者とパスワード（`RegisteredUsers`）は secret のファイルで渡す。C-STORE は、登録した接続先（`DicomModalities`）からだけ受ける（`DicomAlwaysAllowStore: false`。C-FIND・C-MOVE・C-GET も `DicomAlwaysAllow*: false`）。AE タイトルと接続先は、施設の設定ファイル（`ORTHANC_SITE_CONFIG`。既定は `deploy/orthanc/site.json`）に書く。
  - 施設の設定ファイルの既定では、呼ばれた AE タイトルを確かめ（`DicomCheckCalledAet: true`）、接続先の AE タイトルと送り元の IP アドレスの組を確かめる（`DicomCheckModalityHost: true`）。登録した AE タイトルを名乗るだけでは、ほかのホストから C-STORE を通せない。このため、接続先の `Host` には、検査装置の IP アドレス（Orthanc から見える送り元）を書く。
  - **送り元の IP アドレスが変わる場合がある。** ホストの 127.0.0.1 に公開したポートなど、Docker の userland-proxy を通るつなぎでは、Orthanc から見える送り元が、検査装置ではなく `dicom` のネットワークの gateway の IP アドレスになる。そのときは `DicomCheckModalityHost` で検査装置を見分けられないので、施設のネットワークの側で送り元を絞る。開発用の compose の設定ファイル（`docker/dev/orthanc/site.json`）は、接続先の `Host` がコンテナの名前なので `DicomCheckModalityHost: false` にしている。
  - 確かめた版：Docker Engine 29.9.1・Docker Compose v5.6.0（p5820）と、GitHub Actions の ubuntu-24.04 の Docker。Docker Compose は v2.24 以上が要る（`include` と `env_file` の `required`）。
  - volume は、Orthanc の画像とデータベース（`orthanc-db`）と、tsunagi-dicom の `/data`（`tsunagi-data`）を分ける。
  - secret のファイル（`SESSION_SECRET`・Orthanc のパスワード・最初の管理者のパスワード）は `deploy/init-secrets.sh` が乱数で作る。リポジトリに入れない。
  - 開発・試験用の compose（`docker/dev/compose.yaml`）は、この compose を include し、dicom-test-generator（送信元）と DCMTK の storescp（送信先）を足す。`docker/dev/up.sh` で立てる（[`round-trip-test.md`](round-trip-test.md)）。
  - 1つのコンテナだけの `compose.yaml`（リポジトリの直下）は、モックで画面を試すときと、Orthanc を別の場所に置くときに使う。
- CI（GitHub Actions）：PR で lint・型・Vitest・Playwright（モック）と、結合の試験（試験の中で立てた Orthanc と DCMTK のコンテナ）と、開発用の compose の流れ（`tests/flow`。開発用の compose をそのまま立てる）。後の2つは `.github/workflows/integration.yml` にあり、必須のチェックにはまだしていない。`main` への merge では試験だけを流し、イメージは出さない。イメージを作って GHCR へ出すのは、版のタグの push・手動（`main` を選ぶ）・週に1回の作り直し（イメージの中の包みの更新を取り込む）のときだけ。**`permissions: packages: write` は、イメージを作る仕事と古いイメージを片付ける仕事にだけ**付け、`id-token: write`（署名）はイメージを作る仕事にだけ付ける（リポジトリ全体を読み書きにしない）。

## 7. 既知の制約（2026-10-18 時点の実測）
- Orthanc の Worklists のプラグインで、REST（`POST /worklists/create`）でワークリストを作るとき、漢字とかなを JIS（ISO 2022）で入れる道が無い（2026-10-21 に、イメージ 26.9.1（Orthanc 1.13.0）で測り直した）。
  - 規格どおりの JIS の指定は、コード拡張の形の複数の値で、2 つ目から先に `ISO 2022 IR 87` を置く（1 つ目は空か、`ISO 2022 IR 6`・`ISO 2022 IR 13` など。PS3.3 C.12.1.1.2・表 C.12-3・表 C.12-4）。`\ISO 2022 IR 87`・`ISO 2022 IR 6\ISO 2022 IR 87`・`ISO 2022 IR 13\ISO 2022 IR 87` は、どれも断られる（400 `Unknown encoding`）。
  - `ISO 2022 IR 87` だけ（1 つの値）は、規格の定義語に無い形（1 つの値のときはコード拡張を使わない。表 C.12-2 に無い）。Orthanc は受け付けるが、漢字とかなが消える（エラーにならない）。この形は使わない。
  - 指定しなければ UTF-8（ISO_IR 192）で正しく入る。UTF-8 に対応しない古い装置へ JIS で渡すことは、この段の範囲外。
- Orthanc の設定の氏名の整形（1本の正規表現）では直せない形が3つある（`^Taro` の頭の空白など）。このアプリの氏名の解析では直す。
- 削除（3.5）：Orthanc の REST に版を条件にした削除が無いため、最後の照合から `DELETE` までの間の変化と、秒の単位の版（`LastUpdate`）で拾えない変化は防ぎきれない。だから、このアプリを使う場面は、治験・研究・試験の環境にとどめる（2026-10-20）。
